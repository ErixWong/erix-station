## 0. 一句话

> **会话停下 → 平台把事实摆到审查 agent 眼前（不下判决）→ agent 判 → 不过就一句话要求整改 →
> 灌回原会话 → 再判一次 → 再不过转人工。**
>
> ⚠ 只有 `red` 走「整改 → 回灌」。`needs-human` 直接转人工，**不回灌**（§6.2）。

**M9 只有一个判决者。** 平台只**采集事实**、不替 agent 下结论；
（范围仅限 M9：`02`/`05`/`06` 里其他宏的机械判据照旧，见 §1。）

## 1. 为什么 M9 不设「机械判据层」（范围：只限 M9）

> ⚠ **范围限定（2026-11-15 审计后修正）**：本节撤掉的是「**M9 旁边再放一个机械判决者**」，
> **不是**「整个平台不要机械检查」。`02`/`05`/`06` 里的机械判据（M7 的产出非空、失败分诊表、
> 变异测试）**保留**。机械检查在本框架里的角色是**可引用事实与硬前置**，不是最终判决。

曾经设计过「判据层 ①：机械（`gitlight` reason 直接出整改话，零 token），M9 语义层只在它全绿时才跑」。
**撤掉了**，三条理由：

1. **Goodhart**：`git commit` 一下灯就绿，哪怕内容是垃圾（「一个空 commit 也能让灯绿」是站内既有结论）。
2. **两个判决者，用户永远信便宜的那个**：机械层零 token 秒级、语义层一个 run 分钟级 ⇒
   机械层会**替代**语义层，不是漏斗。
3. **它给的是确定性的假象**：**界面只有 4 种灯色**（`portal/src/gitlight.js:41`
   `LIGHT_ORDER = ['red','yellow','grey','green']` —— 注意它是**聚合排序键**，不是封闭 enum
   **【实测：代码行】**），而工作树的状态空间远大于四种。
   `reason` 也不是封闭枚举 —— 它是「这次采样为什么是这个色」，多仓库/部分扫描下取值会继续增加
   （`unreadable` / `busy` / `unchecked_partial` / `no_repo` / `covered_by_outer_repo` / …）
   **【推断：按代码分支推断，未穷举】**。
   **藏起来的不确定性比显式的不确定性更危险** —— 看到"灯绿了"就不再追问，而问题还在。

⇒ **机械证据 ≠ 机械判据**。平台必须把事实采集得**完整且不可回避**（agent 只读，看不到就是不知道），
但**不许替 agent 下结论**。

⚠ **反例要认**：有些机械检查确实比模型可靠（「某条测试退出码必须为 0」「某文件必须存在」）。
它们的正确位置是**硬前置**，但**硬前置不是第二个判决者** —— 措辞要精确：

| 说法 | 成立吗 |
|---|---|
| 硬前置失败 ⇒ 直接落 `verdict=red`、不进模型 | ✅ 成立，但它是**短路**（一个判决，不是两个） |
| 硬前置与模型**并列**各自发布判决，再合并 | ❌ 不许，这才是「两个判决者」 |

⇒ 判据：**硬前置失败时模型根本不跑**（短路），所以全程只有一个判决被产生。
`§6.1` 的「产生者」列要相应写清：`red` 可能由**模型**产生，也可能由**硬前置短路**产生，
但**同一行记录里只有一个**。

## 2. 概念图（五个东西的关系）

```
值守（= 一组 session-scope 订阅 + 一个 until）        ← 不是新概念，是一个组合
  ├─ 完成审查    run-review   有判决、有回灌          ← 第一版第 4 条（M9）
  ├─ 静默告警    run-silence  纯通知（M8）
  └─ 终态通知    run-notify   纯通知（M1）

界面右上角（user scope，管理员代配）
  └─ 定时任务    scheduled-task  任务型（M7）
```

**「值守」不是新实体**：它就是「用户在会话右上角勾的那几个 + 一个到期时间」。
勾了「完成审查」= 开了值守。

## 4. 事实采集（平台的责任，不下判决）

审查启动前，平台把下面这些**摆进工作包**。缺任何一项，agent 就是"不知道"：

| 事实 | 来源 |
|---|---|
| 原任务 | `messages` 首条 user |
| 执行者最后的说法 | 最后一条 assistant |
| `git status --porcelain -uall` | shell（平台侧） |
| `git log --oneline -5` | 同上 |
| HEAD / 是否 detached / 是否有远端 | 同上 |
| `git diff --stat` | 同上 |
| **原 run 跑过的验证命令与退出码** | 从 transcript 的 `tool_result` 提取 |
| `termination.reason` / `error_code` / 轮数 / 用量 | `runs` |

⚠ **第 7 行是硬要求**：审查者只读 ⇒ 它跑不了测试 ⇒ 「验证过没有」只能引用原 run 的记录。
没有这一项，它只能猜。

### 4.1 还要补三组事实（2026-11-15 审计后补）

**① 审查现场**（回答「审的是哪一份成果」）：审查读的是原会话的**活目录**（见 §5.1），
没有「冻结副本」概念，所以只描述「审查开始时那一刻的活目录」。

| 事实 | 为什么 |
|---|---|
| 审查开始时的 `HEAD`（sha / 分支 / detached） | 说清「审的是哪一刻的仓库状态」 |
| `git status --porcelain -uall` + `git diff --stat` 摘要 | 工作树当时的改动面；`--stat` 只是统计，**不是可复核的变更清单** |

**② 验证与审查的绑定**（回答「那些测试结果还算不算数」）：

| 事实 | 为什么 |
|---|---|
| 命令原文 + cwd + 退出码 + 结束时间 | 只有退出码不知道跑的是什么 |
| 具名失败用例（若有） | 「失败 3 个」不如「`not ok 7 - 空态四种`」 |

⇒ **只读审查不许声称「测试通过」**。它能说的是：「原 run 跑过这些命令，退出码 Y；
本次审查未独立复验。」这是两件事，文档必须分开写。

**③ 过滤边界**（回答「审查看到的东西是不是完整的」）：

| 事实 | 为什么 |
|---|---|
| 排除了哪些 ignored 文件（清单） | 排除掉构建配置会让 agent 把不完整目录当完整 |
| 密钥/环境文件如何脱敏 | `.env` 之类既不能给也不能静默丢弃，要记「已脱敏」 |

⚠ 审计原话：「只读审查无需声称测试通过」—— 这一条比原来那句「验证过没有」准确，已采纳。

## 5. 审查（唯一的判决者）

| 项 | 做法 |
|---|---|
| 会话 | **新会话**（`trigger_kind='synthetic'`），同容器、**同 cwd（原会话的 `~/projects/<项目名>`）** |
| 审查对象 | **活目录**（原会话的工作目录，不建快照）——理由见 §5.1 |
| 只读 | jail root = 活目录、`writable: []`、**不给 `shell`**、**不给 note** |
| 工具面 | 只有 `readFile` / `searchText` / `tree` |
| 输出 | 见 §6 |
| 清理 | 无（不建副本，审查结束没有要回收的东西） |

### 5.1 为什么不做快照（直接读活目录）

M9 的审查 run 把 cwd 直接指向**原会话的工作目录**（DB 里存的 `~/projects/<项目名>`，
每个普通 run 都在用这个路径），**不再**为审查单独 `git worktree add` 建冻结副本。

判据（口径，不是某次事故的过程）：

1. **前提不成立**：「必须 worktree」的唯一硬前提是「同一 cwd 同时有两个 run 在写」。
   但真实工作流是「开一棵 worktree → 派一个 agent 干 → 干完再来审计」，这期间没人碰同一目录。
   前提不成立，就没有「通过指哪一刻的工作树说不清」这个问题。
2. **即便成立也不值这个价**：万一真出现两个 agent 同目录，后果只是「审查读到稍微新一点的
   状态」——它仍在判断「这活干得好不好」，看到更新的代码不算错判。冻结只换来「稍旧一点的一致视图」，
   换不来判决的正确性。
3. **路径问题整个消失**：活目录走的是会话约定 `~/projects/<项目名>`（`validateRunCwd` 认它），
   不引入「portal 建在别处、runner 看不见、跨容器路径翻译、孤儿清扫」这一整套零件。
   快照要解决的一致性问题，代价是这些零件；读活目录根本不需要它们。
4. **搬运是重资产、收益薄**：整树拷贝/worktree 的成本随项目规模与脏文件数增长，
   还要四道门闸（超时/字节/文件数/磁盘），每多一道多一个失败原因；而这些只买到「稍旧的视图」。

⇒ **口径**：审查读**活目录**；一致性交给「审查开始时的 HEAD + git status 摘要」（§4.1）去描述，
而不是靠一份冻结副本来保证。运维若要关掉审查，用 `reviewMode='disabled'`（不再写副本相关列）。

### 5.2 为什么只读必须「不给 shell」

`shell` 是 `bash -c <command>`，无命令白名单（`runner/lib/shell-tools.js:84-98,192`）**【实测】**。
`cwd` 只是起点，`cd ~/projects/foo` 就逃出审查目录 ⇒ jail 管不到它。

⚠ 两道门都要关，且**装配点有两处**：`runner/worker.js:613-615`（registry）与 `:643`（`baseToolSchemas`）
**【实测】**。只改一处等于没改。

### 5.3 审查现场的生命周期（读活目录 ⇒ 没有建/清这一环）

读活目录后**没有**「建快照 / 搬运 / 一致性校验 / 清 worktree / 孤儿清扫」这条流水线——
审查 run 起在活目录上、结束就结束，平台侧不产生需要回收的副本。于是：

- **没有搬运**：无 `worktree add` / `diff --binary` / `apply` / `rsync` ⇒ 也没有它们各自的失败原因。
- **没有一致性校验**：不比对「搬运前后指纹」；审查读到的即审查开始时的活目录（前提见 §5.1 判据 1）。
- **没有孤儿清扫**：`macro_runs.worktree_path` / `snapshot_id` 两列保留（历史数据），但**不再写入**、
  也没有启动扫描去回收它们。
- **失败出口收敛**：只剩「审查 run 超时 / LLM 失败 / 工作包构建失败 / 首行非法 / 回灸 409」（§5.4），
  不再有快照那批 `worktree_add_failed` / `patch_apply_failed` / `disk_low` 等。

只读仍然由 jail + 「不给 shell」保证（§5.2）：审查 agent 只能读、不能改活目录，
所以「读活目录」不会带来「审查把目录改了」的风险。

### 5.4 五种失败出口（每种都要有持久状态）

| 情况 | `state` | `verdict` | 谁被通知 | 回灌吗 |
|---|---|---|---|---|
| 审查 run 超时（8 轮 / 240s 到点） | `failed` | `unclassified`（未判） | 用户 | ❌ |
| LLM / API 失败 | `failed` | `unclassified` | 用户 | ❌ |
| 工作包构建失败（§4.1 事实采集出错） | `failed` | `unclassified` | 用户 | ❌ |
| 首行格式非法 | `done` | `unclassified` | 用户 + 管理员 | ❌（存原文供人看） |
| 回灌 409 `run_in_progress` | `skipped` | **保留原判决** | **不通知**（人在场） | ❌，记 `deferred` |

⚠ **前四种**（超时 / LLM 失败 / 构建失败 / 首行非法）都**不许伪装成 `red` 或 `needs-human`**
—— 它们是「没判成」，不是「判成没过」，所以统一落 `unclassified`，界面显示「未判」。

⚠ **第五种（409）不是失败**：审查**已经判出来了**，只是**送不进去**。
所以 `verdict` 保留原值、`state=skipped`、`skipped_reason=deferred`。
把它也归到 `unclassified` 会抹掉一次成功的审查 —— 这是两件事，不能合并。

### 5.5 `until` 到期时的在途审查

`until` 到期 ⇒ `enabled=false`，但**不强杀已经启动的审查**：

| 时刻 | 行为 |
|---|---|
| 到期前已启动的审查 | 允许在 8 轮 / 240s 预算内收尾，结果正常入流水 |
| 到期后 | **禁止**由它再触发整改 run 或下一轮审查 |
| 到期通知 | 与"最后一轮结果"分两条，文案要说清"这轮结果之后不会再审" |
| 用户主动取消值守 | 与自然到期**分开处理**：可中止在途审查，并记 `cancelled_by_user` |

⚠ 没有这一格会出现：到期那一刻在跑的审查回来触发了一次整改，用户以为已经关了。

⚠ **同 UID 不等于"文件系统给不了只读"**（我曾这么写，是错的）。准确说法：
同 UID ⇒ **不能靠属主/传统权限做每会话区分**；只读靠「换根 + 空 writable + 无 shell」。

## 6. 判决的落库：第一行固定格式

回灌要一句话（自由文本），面板要能显示判决（四档）—— 两者用一个最小约定解决。

### 6.1 唯一映射表（全文以此为准）

| 存储枚举（`macro_runs.verdict`） | 模型首行 | 界面词 | 谁产生 |
|---|---|---|---|
| `pass` | `结论：通过` | 通过 | 模型 |
| `red` | `结论：整改` | 整改 | 模型 |
| `no-op-claim` | `结论：未证实有改动` | 未证实有改动 | 模型 |
| `needs-human` | `结论：需人工` | 需人工 | 模型 |
| `unclassified` | —— | 未判 | **平台**（未完成 / 超时 / 首行非法） |

⚠ **`未判` 是平台状态，不是第五种模型判决**，模型不许输出它。
旧稿里的「未通过 / 未达成」已按本表全部替换为 `整改`，**不再作为独立存储或解析枚举**。

### 6.2 首行契约与 fail closed

```
结论：整改
有 3 个未跟踪文件没纳入版本管理：a.js, b.ts, c.md
```

- 平台只接受**首行完整匹配** `^结论：(通过|整改|未证实有改动|需人工)$`
- **正文原样回灌**（前面加 `[系统]`），不引入 JSON、不要求 findings 数组
- **非法输出一律 fail closed**：缺行 / 前置 BOM 或 Markdown / 大小写或空格变化 / 未知值 / 首行被截断
  ⇒ 存原文、`verdict=unclassified`、界面显示「未判」、**不自动回灌**、转人工并发通知
- 不许把正文里偶然出现的「结论：通过」当首行

⚠ **`needs-human` 走人工出口**（通知人），不套用「整改回灌」这个动作 —— 它要求的是人看，不是 AI 再改。

⚠ 这是**有意的取舍**：代价是「整改到第几条了」机器不知道，进度只能靠人看。

## 7. 回灌（唯一的环）

```js
// ⚠ 只在 verdict === 'red' 时执行；needs-human 走人工通知，不走这里
postMessage({
  sessionId: 原会话,
  content: "[系统] <结论之后的正文>",
  triggerKind: 'synthetic',   // CHECK 里已有，零迁移
})
```

| 约束 | 为什么 |
|---|---|
| 幂等 `(assignment, anchor, 判据)` | 否则换个措辞就再灌一次，无限循环 |
| `depth ≤ 1` | 两轮「AI 说成了 / AI 说没成」说明判据不清楚 |
| `409 run_in_progress` ⇒ 记 `deferred`，**不重试** | 人已在场，机器人插话只会更乱 |
| 正文必须以 `[系统]` 开头 | 模型读到的是一段 `role=user` 文本，它不知道这是系统说的 |

### 8.4 用户回来看到什么

```
值守已结束（11-16 09:00 到期）

审查 3 次：
  · 9f3a  整改 → 已回灌（未跟踪文件）
```

## 11. 风险与防线

| 风险 | 防线 |
|---|---|
| 回灌成环 | `depth ≤ 1` + 幂等键 |
| 审查对象在变 | 读活目录时读到稍新的状态不算错判（§5.1 判据 2）；仍保留「同 cwd 有活跃 run 不启动」的 soft-guard |
| 用户以为在守、其实没守 | 到期通知 + 面板「上次评估时刻」+ 管理台 `skipped_reason` |
| 审查者改了用户代码 | jail + `writable: []` + 无 shell（审查只读，见 §5.2） |
| 成本失控 | 值守有 `until`；单次预算 8 轮 / 240s；同 cwd 有活跃 run 不启动 |

### 11.1 「同 cwd 无活跃 run」必须是原子的

⚠ **`capacity=2` 本身不是锁。** 先查"没有活跃 run"、再启动审查，两步之间另一个 run 可以起来。

⇒ 判据落在**同一条 SQL 的条件插入/条件更新**里（或 `SELECT … FOR UPDATE` 锁住该 cwd 的登记行），
不能写成"查一次、然后启动"。查失败/有活跃 run ⇒ 记 `skipped_reason=active_run_in_cwd` 并等下一个事件。

⚠ **这把锁必须被所有会写同一 cwd 的 run 启动路径共用** —— 用户发消息、队列 drain、
M7 定时任务、M9 审查，全部走同一个条件写入。只在 M9 这边加锁 = 没锁。

⚠ **人优先不靠 `capacity`**：容器 `capacity=2` 只说明能并行两个，不保证先后。
人优先必须由**会话级互斥**（同会话单活跃 run）+ 排队规则落实。

**人优先**（`08` §11 那条）同理：用户发消息时若审查在排队 ⇒ 审查标 `superseded`，
**不得回灌过期结论**，重新开始时针对新状态重审。
