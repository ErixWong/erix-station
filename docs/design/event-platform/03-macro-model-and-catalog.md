# 03 · 宏模型与能力清单：管理员定义，用户直接用

> 状态：可研（2026-11-07）。本文记录一个**改变简化版 scope 的决定性收敛**：
> 把「用户可写的规则」换成「**管理员定义的宏目录 + 用户订阅**」。
> 前提仍未变：只做设计，不做开发。

---

## 1. 结论

> **宏不是「省掉用户配置」的便利功能，它是一次范围缩减：把「需要一门规则语言」降级成「需要一张目录表」。**
>
> ⚠ **但它不是「复杂度消除」，是「复杂度集中」**：场景五的「这周没提交」、场景四的「这次升级会红几格」——
> 宏表达不了，必须由**源**算完以 `state` 枚举交出来。⇒ 复杂度从「N 个用户写的规则」搬到「M 个源」
> （`M << N`、可测、可审查、可版本化）。这才是宏模型的真正论证，不是「用户省事」。
> 代价：**源会成为平台里最重的代码**，每个源都必须有「state 枚举是什么意思」的文档与判据，否则它就是黑箱。

三件事同时消失：

| 原本要写的 | 宏之后 |
|---|---|
| 规则表达式语言（谓词、条件、组合） | **不存在**——宏内部零分支（§4.1） |
| 规则的权限模型（谁能写、谁能改、谁能看） | **不存在**——用户不能写规则，只能订阅（§6） |
| 成本不可预估（用户自建规则 × 模型调用） | **可预估**——预算随宏一起定义，管理员能算总账（§6） |

而它换来的东西不是「用户省事」，是 [03](02-event-model-and-verdict.md) 那篇的核心命题落地：
**把一个已经被验证过的验收流程变成可复用的。**
（不是复用「流程」——见 §3，那是 n8n template 的做法，也是我们不该学的。）

---

## 2. 三面分离：定义 / 执行 / 呈现

「在管理台实现简版」这个提法里有三件不同的事，它们落点不同：

| 面 | 是什么 | 落点 | 为什么 |
|---|---|---|---|
| **定义面** | 宏目录、参数、预算、全局开关 | **管理台**（`admin.<域>:9443`） | 这是运维决策，不是用户决策 |
| **执行面** | 事件求值、边沿判定、投递、血统 | **portal 后端**（不属于任何 UI） | 它是后端循环，不该依赖有人打开页面 |
| **呈现面** | 用户看到「这个目录被哪些宏盯着」「这个会话被唤醒过几次」「证据」 | **工作台**（session 相关） | 证据落在会话账本里，用户在那儿看 |

### 2.1 一条硬边界（#450 之后就是物理的）

管理台入口的边缘白名单**只放** `①SPA ②/api/admin ③/api/auth + /api/me`，其余 `/api/*` 一律 deny。
⇒ **任何「用户侧」的动作（订阅、查看自己的宏、看证据）都不能做成 `/api/admin/*`**，
否则用户为了开关一个宏得开两个 host —— 这是可用性灾难，不是洁癖。

⇒ 正确的切法：**宏的定义与预算是 admin API；宏的订阅与证据是用户面 API。**
同一个宏在两个 UI 里各出现一半，**这是设计要接受的分裂，不是 bug**。

## 3. 宏是什么（五格）

```
macro:
  anchor_type   目录 | 仓库 | 端口 | 服务 | 会话 | 用户   ← 它盯着什么（见 §4.2 三层）
  on_state      (source, object_key, state) 的枚举值  ← 什么时候动（封闭，允许派生）
  action        投一句话 / 起一个 run / 只记一笔 / 发通知  ← 做什么
  criteria      判据清单（声明式，随宏版本快照）    ← 怎么算数
  budget        每锚每日 N 次 + 免打扰时段 + 单 run maxRounds  ← 花多少钱
```

**没有第六格。没有表达式、没有条件分支、没有子宏调用、没有编排。**

### 3.1 与 n8n template 的根本区别

| | n8n template | 本平台的宏 |
|---|---|---|
| 复用什么 | **流程**（节点连线） | **判据**（什么算干完了） |
| 用了之后 | 流程跑完了 | 你接受了一套验收标准 |
| 失败了谁告诉你 | 节点报错 | 判决是 `red` / `no-op-claim` |
| 有没有「看起来成功」 | 有（返回 200 就算成功） | **没有**（`no-op-claim` 单独一档） |

> **n8n 有几千个模板，全是流程。流程模板不告诉你它到底有没有用。
> 我们的宏把判据一起打包 —— 所以「用这个宏」= 「接受这套验收标准」。**

这是唯一一处我们比 n8n 强、而且它结构上学不来的地方（它没有可执行判据的土壤）。

## 4. 三个必须接受的代价

### 4.1 分支判断必须前移到源的 `state` 枚举

宏内部零分支，所以「如果 A 就 X，否则 Y」必须变成 **两个宏 + 一个更细的 `state` 枚举**：

```
源产出 state: trivial | breaking | blocked-by-upstream
宏① on_state=trivial   → 起一个升 pin 的 run
宏② on_state=breaking  → 通知人并附证据
宏③ on_state=blocked   → 静默退避（不通知）
```

**这不是妥协，这是收益**：它强迫「这个判断到底是什么」变成**有名字、可测试、可计数**的东西。
反例就是站内 §8.87 那次事故——「TTL 层有没有工作」这个判断没有枚举，我就读错了观测面。

⚠ **对源的硬要求**：源的 `state` 必须足够细，细到「一个 state 对应一个动作」。
如果做不到，说明**这个判断还没想清楚**，不是「宏不够灵活」。

### 4.2 锚 ≠ 投递目标（这条解决了「事件和 session 相关」的直觉）

用户的直觉对一半：**证据、通知、用户看的地方都在会话里**——这是对的。
但**订阅不能绑会话**，三条理由：

1. **会话有生命周期**。用户今天开新会话，昨天订阅的宏就失效了。
2. **同一目录会有 N 个会话**。绑会话就要重复订阅 N 次。
3. **事件是目录/仓库的属性**（git 灯、端口、证书），不是会话的属性。

⇒ **订阅锚 = 作用域；事实对象 = 那个具体的东西；投递目标 = 某个会话。三层分开。**

| 层 | 是什么 | 例 |
|---|---|---|
| **订阅作用域** | 我允许这个宏盯我哪些东西 | 我的所有目录 / 某个目录 / 我的所有会话 / 我的账号 |
| **事实对象** | 具体那个东西 | `dir:~/projects/x` / `run:<uuid>` / `port:22000` / `service:tls` |
| **投递目标** | 通知落在哪个会话 | 该作用域下最近活跃的会话 / 新建 |

⚠ **「会话」不是事实对象，但它是合法的作用域**（这两句不能混）：

- **作用域**可以是会话：「这个会话的 run 结束时通知我」——筛的是 run，会话只是筛选边界
- **事实对象**永远不是会话：没有任何事件的 `object_key` 是 `session:<uuid>`
  （砖化是平台缺陷，不是事件，见 [09](03-macro-model-and-catalog.md) §14.1）
- **投递目标**常常是会话：「通知落在哪」

⚠ **「订阅绑目录/仓库」也不成立**（会话有生命周期、同目录多会话），所以第一版虽然从会话下拉订阅，
但**订阅存的是 `(用户, 会话, 宏)`，不是把宏写进会话的配置里**——会话没了，订阅跟着失效，这是有意的。

### 4.3 宏不组合

一旦允许「A 完再 B」，就回到 DAG，然后回到可视化编排器（[01](01-decision-and-feasibility.md) §5）。

**替代品是黑板**：宏之间不互相调用，只通过**锚的状态**互相看见。
`A 干完 → 锚的 state 变了 → B 的 on_state 命中`。这不需要任何组合语法。

## 5. 关键一刀：宏的「是什么」在代码里，「开不开 / 参数多少」在 DB

这是让整个模型落地的最小形状：

| | 存哪 | 谁能改 | 为什么 |
|---|---|---|---|
| **宏的内容**（锚类型 / on_state / action / criteria / 默认预算） | **代码**（一份常量表） | 只有发版 | 判据要能被**变异测试**、被审查、被 diff。放进 DB 编辑就等于把判据变成数据，而数据不能被测试 |
| **启用状态 / 参数 / 预算覆盖** | **DB** | 管理员（管理台） | 调参不该发版 |

⇒ 管理台 UI 因此极小：**一个列表 + 每行几个参数框 + 一个开关**。**没有编辑器。**

### 5.1 ⚠ 「参数」分两类，不能混（否则 state 会退化成用户输入）

| 类 | 例子 | 谁定 | 为什么 |
|---|---|---|---|
| **源的 `state` 枚举** | `silent` / `completed` / `expiring_7d` | **平台**（封闭） | 它回答「世界处于什么状态」，且是幂等键的一部分 |
| **宏参数**（不是 state） | `threshold` / `phases` / `quiet_hours` / `max_per_day` | **宏模板**（第一版用户不可改） | 它只回答「什么时候值得叫我」 |
| **订阅** | 开 / 关 + 作用域 | 用户 | 不给参数，否则运维无法审计「这个宏到底在干什么」 |

**判据：改它会改变「世界是什么状态」⇒ 平台定；只改变「什么时候叫我」⇒ 宏参数。**

⚠ **反例**：把阈值写进 state（`silent_10m` / `silent_30m`）——
每填一个新值就造出一个**没人评审过**的新 state，幂等键不可枚举、测试无法穷举。
⇒ 正确形态：`state = silent`（一个值）+ `threshold`（参数）。详见 [09](03-macro-model-and-catalog.md) §14.8。

⚠ **参数化阈值的宏，幂等粒度是订阅不是宏**：键 = `(订阅, anchor, state)`。
若只写 `(macro, anchor, state)`，同一对象上两个不同阈值的订阅会互相吞（先到的占住键，后到的永不发）。

⚠ 这条同时解决了「宏会腐烂」的一半：宏改版 = 发版，所以它跟着代码一起过 CI、过变异测试、过 review。
DB 里的宏定义会静默腐烂（站内 #331「配了没人读」正是这一族）。

## 6. 三方分离：定义权 / 订阅权 / 预算权

| 权力 | 谁 | 后果 |
|---|---|---|
| **定义** | 管理员（改代码 + 发版） | 用户不能写规则 ⇒ 没有规则语言 ⇒ 没有权限模型 |
| **订阅** | 用户（在自己的目录上开/关） | 用户自己决定「这个目录要不要被盯着」 |
| **预算** | 管理员（宏自带日限额，可覆盖） | **全公司开满的最坏成本可算** |

**超额行为必须是确定的**：超过日限额 ⇒ **静默退避 + 记一笔「因预算跳过」**，不排队、不补发。
理由：补发会让成本在第二天翻倍，而「因为没钱所以没提醒你」这件事**必须可见**（否则就是 [02](02-event-model-and-verdict.md) §8 的静默死法）。

⚠ **`budget` 不只管次数，还管时段**：通知型宏必须有 `quiet_hours`（默认 22:00–08:00，UTC+8），
否则凌晨三点一封「session 完成」的邮件会让人关掉整个功能。窗口内**积压到窗口外合并发一封**
（不是丢弃，也不是逐条补发）——「因为你睡觉所以没告诉你」同样必须可见。

⚠ **一个真实的错配**：用户开满 10 个宏，管理员预算只够 2 个。⇒ 宏列表上必须**同时显示**「这个宏一天最多花多少」
和「你已经开了几个」，否则用户以为自己在用，实际全被预算挡掉。

## 7. 投递目标：通知型 vs 任务型

宏声明自己是哪一种，决定通知落在哪：

| 类型 | 动作 | 投递目标 | 成本 |
|---|---|---|---|
| **通知型** | 往会话投一句话（不起 run） | **该锚下最近活跃的会话** | 0 |
| **任务型** | 起一个 run | **新建会话**（除非宏显式指定） | 一个 run |

**为什么任务型默认新建会话**：长会话反复被机器人插话会让账本形状变复杂（站内为账本形状修过六轮），
而且「这是宏起的活」和「这是我刚才在聊的活」混在一个会话里，用户分不清。

**为什么通知型投最近活跃会话**：用户正在那儿工作，弹在眼前才有用。新建会话会让「提醒」变成「又开一个窗口」。

## 8. 宏的版本与判据快照

宏的身份是 `macro:<name>@<version>`。改判据 = 升版本，不原地改。

理由（[03](02-event-model-and-verdict.md) §17）：**判据必须随 run 存快照**，否则改完判据之后，历史 run 会变成
「按今天的标准看它失败了」——你在**重写历史**。

⇒ 订阅存的是 `macro:<name>`（跟随最新版），但**已跑的 run 记的是当时那个 `@<version>` 的判据全文**。

## 9. 简化版因此缩到多小

对照 [04](01-decision-and-feasibility.md) §12 那四小格：

| 原四小格 | 宏模型之后 |
|---|---|
| ① 规则表（四格 + 作用域 + 预算） | **拆成两件更小的**：宏目录（代码常量）+ 订阅表（`(user, anchor, macro, params, enabled)`） |
| ② 谓词求值 + 边沿/状态区分 | **只剩**「`state` 枚举比对 + 边沿/状态区分」，**没有表达式求值** |
| ③ 血统 | **不变**（`trigger_kind` 进谓词 + 深度上限） |
| ④ 可见性面 | **不变**（且多一格：`因预算跳过`） |

⚠ **诚实的一句**：宏砍掉的是「**用户可写的规则语言**」和「**权限模型**」，**不是执行机制**。
求值、边沿、血统、可见性一样都不能少（[04](01-decision-and-feasibility.md) §14 同一条纪律）。
把「宏」理解成「所以实现变简单了」是错的；它变简单的是**要设计的东西**，不是**要跑的东西**。

## 10. 宏目录的初稿已经写好了

**`AGENTS.md` 的每一节都是一条宏的草稿。** 那不是文档，那是需求。

而且它自动分两类，锚不同：

| 类 | 例 | 锚 | 执行者 |
|---|---|---|---|
| **用户宏** | 收工检查（git 灯红/黄）、依赖更新、日报 | 目录 / 用户 | 该 FDE 自己的容器 |
| **运维宏** | 部署后 digest 核对、证书到期、号池占用、版本漂移 | 仓库 / 服务 / 端口 | 一个指定的 FDE（或运维自己的） |

⚠ **没有「无锚宏」**。运维宏看起来最像「平台自己干的事」，但它仍然锚在某个具体对象上，
执行仍然落在某个具体 FDE 里 —— 否则没人跑它、没人付 token（[02](02-event-model-and-verdict.md) §6.2 的同一条）。

## 11. 三条风险（宏模型特有的）

| 风险 | 形态 | 防线 |
|---|---|---|
| **宏会腐烂** | 写了一次、判据过时、没人再验 | 宏在代码里 ⇒ 跟着 CI 跑；判据必须钉在具名用例上（[03](02-event-model-and-verdict.md) §16）；宏的命中率上可见性面 |
| **宏目录会变成「功能列表」** | 20 个宏之后要求组合、要求条件、要求编辑器 | §4.3 不组合 + §4.1 分支前移到枚举。**这两条一破就回到 n8n** |
| **用户开满但预算不够** | 界面显示「已启用」而实际全被挡 | §6 的错配提醒 + `因预算跳过` 必须可见 |

## 12. 第一个该设计的宏：收工提醒（git 灯）

> ⚠ **本节是被取代的旧提案，保留作决策过程记录。**
> 决策者 2026-11-08 定了**第一版只做 E1 + E5**（见 [05](05-first-macros.md) §2），
> 收工提醒（E2）**挂账**。不要按本节去做首步。

选它而不是「上游发版」，因为它验的是**链路**而不是**钱**：

| 格 | 值 |
|---|---|
| `anchor_type` | 目录 |
| `on_state` | `gitlight: uncommitted`（🔴）或 `unpushed`（🟡） |
| `action` | 通知型：往该目录最近活跃会话投一句话（附仓库名 + 灯色 + 「让 AI 收尾」的提示） |
| `criteria` | `git status --porcelain -uall` 为空 ∧ 有远端时 `HEAD == refs/remotes/<r>/<br>`（**就是 `gitlight.js` 现有判据，零新增**） |
| `budget` | 每目录每日 1 次 |

四条理由：

1. **判据现成**（`gitlight.js` 已实现红/黄/绿/⚪ 三态判定与全部坑：`-uall` 不能退化成 `-uno`、`--no-optional-locks` 必须在子命令之前、worktree 的 refs 在 `commondir`）。
2. **成本几乎零**：通知型，不起 run；大部分时候不触发。
3. **它补的是一个已经被决策者认下的洞**：D9 明确写了「告知面先行，灯后上」，灯已经上了（#359 P0a/P0b），
   而**「收工即提交」至今只有告知面，没有任何执行者**。
4. **它验全链**：源（gitlight）→ 影子表（目录状态）→ 谓词（红/黄）→ 边沿/状态 → 动作（投递）→ 血统（`trigger_kind`）→ 可见性（命中了几次、为什么没触发）。

第二个再上「上游发版」（任务型 + 语义源 + 真花钱），验的是 run 侧与预算侧。

**第 2 部分 · 能力清单：我们能提供哪些事件、哪些动作、参数怎么设**

## 14. 事件表（**五个**）

### 14.1 判据：有没有一个人，在不知道这件事的情况下会**做错决定**

比「有没有状态」和「平台能不能自己修」都更准。拿它过一遍：

| # | 事件 | 事实对象 | `state` 枚举（封闭） | 幂等键 | 现在有吗 | 不知道会做错什么 |
|---|---|---|---|---|---|---|
| E1 | **run 终态 + 静默** | `run:<id>` | 边沿：`completed` / `failed` / `capped` / `aborted` / `persistence_failed` / `guard_unverified`；状态：`silent`（阈值是宏模板参数，不是 state，§14.8） | `run:<id>`+state | **已有** | 以为还在跑、或以为成了、或以为它还活着 |
| E2 | **收工灯** | `dir:<path>` | `uncommitted` / `unpushed` / `never_fetched` / `no_remote` / `no_commits` / `synced` / `grey` | `dir:<path>`+state | **已有** | 以为收工了，其实没提交/没推 |
| E3 | **端口对账** | `port:<n>` | `assigned_not_listening` / `listening_not_assigned` / `duplicate_in_dir` / `stale` | `port:<n>@<pid>` | **已有**（两张表合成，§14.3） | 以为预览能用，实际打不开 |
| E4 | **服务证书** | `service:tls` | `expiring_30d` / `expiring_7d` / `expiring_1d` / `not_yet_valid` / `host_not_covered` / `chain_incomplete`（+ `expired` 仅作客观表示，见 §14.4） | `service:tls`+state | **已有**（§14.4） | 见 §14.4 的静默度表 |
| E5 | **时钟** | `clock:<date>` | `tick`（状态型：今天还没 tick 且已过点） | `clock:<date>` | **需新建**（很小） | 以为检查过了 |

**五个事件，四个已有。**

⚠ **「事件清单」≠「第一版宏目录」**：前者是「平台能观测什么」（5 个），后者是「第一版配哪些宏」。
**E4 在清单上，但第一版不配宏**（理由见 §14.4 末）。别把「留在清单上」读成「要做」。

### 14.2 E1 与 E2 的区别（最容易混的一对）

一句话：**E1 管「对不对」，E2 管「丢没丢」。** 两者正交。

| | **E1 run 终态** | **E2 收工灯** |
|---|---|---|
| 事实对象 | `run:<id>`（一次执行） | `dir:<path>`（一个目录） |
| 数据源 | `runs.status` + `termination.reason` | `git status --porcelain -uall` + 读 ref 比 sha |
| 时间性质 | **边沿**：那一刻发生一次，此后不再变 | **状态**：随时在变（改一个文件就红） |
| 回答什么 | 这次活**干成了吗**（judge 判过？被停？超轮？） | 这个目录的活**被 git 兜住了吗** |
| 覆盖谁干的活 | 只覆盖 **agent** 的改动 | 覆盖 **所有人**的改动（含你自己手改的） |
| 自带时机吗 | ✅ 自己告诉你「结束了」 | ❌ **需要采样时机**（见下） |

**关键：`run` 结束 ≠ 灯变红。** 三种情况都不红：agent 只读没改、agent 改了自己 commit 了、agent 改了你已经推了。
反过来，**灯红也不说明刚跑过 run**——可能是你昨天手改的文件。

#### 为什么两个都不能砍

| 只留 E1 | 只留 E2 |
|---|---|
| 永远不知道「活有没有被兜住」。**这正是 #359 D9 立项的理由**：真机实测 agent 说「完成了」而文件没提交 | 不知道「这次活干对了没有」。灯绿只说明「没有未提交的改动」——**一个空 commit 也能让灯绿** |

#### 最有价值的是**联合**，不是任一个

```
E1 命中 judge_done（看起来成功） + E2 命中 uncommitted（灯红）
  ⇒ 「agent 说成了，但活没兜住」
```

这是站内真实发生过的失败形状，也是单看任一事件都看不出来的。

#### 时机问题（这条决定 E2 怎么用）

E1 **自带时机**（run 结束那一刻）。E2 **不自带**——「灯红」在 run 结束后一小时、一天后依然成立，
它不是「刚才发生了什么」，是「现在是什么状态」。所以 E2 有两种用法：

| 用法 | 时机从哪来 | 适合 |
|---|---|---|
| **A. 挂在 run 终态之后** | 复用 E1 的时机（run 结束顺手看一眼灯） | 「agent 说完成 → 我核一下有没有真提交」 |
| **B. 定时检查** | 需要 E5（时钟） | 「每天 18:00 看所有目录」= 真正的**收工提醒** |

⚠ 用法 B 意味着 **E2 单独不能成宏**，它得配 E5。这也是为什么 E5（时钟）不是可有可无的第五个——
**它是所有「状态型事件」的时机来源**。

### 14.3 E3 端口对账 = 两张表合成的一条事件（不是两个）

| 输入 | 回答什么 | 出处 |
|---|---|---|
| `port_allocations`（号池） | 平台**分配**了哪一段 | `previewpool.js` / #256 端点 |
| `port_observations`（观测） | 容器里**实际**在听什么 | `port_observations`（#352，45s 新鲜度窗） |

**有价值的是两者的差**，不是任何一张表。`assigned_not_listening` 就是「分给你 22000，你听 3000」
——这正是 #352 已经算出来的「同一目录同时开在两个端口，多半是两个版本并存」。

⇒ 同一条事件的两个输入，分开列会让人以为要做两个功能。

### 14.4 E4 服务证书：一个对象，**七个 state**，其中四个是静默的

我一度把证书降级成「一条 cron 就够」，理由是「只有一张、运维自己盯」。
**那个理由建立在「证书失效是可见的」这个错误前提上。**

真实状态面（`tls-cert.js` 的服务端机器码 + `verifyLiveCertificate` 的握手结论 + 前端算的到期分档）：

| state | 判据 | **静默度** | 谁被叫醒 | 能不能做成宏 |
|---|---|---|---|---|
| `expired` | `notAfter <= now` | **低**（浏览器硬告警，所有人立刻发现） | 管理员 | ✅ 但价值最低 |
| `expiring_1d/7d/30d` | 剩 1–29 天，**分三档** | **高**（还有 29 天，没人看） | 管理员 | ✅ **提前量才有意义**——过期后补签发要等时间 |
| `not_yet_valid` | `notBefore > now` | 高 | 管理员 | ✅ |
| `host_not_covered` | `coverage.covered=false` | **极高**（装了但不管用） | 管理员 | ✅ |
| `chain_incomplete` | verify `mismatch` + `reason:'chain_incomplete'` | **极高**（#462 活标本：页面报 live ✓，客户端严格校验 **error 21**） | 管理员 | ✅ |
| `not_reloaded` | verify `mismatch` + `reason:'fingerprint_mismatch'` | **极高**（换了文件但 Traefik 没 reload，§8.94 踩过） | **平台** | ❌ 平台能自己修（重写 `tls.yml`）⇒ 内置告警 |
| `unverifiable` | verify `unreachable` | — | 没人 | ❌ 不知道 ≠ 坏 |

**所以「证书过期」是事件，但它是这七个里最不静默的那个。** 真正需要框架的是
`chain_incomplete` / `host_not_covered` / `not_yet_valid` —— **所有信号都说好，只有严格校验说不好**。

**动作只能是「通知」，不能是「换证」**：换证需要人给新证书（A10 的 `certPem`/`keyPem` 从哪来？）。
⇒ 证书宏只能是**纯通知型**：零 run、零成本、零破坏性。

**处置（决策 2026-11-07）：留在事件清单，第一版不配宏。** 四条理由：

1. **真过期就没意义了** —— `expired` 只是「已经坏了」的客观表示，**它不该是任何宏的 `on_state`**。
   有用的只有提前量（`expiring_30d/7d/1d`），而提前量就是个定时提醒。
2. **动作只有通知，没有判断** ⇒ 一条 cron + 一封邮件就能做完，**不需要宏框架**。
3. **触发一个 agent 来处理没必要**：agent 换不了证（拿不到新私钥），它能做的只是「再检查一遍」，
   而检查这件事本身已经是 `verifyLiveCertificate` 的职责。
4. 它与第一版的具体场景（收工 / 完成 / 端口 / 日报）**没有关联**。

⚠ 但记一条备用价值：**它是五个源里唯一「判据全在、零新建代码、连静默度都算好」的**。
将来要验「宏引擎管道通不通」（事件→判据→动作→可见），拿它当靶子最便宜——
不需要造数据、不需要等 run、不会误伤任何人的项目。**别把这条当排期，当工具箱。**

### 14.5 ⚠ 状态型事件必须**分档**，档位就是幂等键的一部分

`expiring` 是**状态**不是边沿：剩 29 天、28 天、27 天都是「快过期」。
如果幂等键只有 `service:tls@expiring`，后果是二选一：

- 一天发一次（把 `(source, object_key, state)` 当边沿用，实际是状态）→ 用户三天后关掉整个功能
- 只发一次（幂等键生效）→ 之后再也不提醒，直到过期

⇒ **状态型事件必须切档**（`expiring_30d` / `expiring_7d` / `expiring_1d`），每档各发一次。
同一条规则适用于所有状态型源：收工灯（本来就是离散态）、端口对账（离散态）、时钟（按日期分桶）。

### 14.6 不进事件表的两类

**① 平台自己的故障 —— 内置告警，不可配置、不可关闭**

| 事项 | 该由谁处理 |
|---|---|
| 会话砖化（`invalid_messages`） | **平台**：读侧折叠已修（#351/#352）；存量按巡检手册修数据（要备份 + 人批） |
| 排队输入卡 `delivering` | **平台**：`CLAIM_STALE_MS` 重新认领语义已存在（#370） |
| 租约过期 / 重排耗尽 | **平台**：reaper 已在做，`attempt_killed` 已可见（#288/#292） |
| 容器镜像漂移 | **平台**：`reconcile` 的职责 |
| 证书 `not_reloaded`（盘上对、线上旧） | **平台**：重写 `tls.yml` 即修（§14.4） |

**把平台该自己修的事做成事件，就是把平台的责任转嫁给用户。** 而且事件表会变成 bug 列表（无限长）。

**② 现在不做**

| 事项 | 为什么 |
|---|---|
| **预览缺件**（`preview_miss_stats`：哪些扩展名撞 415/413） | 它是**统计**不是状态，回答「产品该支持什么格式」，**没有人会因为不知道它而做错决定**（点不开用户自己会看见）。管理台已有一页 |
| **上游发版** | 一次性仪式、不重复；且需要语义源（简化版明确不做） |
| **应用不健康**（listening 但回 5xx） | 当前项目里的应用**全是开发环境**；dev server 每次保存都重启 ⇒ 会变成误报机 |

⚠ **教训（值得单独记）**：我第一版列了 12 个事件，其中**九个是从代码里搜出来的**
（`gitlight.js` / `tls-cert.js` / `port_observations` / `preview_miss_stats` / `previewpool.js` …）。
**从「系统里有什么」出发列表，一定会混进平台故障和统计数字。** 正确顺序是反过来：
先问「谁需要被叫醒」，再去代码里找能不能算出来。

### 14.7 同一个源可以同时有「边沿 state」和「状态 state」

E1 上面只列了终态（边沿）。但「run 卡住不说话」也是 `run:<id>` 的一个 state，它不是终态：

| state | 类型 | 判据 | 谁在等 |
|---|---|---|---|
| `completed` / `failed` / `capped` / `aborted` … | **边沿** | `runs.status` 写入那一刻 | 想知道「结束了吗」 |
| `silent` | **状态** | `now - max(run_events.ts) > 阈值` | 想知道「还活着吗」 |

区别**不在源，在求值方式**：

- **边沿**：源写入时触发一次，此后幂等键不再命中
- **状态**：由评估循环定期求值，进状态 / 出状态各算一次

⚠ **混在一起的唯一代价**：宏的 `on_state` 必须知道自己在等哪一类。
⇒ 宏定义里 `on_state` 旁边要标 `edge` / `level`（见 [10](05-first-macros.md) §3）。

⚠ **通用规律：状态型宏的阈值必须小于「会改变该状态的上游机制」的阈值。**
否则上游抢先处理 → 状态复位 → 宏永不触发。实例：静默告警必须 < `ERIX_AGENTD_WATCHDOG_MS`（300s），
否则 worker 真死那一类全被 watchdog 吃掉（[10](05-first-macros.md) §4.3）。

⚠ **“静默”用哪个时钟量很重要**：IPC 与 `run_events` 是两个不同的量。
`shell` 工具执行期每 30s 发 `shell_liveness` 心跳（`worker.js:593-603` 明写「绝不得走 emitEvent」）
⇒ 长命令期间 **IPC 一直有、`run_events` 一条没有**。用户感知的「没反馈」是后者。

### 14.8 源的**档位**与订阅的**阈值**是两件事（别混）

两者都是「分档」，但一个属于源、一个属于订阅：

| | 源的**档位** | 规则的**阈值** |
|---|---|---|
| 例子 | 证书 `expiring_30d` / `7d` / `1d` | 静默告警的 `threshold: 15m` |
| 谁定 | **平台**（写进 state 枚举） | **宏模板**（管理员定，第一版用户不可改） |
| 为什么 | 它是**世界事实的分界**（30 天到期是客观的） | 它是**规则参数**（多久算卡住因场景而异） |
| 幂等粒度 | `(anchor, state)` | `(订阅, anchor, state)` |
| 后果 | 三档 ⇒ 三次提醒 | 一个订阅 ⇒ 一次提醒 |

**判据：改它会改变「世界是什么状态」⇒ 平台定；只改变「什么时候叫我」⇒ 宏参数。**

⚠ **反例（必须避免）**：把阈值写进 state（`silent_10m` / `silent_30m`）——
每填一个新 N 就造出一个没人评审过的新 state，幂等键不可枚举、测试无法穷举。
⇒ 正确形态是 `state = silent`（一个值）+ `threshold`（参数）。

## 15. 动作表（平台能做什么）

> ⚠ 本节 12 个动作**都是「做事」**，不是「修自己」。修自己的动作（重建容器 / 改证书 / 改 LLM 绑定）
> 之所以在表里，是因为它们对**运维宏**合法（E3 证书到期 → A10 换证），不是因为它们是平台自愈手段。

| # | 动作 | 类型 | 参数 | 现在有吗 |
|---|---|---|---|---|
| A1 | **投一句话到会话** | 通知 | `session`（锚解析）/ `text`（模板）/ `role`（默认 `user`） | **已有**（`postMessage`） |
| A2 | **新建会话** | 通知 | `cwd` / `title`(≤200) / `model`(≤100) / `origin` | **半有**（`createSession` 有前三个，**无 `origin`**） |
| A3 | **起一个 run** | 任务 | `cwd` / `task`（模板）/ `maxRounds` / `session`（新建或复用） | **已有**（= A2 + A1 + 队列） |
| A4 | **发邮件** | 通知 | `to`（**枚举**，见 §15.2）/ `subject` / `text`（纯文本） | **半有**（`mailer.send({to,subject,text})` 有，只用于验证码，缺「通知用」路径与模板） |
| A5 | **站内通知** | 通知 | `user` / `title` / `body` / `link` | **需新建**（小，但需要一个 UI 落点） |
| A6 | **平台落盘** | 通知 | `path`（模板，限 `~/reports/…`）/ `content`（= run 的 `final_text`） | **需新建**（小；平台不受 jail 限制，见 [08](06-execution-and-recovery.md) §1） |
| A7 | **停 run** | 控制 | `run` / `reason` | **已有** |
| A8 | **重建容器** | 运维 | `fde` / `image`(digest) | **已有**（`provisioner`） |
| A9 | **签预览票** | 运维 | `allocation` / `ttl` | **已有**（`/api/me/ports/batch-tickets`） |
| A10 | **改证书** | 运维 | `certPem` / `keyPem` / `confirmDomains` | **已有**（`PUT /api/admin/tls`） |
| A11 | **改 LLM 绑定/白名单** | 运维 | `fde` / `models[]` / `budget` | **已有**（`/key/update`） |
| A12 | **写档案（note）** | 通知 | `scope`（**今天只有 `sessionId`**）/ `key` / `text` | **半有**（缺 `user` / `dir` scope） |

### 15.1 三个「类型」的含义

| 类型 | 起 run 吗 | 成本 | 失败要不要通知 |
|---|---|---|---|
| **通知** | ❌ | ≈0 | 失败静默可接受（它本身不产生价值，只是搬运） |
| **任务** | ✅ | 一个 run | **必须通知**（[08](06-execution-and-recovery.md) §6） |
| **控制/运维** | ❌ | ≈0 | **必须通知**（它改的是系统状态） |

⚠ 这不是分类癖：**「任务型失败必须自己会说话」是 [08](06-execution-and-recovery.md) §6 那第四种静默死法的唯一防线**。

### 15.2 参数只许六种类型（这是「不需要规则语言」的代价）

| 类型 | 约束 | 例 |
|---|---|---|
| `enum` | 封闭取值 | `to` / `model` / `role` |
| `path` | 必须落在 jail 或 userspace 白名单内，且**不允许 `..`** | `cwd` / `path` |
| `int` | 带上下界 | `maxRounds`(1–100) / `ttl`(≤600) |
| `duration` | `Ns`/`Nm`/`Nh`，有上限 | `quiet_hours` / `jitter` |
| `text` | 长度上限 + **只能引用白名单变量**（§15.3） | `text` / `subject` / `title` |
| `email` | **只能从枚举里选**，不接受自由填写 | `to` |

### 15.3 模板变量白名单（**这是唯一的小语言，必须极小**）

```
{{anchor}}     锚的可读名（目录名 / 仓库名 / 端口号 / 会话标题）
{{state}}      本次命中的 state 字面值
{{evidence}}   证据摘要（源给的，纯文本，≤500 字）
{{date}}       本地日期（UTC+8，YYYY-MM-DD）
{{run_id}}     触发本次动作的 run（任务型才有）
{{url}}        可点的落点（预览地址 / 管理台链接）
```

**没有条件、没有循环、没有函数、没有算术。** 认不出的变量 ⇒ **渲染失败 + 记一笔**，
不许原样输出 `{{xxx}}`（那会把内部变量名漏给用户）。

⚠ **收件人必须是枚举**（`当前用户` / `管理员` / `自定义白名单`），**不许自由填邮箱**。
否则「一个宏」= 「一台发信机」，而这个系统里任何能写规则的人都能用。

## 16. 三个必须一起定的边界

| # | 边界 | 为什么 |
|---|---|---|
| 1 | **动作必须可逆或可解释** | `A8` 重建容器会**打断正在跑的 run**；`A10` 改证书能把自己锁在门外（[#462](04-scenarios.md)）。⇒ 这类动作要 `destructive: true` + 默认不启用 |
| 2 | **动作不许写外部系统**（[05](01-decision-and-feasibility.md) §18.1） | 边界是「谁的渠道」：`A4`/`A5`/`A6` 走平台自己的渠道 ⇒ 可以；在 GitHub 评论 ⇒ 不行 |
| 3 | **`criteria` 不能为空就宣布成功** | 通知型动作（A1/A4/A5/A6）**本来就没有判据**，那是正常的；但**任务型（A3）必须有判据**，否则「跑完了」= 「成了」，那就是 `no-op-claim` |

## 17. 覆盖度自查：5 个事件 × 12 个动作

| 事实对象 | 能用的事件 | 能用的动作 |
|---|---|---|
| `run` | E1 | A1 A4 A5 A6 A7 |
| `dir` | E2 E3 | A1 A3 A4 A5 A6 A12 |
| `port` | E3 | A1 A3 A4 A5 A9 |
| `service:tls` | E4 | A4 A5 |
| `clock` | E5 | A3 A4 A5 A6 |

**≈20 个合法组合**（其中 E4 那一行是**清单上合法、第一版不配**，见 §14.4 末）。 这是「不需要规则语言」最硬的证据——20 个组合，
每一个都能写成一条具名宏、被单独测试、被变异验证。一门表达式语言在这种规模上只会增加不透明度。

⚠ **注意「会话」不在这一列**：它**不是事实对象**，是**作用域**（我允许这个宏盯我哪些东西）
与**投递目标**（通知落在哪）。事实是 `run` / `dir` / `port` / `service:tls` / `clock`。

## 18. 所以「参数怎么设」的完整答案

以用户举的两个例子收尾：

```
宏：任务完成 → 发邮件
  anchor_type   用户（作用域 = 我的所有会话）
  on_state      E1: run.completed
  action        A4 发邮件
    to          enum: 当前用户           ← 不是自由邮箱
    subject     text: "[{{anchor}}] 任务完成 · {{date}}"
    text        text: "{{evidence}}\n\n查看：{{url}}"
  criteria      （空 —— 通知型不需要）
  budget        max_per_day 20 / quiet_hours 22:00-08:00
  notify_on_failure  true

宏：每天打卡 → 开新会话跑活
  anchor_type   用户
  on_state      E5: clock.tick
  action        A3 起一个 run
    session     新建（title = "{{date}} 每日检查"，origin = macro:daily-check）
    cwd         path: ~/projects/<项目>   ← 由订阅时选，不是模板变量
    task        text: 固定任务描述（模板）
    maxRounds   int: 16
  criteria      见 [07](04-scenarios.md) §6 判据②③
  budget        max_per_day 1 / jitter ±10m
  notify_on_failure  true
```
