# 01 · 定位与可研：它是什么、做多少、怎么证明

> 状态：可研（2026-11-07）。**【实测】** / **【推断】** 逐条标注。

---

## 1. 单位决定产品

| 平台 | 价值单位 | 交付的东西 |
|---|---|---|
| n8n | **一次触发** | 一条流程 |
| Dify | **一个应用 / 一次对话** | 一个给别人用的能力 |
| Airflow / Temporal | **一次编排** | 一条可重跑的作业图 |
| **本平台** | **一条被带证据关闭的工作项** | **一个结果** |

这个区别不是修辞，它决定产品形状：**n8n/Dify 的用户是「给别人造东西的人」，我们的用户是「给自己找人干活的人」。**

## 2. 护城河不在「能编排」，在「能执行判据」

n8n 的一个节点是**一次 API 调用**。本平台的一个动作是：

- **跑一遍测试，只认退出码 + 点名到用例名的 `not ok N`**
- **逐字读 `git diff` 的 `+` 行，不许读 commit message**
- **改一行它声称承重的代码，测试必须红**（变异探针）
- **声明的字面值必须在本次工具返回里逐字找得到**

**这四件事在 n8n / Dify 里表达不出来——不是难，是缺主语。** 它们需要一个有 shell、有 repo、
有测试框架、有历史的**真机器**。而那正好是 station 已有的三件套合成品：
**牢笼（L0）+ 账本（L1）+ 判决（本平台）**。

由此得到三条它们结构上做不到的事：

| | n8n | Dify | 本平台 |
|---|---|---|---|
| 活在哪跑 | 共享进程 | 共享进程 | **租户自己的容器 + jail + 独立 `/29`** |
| 有无真文件系统 | ✗ | ✗ | ✓（真目录、真 git、真测试框架） |
| 过程记录 | 执行日志 | 消息历史 | **transcript 账本**（折叠/压缩/终止语义，站内磨了六轮） |
| 钱 | 按执行/席位 | 按 token/席位 | **per-租户虚拟 key 在边缘注入 + 按工作项归账** |
| 正确性判据 | 「节点没报错」 | 「模型返回了」 | **「活落地了吗」** |

## 3. 它们比我们强的地方（诚实版）

| | 它们赢 | 我们输 |
|---|---|---|
| 集成广度 | n8n 几百个 connector | 只有 Gitea / git / npm / LLM 网关 |
| 上手时间 | Dify 20 分钟出一个能用的 bot | 要容器 + FDE + digest pin |
| 确定性 | n8n 确定、可复现、便宜 | 随机、贵（一个 run 的钱） |
| 非技术用户 | 都能用 | 只有工程师能用 |

⇒ **该用 n8n 的场景就别用本平台**：连一堆 SaaS、定时拉数据写表、发通知、审批流——这些已有便宜且确定的解。
本平台只该出现在**「需要一个真机器 + 一个有历史的目录 + 一条能跑测试的判据」**的地方。

## 4. 真正危险的邻居

不是 n8n/Dify，是这两类：

1. **自主编码 agent + issue 队列**（Devin 类）。我们的差异：自托管（代码不出内网）、多租户牢笼、
   账本与判决纪律、自己的 LLM 网关（成本可归因）。
2. **平台团队用 Temporal + k8s job 自建「AI 运维」**。我们的差异：**他们得先花半年造牢笼和账本，我们已经造完了。**

⇒ 对外定位应是「**自托管、多租户、可判据的 AI 员工运行时**」——前一句是功能，后一句是唯一能赢的位置。

## 5. 两条会让我们「变成它们」的路

| 诱惑 | 会变成 | 防线 |
|---|---|---|
| **可视化编排器**（拖节点、连线、条件分支） | n8n | 规则只有四格：**状态迁移 → 动作 → 锚 → 预算**，无表达式、无编辑器。一旦有编辑器，就要跟 n8n 比 connector 数量——那一局必输 |
| **Prompt 管理 / 模型目录 / RAG 产品化** | Dify | LLM 管理只为「**给员工发预算并归账**」服务。判据：*这个功能是让用户造东西给别人用，还是让用户给自己找人干活？* |

⚠ 第二条要盯住：station 现有的 LLM tab 已经是 Dify 的种子。

## 6. 与 erix-station 的关系

### 6.1 结论

> **station 是执行平面（让它能安全地跑起来），本平台是决策平面（让它值得跑、跑完算不算数）。**
> 不是父子，不是 v1/v2，而是**同一栈的上下两层，各自独立发布，接缝由测试钉住**。

### 6.2 代码称重（为什么说它「已经是下半身」）**【实测】**

`portal/src` 共 25048 行，按职能：

| 职能 | 行数 | 是 FDE 专属吗 |
|---|---|---|
| 执行底座（provisioner / ipam / routes / tls / materializer / portalloc / preview / onboarding / offboarding） | 6120 | **不是**，任何 agent 平台都要 |
| 传输层（http / internal） | 6550 | 不是 |
| 身份与钱（auth / llm / llm-gateway / llm-chat） | 2519 | 不是 |
| 工作追踪（sessions / session-view / gitlight / queued-inputs / dirs） | 2955 | **一部分是** |
| 其余（cli / idempotency / ratelimit / mail / git-mint 等） | ~6900 | 不是 |

⇒ 只有 12% 有「FDE 开发工位」的味道，其中真正专属的又只是一小块（`cwd = ~/projects/<project>` 这条锚、
`gitlight` 的判据、预览端口）。

### 6.3 但「agent + 容器」不是一个东西 **【实测】**

`portal/src/internal.js` 的导出面 = 容器↔portal 的运行时契约，共 **52 个**，逐条归类：

| 类别 | 数量 | 例 |
|---|---|---|
| **真·通用运行时** | **25** | `authenticateContainer` `claimRun` `releaseUndeliveredClaim` `releaseRun` `heartbeat` `reapExpiredRuns` `startReaperLoop` `setRunState` `broadcastStopRequest` `broadcastSteerRequest` `broadcastRevoke` `registerSseClient` … |
| **引擎形状** | **23** | `putRound` `getTranscript` `recallTranscript` `putCheckpoint` `getLatestCheckpoint` `putSessionRound` `getSessionTranscript` `saveRunState` `loadRunState` `canonicalHash` `validateEventPayload` … |
| **产品形状** | **4** | `assembleTicket` `createApproval` `getApproval` `drainQueueAfterRun` |

关键事实：**那 23 个不是「通用存储」，它们是 erix-agent 自己的形状**——其中 15 个
（9 个 transcript：`putRound` / `getTranscript` / `recallTranscript` / `putCheckpoint` / `getLatestCheckpoint`
及 4 个 session 变体；6 个 run-state）**逐字就是 `TranscriptStore` 的接口**，用 HTTP 搬过去；
另 8 个（`canonicalHash` / `validateEventPayload` / `postEvents` / `sanitizeListeners` 等）是引擎的事件/快照/校验形状。

⇒ 把「agent」抽进底座，底座就**认识 erix-agent** 了。那它就不是底座，是「erix-agent 托管平台」——
名字没错，但**不能叫基础设施**，因为基础设施的第一性质是不认识它的负载。

### 6.4 真正的分层：两张产品，三层

```
L0  runtime kernel   租户 · 牢笼(jail) · 网络/入口 · 租约/认领/心跳/回收 · 能力注入(虚拟 key)
                      —— 不认识任何引擎，只知道「有个 workload 在领活、续租、要能力」
L1  agent runtime    runs · transcript · termination · queue · run_state
                      —— 故意耦合 erix-agent（就一个引擎，这是决定，不是缺陷）
P1  erix-station     开发工位：projects · dirs · cwd 锚 · git 灯 · 预览端口
P2  本平台           工作项 · 角色 · 契约 · 判据 · 源适配器
```

**L1 为什么不并进 L0**：L0 的契约能用一个**非 agent 负载**验证；L1 不能——它天生是「一个 LLM 工具的账本」。
并成一层等于宣布「底座只能跑 agent」，那句话一旦写进文档，将来想跑爬虫/构建器就得改底座。

**L1 为什么不并进 P1/P2**：两个产品都要 `runs` 和 `transcript`，复制一份就是第二个真相源。

### 6.5 本平台的三条硬不变量

1. **零凭据**：不持 git token、不持 LLM key、不直连外部 API。需要凭据的探测走容器内探针。
2. **零容器**：不起容器、不碰 docker socket。要执行 ⇒ 调 station 的 API。
3. **零身份**：不建自己的登录。人就是 station 的人。

> **这条最容易被破**：一旦它长出自己的登录页，你就有两套身份、两套权限、两套「这个人能看到什么」。

依赖方向因此是单向的：**本平台 → station，永不反向。** station 里一旦出现「员工」「工作项」「判据」这些词，接缝就没了。

### 6.6 现在不抽取底座，理由与许可证

**不抽的三条理由（都有站内先例）**：

1. **一个负载 = 没有「通用」的证据。** 两个产品今天跑的是同一个引擎 ⇒ L0 的「通用接口」从没被第二种负载验证过。
   这是 D8（预支 worktree 复杂度后整块拆掉）、#247、§8.85（故意不传三个引擎新叶子）的同型错。
2. **抽取的成本不在文件，在契约。** `internal.js` 里通用与引擎形状**交织在同一个导出列表里**；
   `/api/internal/*` **没有任何版本标记**（本轮 grep 零命中）。⇒ 现在拆开，契约破了不会响，只会静默出错。
3. **发布税会变三倍。** 今天一次发版：六文件 bump → main CI → tag → 拉三镜像（GHCR 实测时好时坏，
   fde 镜像 422MB 单层 0 B/s 是常态）→ pin 三行 → `docker rm -f` 五台重建。三个产物 = 三套版本、三套 digest pin。

**抽取的许可证（可证伪）**：

> **L0 的成立不靠第二个产品，靠第一个「非 agent 负载」。**

最可能是**外部源的探针容器**（轮询 Gitea / `ls-remote` / npm `dist-tags`，拿凭据，**完全不调 LLM**）：

| | agent 容器 | 探针容器 |
|---|---|---|
| 领活 | 领一个 run，跑工具循环 | 领一个观测任务，跑一次 HTTP |
| 心跳 | 续租 + 捐带 listeners | 续租 + 捐带观测结果 |
| 能力 | LLM 虚拟 key | 只读 git token |
| 存储 | 要 `TranscriptStore`（L1） | **什么都不要** |

⇒ 探针容器能只靠 L0 跑起来的那天，L0 才被证明是 L0。在那之前它只是「L1 的一部分被提前命名了」。

### 6.7 现在寄宿在 station 下是对的

**不抽，但可以「命名」**。零成本、可回退的两件事：

1. 把 L0/L1/P1/P2 这个拓扑写进文档（本目录就是），消除「谁是父项目」这个反复出现的混乱。
2. 一条机器可查的归属判据：`claimRun`/`heartbeat`/`reapExpiredRuns` 属 L0，`putRound`/`getSessionTranscript` 属 L1。
   **注意这条判据只能先按函数判、不能按文件判**——这就是「接缝穿在文件中间」的代价，先承认它。

## 7. 两版：分裂轴是「事件源与作用对象的边界」

### 7.1 三段式为什么错

「简版 / 企业版 / 加强版」这种切法通常按功能切，中间那档永远是「加强版减功能」——
**由减法定义的产品没有存在理由**。两档就够。

### 7.2 分裂轴

| | **简化版** | **威力加强版** |
|---|---|---|
| 事件 | **系统内**（自己的库/账本/容器/证书/端口/心跳） | 系统内 + **系统外**（git 远端、issue、npm、webhook） |
| 动作 | **系统内**资源（会话、run、notes、容器、文件、路由、key） | 同上 + 写外部系统（评论/留痕） |
| 语义源 | ❌ 不需要（内部事实都是机械可判的） | ✅ |
| 凭据 | **零** | 有（在容器侧） |
| 多租户 | 单实例、我们自己 | 有 |
| 一句话 | **把平台自己的运维仪式自动化** | 把这件事变成产品 |

这个切法比我最初想的「谁提供执行」（调用方 CI vs 我们牢笼）好在三点：

1. **它可判。** 「外部」有硬边界（要不要凭据、要不要出网、要不要验签）；「谁提供执行」是软的。
2. **它一次砍掉最贵的三块**：外部凭据、外部轮询/webhook、语义源。
3. **它让第一版的客户就是平台自己**——唯一一种「不需要市场验证也能验证」的自证。

⚠ **代价要认**：简化版不再有对外分发价值（没有 npm 包 / Action 给别人用）。它的价值只剩
「把自己从八千行仪式里赎出来」——而这恰好是最实的价值，只是它不是生意。
**这一点对「只做可研不做开发」的决定反而是支持的**：可研阶段不需要分发。

## 8. 价值判断：客户数 = 1，值不值得做

**按市场算：不值得。按你自己的时间算：非常值得。两件事不该混着说。**

- 按市场：一个用户、无第二客户、无集成广度、无确定性 ⇒ 任何评估都会说「这是个内部工具」。
- 按时间：你正在手做的那些事——**上游发版考据、部署核对、台账维护、砖化巡检、worker 报告复算、
  变异性取证**——全是「重复 + 需要判断 + 每次都要翻八千行文档」的形状，而那正是**唯一一种
  自动化收益大于成本的形状**。

第一版的成功判据不该是「有多少员工」，而是：

> **这周有没有哪一次，是「到点它来找我，并附上证据」，而不是「我记得要去看」。**

这个判据可证伪，第一次就能达成，而且**它也是 n8n 给不了的东西**：n8n 能告诉你「有新版了」，
不能告诉你「这次升级会红几格、证据在哪」。

## 9. 两版逐层对表

| 层 | **简化版**（内部事件 → 内部资源） | **威力加强版** |
|---|---|---|
| **判决层**（[03](02-event-model-and-verdict.md)） | ✅ **全部**（这就是它存在的理由） | ✅ 同一份实现 |
| 证据形状 / 封闭枚举 | ✅ 全部 | ✅ 同一份 |
| 源适配器 | ✅ 3~5 个**机械源**（git 灯、测试退出码、文件存在、账本事实） | ✅ 全量（机械 + 语义 + 人类） |
| **语义源** | ❌ **不做** | ✅ |
| 工作项（`subject`） | ❌ 用现成的锚（会话 / 目录 / 分支），不建新表 | ✅ 自己的账本 |
| 角色 / 员工定义 | ❌ 一个规则就是一个角色，写死在配置里 | ✅ 可实例化 |
| 工具面裁剪 | ❌ 不拥有工具 | ✅ |
| 多租户牢笼（L0） | ❌ 用 station 现成的 | ✅ |
| 身份 / 钱 / 入口 | ❌ 用 station 现成的 | ✅ |
| 账本（transcript / 折叠 / 终止） | ❌ 用 station 现成的（L1） | ✅ |
| dashboard | ❌ | ✅ |
| DB | ❌（最多一份本地 JSON / 复用 station 库） | ✅ |

**关键一格：简化版没有语义源。** 这不是砍功能，是硬约束——
语义源 = 一个 run = 一次模型调用 = 需要 jail、需要钱、需要账本。三件都没有的时候，
**「能机械判的绝不允许调用模型」这条原则自动成立**，而这恰好是简化版最该有的纪律。

## 10. 简化版的事件面：五个，四个已有

**判据（[09](03-macro-model-and-catalog.md) §14.1）：有没有一个人，在不知道这件事的情况下会做错决定。**

| # | 事件 | 出处 | 今天的状态 | 不知道会做错什么 |
|---|---|---|---|---|
| E1 | run 终态（10 种 reason） | `runs.termination` | **已有**，只上了颜色 | 以为还在跑 / 以为成了 |
| E2 | 收工灯（7 个 reason） | `gitlight.js` + `GET /api/git-light` | **已有**，**只上色，没有执行者** | 以为收工了，其实没提交 |
| E3 | 端口对账（分配 vs 实际在听） | `port_allocations` × `port_observations` | **已有两张表**，差集没人算 | 以为预览能用，实际打不开 |
| E4 | 服务证书（6 个可用 state，**四个静默**） | `tls-cert.js` + `verifyLiveCertificate` | **已有**，只上色 | 见 [09](03-macro-model-and-catalog.md) §14.4 |
| E5 | 时钟 | —— | **需新建**（很小） | 以为检查过了 |

> 结论修正：**「十个源零新建」是虚的。** 那个数字之所以好看，是因为它把平台的 bug（砖化/租约/镜像漂移）
> 和统计数字（预览 415/413 分布）都算成了「事件源」。**从「系统里有什么」出发列表，一定会这样。**

**⚠ 「在清单上」不等于「第一版要做」**：事件清单是「平台能观测什么」，宏目录是「第一版配哪些」。
**E4 留在清单，第一版不配宏**（真过期没意义、动作只有通知、agent 换不了证、与本版场景无关联）。

**第一版只配 E1 + E5**（决策者 2026-11-08：「我只需要 session 运行的消息（尤其是结束消息），时钟」）
⇒ E2 / E3 / E4 全部挂账。但注意 E1 的覆盖面比“终态”宽：它还包含**非终态的静默**
（`run.silent` + 宏模板参数 `threshold`，见 [09](03-macro-model-and-catalog.md) §14.7/§14.8）——「出错」走终态，「超时/卡住」走静默，
两者合起来才是「run 的消息」的完整面（[10](05-first-macros.md) §4.3）。

**E4 为什么算事件（我一度降级，又收回）**：理由不是「证书过期」，是**它的失效大多是静默的**——
`chain_incomplete` 的活标本就是 #462：页面报 `live ✓`，客户端严格校验 **error 21**。
「所有信号都说好，只有严格校验说不好」正是这个平台存在的理由。
而真正**不静默**的那个（`expired`，浏览器硬告警）反而是七个里最不需要宏的。

### 10.1 不进事件表的两类

| 类 | 项 | 去处 |
|---|---|---|
| **平台自己的故障** | 账本形状、队列卡 `delivering`、租约/停滞/重排耗尽、镜像漂移、证书 `not_reloaded`（盘上对、线上旧） | **内置告警**（不可配置、不可关闭）+ 运维手册 |
| **现在不做** | 预览缺件统计（产品该支持什么格式，不是状态）、上游发版（一次性仪式 + 需要语义源）、应用不健康（当前全是 dev 环境，会变误报机） | 延后 |

## 11. 简化版的资源面：全部已存在

| 动作 | 出处 | 关键性质 |
|---|---|---|
| 往会话投一句话 / 起 run | `postMessage` + `drainQueuedInputs` | CAS 认领 `pending→delivering` + **过期重认领** + 容器存活闸门 + 阻塞原因 |
| 转向 / 停止 | `steer_arm` + `onRound` abort | 本轮跑完再停；不新增 run 状态 |
| 写 note | notes 六方法 | **已实测「agent 写的注回到模型输入」** |
| 起 / 停 / 重建容器 | `provisioner.js` | 已有 409 幂等、adopt 分支 |
| 写文件（jail 内） | 文件工具（5 个） | 边界谓词「相与」不是替换 |
| 改路由 / 换证书 | `routes.js` / `tls-cert.js` | 已带审计、已带回滚 |
| 只发通知 | mail（#457）+ 审计日志 | channel 已存在 |

⚠ **一条必须避开的坑**（读代码读出来的）**：定时/规则触发不能直接复用 `follow_up` 的投递判定。**
`drainQueuedInputs` 的判定表写着「`failed` / `persistence_failed` / `max_rounds_cap` ⇒ **不投，留在队列**」
（别把排队的话烧在一个坏 run 上——这是对的）。但规则继承这条就会得到：
**一次失败 ⇒ 后续所有唤醒堆在队列里出不来**，而人不在跟前，你永远不会知道日报从周二起就没发过。
⇒ 规则触发要么走独立的 kind 并自带「不投也要记账 + 过期作废」，要么根本不入队、直接 `postMessage`。

## 12. 简化版真正要新写的：引擎侧四格 + 源侧两格

**引擎侧（本节四格）** —— 与「配哪几条宏」无关，做不做宏都要有：

| # | 要写什么 | 为什么绕不开 |
|---|---|---|
| 1 | **规则表**（四格 + 作用域 + 预算） | 没有它就没有平台，只有一堆散落的 cron |
| 2 | **谓词求值 + 边沿/状态区分** | 照 `reapExpiredRuns` 的三条分支抄，别新造 |
| 3 | **血统**（`trigger_kind` 进谓词 + 深度上限） | 没有它就是秒级无限循环（[02](02-event-model-and-verdict.md) §7） |
| 4 | **可见性面**（上次评估 / 真假 / 动作结果 / 花费） | 没有它就分不清「没触发」和「不该触发」（[02](02-event-model-and-verdict.md) §8） |

**其余全部复用。** 这四格里，第 3、4 格是「不做就会死」，不是「以后补」。

**源侧两格（只随第一版宏目录出现）**：E5 时钟源（状态型「今天还没 tick 且已过点」，不需要 cron 表）
与 E3 差集计算（`port_allocations` × `port_observations`，纯读）。它们不属于引擎，只属于那两个源。
⇒ 逐条宏与完整新建面见 [10-first-macros.md](05-first-macros.md) §6。

## 13. 加强版多出来的

| 多出来 | 为什么简化版没有 |
|---|---|
| **外部源**（Gitea API / `ls-remote` / npm `dist-tags` / webhook） | 要凭据 + 要出网 + 要验签 + 要幂等 |
| **语义源**（agent 探测） | 要 jail + 钱 + 账本 |
| **工作项账本**（`subject` 进模型） | 简化版用现成的锚就够 |
| **角色 / 员工定义 + 工具面裁剪** | 简化版一个规则就是一个角色 |
| **多租户** | 简化版就我们自己一个实例 |
| **dashboard** | 简化版靠日志 + 一次 SQL |

⚠ **`subject`（工作项锚）是加强版里唯一要动会话模型的一格，也是最值的一格**：
它把「外部对象 ↔ 谁在干 ↔ 花了多少」变成一等公民。

⚠ **它的债要一起认**：一个活跃仓库一天十几次 push 灌进同一个 `subject`，就是**长会话砖化的另一个入口**。
站内修过六轮账本形状缺陷（分页切轮 → 链式 `partOf` → 未结清 `tool_use` → `:resume` 裸重放 →
归档线性膨胀 → 取错折叠行），**别主动往里灌**。所以锚必须配去抖与合并。

## 14. 简化版砍掉的是外部的麻烦，不是系统的麻烦

这一点必须写在 scope 里，否则会有人以为「简化 = 简单」：

| 麻烦 | 简化版砍掉了吗 |
|---|---|
| 外部凭据 / 出网 / 验签 | ✅ 砍掉了 |
| 语义源的抖动与幻觉 | ✅ 砍掉了（不做语义源） |
| **回环** | ❌ **更危险**（周期秒级、同一张表、因果不可见） |
| **静默不触发** | ❌ 一个没少，而且内部事件面更密 ⇒ 更容易选错观测面 |
| **事件快于执行** | ❌ 一个没少（十个会话同时终态就会堆） |
| **成本失控** | ❌ 反而更容易（外部客户会催，内部事件不会） |
| **「有用」无法自证** | ❌ 只能靠「被赎出多少小时」 |

⇒ 五个硬问题的分析在 [05-feasibility.md](01-decision-and-feasibility.md) §17。**它们就是可研的正题。**

## 15. 可研的交付物不是代码

因为 `erix-station` 要做大升级，本项目的正确产出是**一组能用现有代码/数据回答的问题**，
而不是一个原型。理由：原型会腐烂，问题不会；而这些问题每一个的取证成本都在一小时以内。

## 16. 五条待证命题

| # | 命题 | 怎么证（便宜） | 判据（什么算证成） |
|---|---|---|---|
| **1** | **内部事件面足够表达「值得自动化的仪式」** | 把 `AGENTS.md` 里所有人工仪式逐条翻译成「事件 + 谓词 + 动作 + 锚 + 预算」 | 能翻译的比例 ≥ 多数；**翻不出来的那些本身就是「这平台做不到什么」的清单**（比任何架构图都有用） |
| **2** | **最贵的那几条仪式真的能被自动执行** | 挑**一条**，人工跑一次，把它的判据写成配置文件 | 判据能只用「命令 + 退出码 + 坐标比对」表达，不需要模型参与判断 |
| **3** | **回环与成本可控** | 数「一次 run 终态会命中几条规则」，乘 run 成本，算最坏一天 | 最坏值在你愿意付的钱之内；且深度上限能真的掐住 |
| **4** | **判据能被执行而不只是被描述** | 取一条现有判据（如「跑测试只认退出码」），检查它的输入面 | 只需「一条命令 + 一个退出码 + 一份声明清单」；**需要服务端上下文/跨会话记忆才能表达的，就不是判据，是判断** |
| **5** | **「被赎出多少小时」可度量** | 设计一个能记账的地方：每条规则命中几次、花了多少、人是否因此少做一步 | 能回答「上周这套东西替我做了什么」；答不出来就等于没做 |

### 16.1 命题 1 的做法（最有价值的一条）

不要写文档，**做一张表**：`AGENTS.md` 的每一节 → 它现在靠什么触发 → 它要什么判据 → 它落在哪个锚。

副产品会非常有价值：

- **翻不出来的那些节** = 「这平台做不到什么」的诚实清单（比如「判断这个设计对不对」翻不出来，
  因为它没有判据——那是 `needs-human`）。
- **翻出来但判据依赖模型的那些** = 语义源的候选清单（同时也是成本清单）。
- **翻出来但今天没有任何事件源的** = 要新造源的最小集合（我预期这个集合很小，因为
  [04](01-decision-and-feasibility.md) §10 那十个源已经覆盖了大部分）。

### 16.2 第一个垂直切片：上游发版 → 该不该升 → 派活

**不用「名人去世 → 写悼文」**——那是极好的演示，但**演示不能证伪**。这个切片能：

```
源①  npm dist-tags.latest              机械 · 免费 · 一分钟一次
       state: unchanged | new-version
源②  「这次升级对本仓会红几格」          语义 · 一次 run · 必须带 evidence
       state: trivial | breaking | blocked-by-上游未发版   ← 封闭枚举
       evidence: 读了哪两个包目录 diff、哪几条判据翻红、npm pack 的 shasum
动作   trivial → 起一个升 pin 的 run
       breaking → 通知人并附证据
       blocked → 静默退避
```

它同时验证：机械源产事件、语义源产**带证据的判断**、`state` 枚举挡住模型自由发挥、
三档动作各走不同通道、退避与幂等都有真实对象。

**而且它立刻有用**——站内为「上游发版了没 / 能不能升 / 升了会怎样」写过至少三篇长考据
（§8.60 / §8.86 / §8.90），其中 §8.86 那次甚至抓到**上游文档说删了 16 个导出、npm 上实际一个没删**，
得自己 `npm pack` 对 `dist.shasum` 才敢下结论。**这就是「不信文档、要证据」的标本**，
也是这个切片存在的理由。

## 17. 五个硬问题（简化版一个都没躲开）

### 17.1 回环（内部版更危险）

规则起 run → run 终态 → 触发规则。**周期是秒级、在同一张表里、因果链看不见。**
外部版至少还隔着分钟级的外部系统，内部版没有这层缓冲。

站内已有血统位：`runs.trigger_kind` 的 `'synthetic'` **运行时零使用**（迁移预留、一直空着，
本轮全仓 grep 只在 `0024-queued-inputs.sql` 的 CHECK 里出现）。
**它必须进谓词，不能只落库好看。** 另加 `causal_id` 深度上限兜住「没想到的回环」。

### 17.2 静默不触发（三种形态，本站最高频死法）

| 形态 | 实例 |
|---|---|
| 库里存着，读不出来 | #371-A |
| 配了，没人读 | #331（下发但零读取 = 死光纤） |
| **判据落在错误的观测面上** | §8.87（两次把「0 条 `compaction` 事件」当「TTL 层没工作」，而 TTL 层**根本不发那个事件**；真相在 `compactionStats`，75 次触发省 31.4 万 token） |

第三种最危险，因为它**看起来有数据**。那次错误的代价不是返工，是**差点建议撤掉一个正在省 31 万 token 的配置**。

### 17.3 事件比执行快

`capacity=1` 串行 + 每会话单活跃 run，而事件不会因为你忙就少来。十个会话同时终态就会堆。
⇒ 源侧退避 + 总线侧背压 + 规则侧丢弃陈旧（[02](02-event-model-and-verdict.md) §10）。

### 17.4 规则即平台代码

简化版的规则是我们自己写的（省掉了权限模型，这是巨大优势），代价是
**规则的每次修改都等于改平台** ⇒ 需要和代码同等的审查纪律：变异测试、判据随 run 快照、判据落在具名用例上。

### 17.5 「有用」无法自证

外部版有采用率，内部版只能靠「被赎出多少小时」。这需要一个**可判的**度量（命题 5），
否则做完之后无法回答「这套东西值不值」——而那是最容易变成「做完就没人再提」的死法。

## 18. 已知边界与不做清单

### 18.1 本平台明确不做

| 不做 | 理由 |
|---|---|
| 消息中间件 / 内存总线 | 站内总线已经是 DB；再引入一个 = 第二个真相源，违反「DB 是状态真相」 |
| 可视化编排器 / 表达式 / DAG | 那是变成 n8n 的唯一路径（[01](01-decision-and-feasibility.md) §5） |
| 公网 webhook 入口（第一版） | 现网用户面仍是明文 HTTP；投递入口是拓扑级的事。先轮询 + 容器侧探测，零暴露 |
| 语义源（简化版） | 要 jail + 钱 + 账本，三件都没有 |
| 平台写外部系统（第一版） | 边界是「**谁的渠道**」，不是「出了容器没有」：发邮件 / 站内通知走平台自己的渠道（`mail_settings` / `users.email` 已有）⇒ **可以做**；在 GitHub/Gitea 上评论留痕是写**别人的**系统且会暴露平台身份 ⇒ 仍延后，要单独裁决 |
| 自己的一套身份 | 一旦有第二个登录页，就有两套权限、两套「这个人能看到什么」 |
| 抽 L0 底座 | 许可证是「第一个非 agent 负载」（[01](01-decision-and-feasibility.md) §6.6），不是「产品分开了」 |

### 18.2 已知的、必须先解的空缺

1. **跨会话的机器档案放哪**：notes 作用域是 `sessionId`，而「issue / 分支 / 名人」这些对象跨会话。
   **它是 agent-as-source 的硬前置**，不是细节。
2. **`/api/internal/*` 零版本标记**：三产物之前必须先有它，否则契约破了不会响，只会静默出错。
3. **station 没有给「平台级消费者」的事件出口**：SSE 绑 session 且要登录 cookie。今天只能轮询 `runs` 表。
   正解是照抄站内已有的 `route_outbox` / `materialize_outbox` 那套 **outbox 表**（已有两处同型先例）。
4. **`runs.actor` 与 `runs.trigger_kind` 必须分开**：前者是执行者，后者是发起者，一个 `user_send` 的 run
   完全可以由某个员工执行。合成一列则「员工干的、人发起的活」永远分不出来。

### 18.3 一条硬边界：能力而非密钥

station 今天**容器里不放平台密钥**（git 凭据是只读 bind、LLM 是边缘注入的 per-FDE 虚拟 key）。
这个设计在通用平台上反而更强——**员工拿到的是一个被裁剪的能力，不是一个秘密**。
⇒ 通用化时**不许退化成「往容器里塞 token」**。

## 19. 结论标准（提前写好，免得事后找理由）

可研结束时按这三档判：

| 判定 | 触发条件 |
|---|---|
| **值得做（按简化版）** | 命题 1 能翻译出**多数**仪式；命题 2 至少一条判据能纯机械表达；命题 3 的最坏日成本可接受；命题 5 能给出一个可读的周报 |
| **缩小范围** | 命题 1 只能翻译出少数、且集中在**同一族**（例如全是「部署核对」类）⇒ 那就只做那一族，别做平台 |
| **不值得做** | 命题 2 失败（判据都需要模型判断）**或**命题 3 最坏成本不可接受 **或** 命题 5 无法度量 |

⚠ **一条反直觉的顺序**：命题 5（可度量）比命题 2（能执行）更该先做。
因为「做完发现没法证明它有用」是这类内部工具最常见的死法，而它的成本只是**设计一个记账位置**。
