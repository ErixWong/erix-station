# 09 · 可观测性：怎么回答「执行了没有、结果如何」

> 状态：可研（2026-11-15）。上游 [05](05-first-macros.md) 第一版宏、[07](07-surfaces-and-panel.md) 三个面、
> [08](08-watch-and-review.md) 判决契约。
> 本文只回答一件事：**每次触发有没有发生、结果是什么、为什么没发生 —— 在哪里看。**
> 结论标注沿用【实测】/【推断】/【未验】。

---

## 0. 为什么这块要先落地

前面所有机制（事件、判据、回灌、worktree）都建立在「能看见发生了什么」之上。
**没有可观测性，整套东西不可验证** —— 站内反复出现的「配置了但没有消费者」正是这一格的缺失
（#331 死光纤、#371 事件承接面）【实测：既有事故】。

## 1. 「执行了没有」是三个不同的问题

这是最容易做错的一格。混成一个状态，就再也查不清。

| # | 问题 | 看哪 | 数据 |
|---|---|---|---|
| ① | **平台有没有看过？** | 订阅卡片的**评估水位线** | `macro_assignments.last_evaluated_at` |
| ② | **看过了，命中了吗？** | 流水列表（命中才有行） | `macro_runs` 是否存在 |
| ③ | **命中了，做成了吗？** | 流水那一行的状态 + 判决 | `state` / `verdict` / `reason` |

⚠ **关键：未命中不建记录。** 否则「每个 run × 每条模板」都有一行，纯噪音。
所以「有没有看过」**不能靠记录证明，只能靠水位线**。这两件必须配对设计，少一个就答不了。

### 1.1 水位线的写入语义（2026-11-15 补，审计 blocker）

⚠ **顺序决定它能不能作为证据**：必须**先求值成功、再推进水位线**。
反过来（先写水位线再求值）会让「求值抛异常」的订阅显示健康 —— 那正好把要抓的东西藏起来。

| 时机 | 动作 |
|---|---|
| 求值**成功**（无论命中与否） | `UPDATE … SET last_evaluated_at = now()` |
| 求值**抛异常** / 该条被跳过未求值 | **不写**（保持陈旧 ⇒ 暴露为「循环有问题」） |
| 首次订阅 | `last_evaluated_at = NULL`（界面显示「尚未评估」） |

**新鲜阈值**：`now() - last_evaluated_at > 3 × 评估间隔`（默认间隔 60s ⇒ **180s**）即判陈旧。
留 3 倍余量是因为单轮求值可能慢（要查 git、查 run 状态）。

**写入负载**：每轮 N 条订阅各一次 UPDATE。N = 活跃订阅数（第一版按 20 用户 × 3 条 ≈ 60）。
⇒ 60 次 UPDATE / 60s = **1 次/秒**，【推断】可接受；但**不批量写**，因为要逐条记录
「哪条成功了」（批量写会把失败的也推进）。

⚠ 若将来 N 上到几千，改成「只写成功的那些 + 失败的不动」仍然成立，但需要评估 UPDATE 频率。
现在不预先优化。

## 2. 四态判定表（核心）

拿到一条订阅，看三个数就能定位到唯一一格：

| 水位线 | 流水有行？ | `state` | 结论 | 该查什么 |
|---|---|---|---|---|
| 有，且新鲜 | ❌ | — | **没命中**（正常） | 判据是否太严 |
| 有，且新鲜 | ✅ | `pending` | **已登记，等槽位** | 排队中，正常 |
| 有，且新鲜 | ✅ | `running` | **正在执行** | 超预算仍未终态 ⇒ 见下 |
| 有，且新鲜 | ✅ | `skipped` | **命中但被跳过** | `skipped_reason` |
| 有，且新鲜 | ✅ | `done` / `failed` | **执行完了** | `verdict` |
| 有，且新鲜 | ✅ | `superseded` | **被人优先挤掉** | 会针对新快照重审 |
| **没有 / 陈旧** | — | — | **评估循环没跑**（平台故障） | portal 进程 |

⚠ **`running` 卡死的收敛规则**（审计指出的漏格）：`running` 且
`now - started_at > 2 × 单次预算`（8 轮 / 240s ⇒ **480s**）⇒ 界面标「疑似卡死」，
**不是**自动改状态（平台不改事实），而是触发一条内置告警。

⚠ 这一格**与水位线陈旧是两回事**：水位线陈旧 = 循环不转了；`running` 卡死 = 循环转着但那次执行没回来。

⚠ **水位线陈旧 + 有历史行**：两个信号并列显示，不互相覆盖 ——
历史行告诉你「过去跑过什么」，水位线告诉你「现在还在不在转」。

**最后一行是唯一需要报警的**，前四行都是正常语义。

⚠ **没有记录 ≠ 没执行。** 把「没命中」和「循环死了」都显示成「无记录」，
就是把平台故障伪装成正常静默 —— 这是站内踩过的坑。

## 3. 用户面：会话内值守面板

从会话右上角 `⚙ 值守` 打开，**覆盖式右抽屉 480–520px**
（形态照 `DelegateChildDrawer.vue:217-225`，不是并排，见 [07](07-surfaces-and-panel.md) §11）。

```
┌─ 消息流（被遮罩）────────────────┬ 值守 ─────────────────────────┐
│                                  │ 2 个启用 · 到 11-16 09:00  [⚙]│
│                                  │ ┌ 筛选 ────────────────────┐  │
│                                  │ │ [全部▾] [全部判决▾]      │  │
│                                  │ └──────────────────────────┘  │
│ ── 宏：完成审查 · 整改 ──────────│ 14:03 · run 9f3a · judge_done │
│                                  │   整改 · 3 个未跟踪文件        │
│                                  │   → 已回灌到本会话             │
│                                  │   ↑82k ↓3.1k · 4m12s   [展开] │
│                                  │ ──────────────────────────── │
│                                  │ 13:50 · run 7c21 · judge_done │
│                                  │   通过 · 机械前置通过          │
│                                  │ ──────────────────────────── │
│                                  │ 12:40 · run 8a11 · judge_done │
│                                  │   跳过 · 你刚发了消息          │
│                                  │ ──────────────────────────── │
│                                  │ 本会话 ↑124k ↓9.2k  [估算详情]│
└──────────────────────────────────┴───────────────────────────────┘
```

### 3.1 抽屉顶部：订阅卡片（回答「它活着吗」）

```
┌ 值守 ──────────────────────────────────────┐
│ ☑ 完成审查 · 默认      到 11-16 09:00      │
│   上次评估 14:03:12 · 命中 3 · 跳过 1      │
│ ☐ 静默告警 · 15m                           │
│ ─────────────────────────────────────────  │
│ [停用全部]                                 │
└────────────────────────────────────────────┘
```

**「上次评估 14:03:12」是用户能看到的唯一平台健康信号。**
没有它，用户分不清「没触发」和「坏了」。

### 3.2 用户的筛选只有两个

| 筛选 | 为什么 |
|---|---|
| 模板 | 「我只想看审查的」 |
| 判决 | 「我只想看没通过的」 |

⚠ **用户看不到**：`skipped_reason` 的原始枚举（显示成人话）、`snapshot_id`、
`worktree_path`、`reason` 的原始错误码 —— 那些是管理员诊断面。

### 3.3 用户看到的 `skipped_reason` 人话对照

| 内部值 | 用户看到 |
|---|---|
| `budget_exhausted` | 今日额度用完（20/20）· 琥珀 +「查看额度」 |
| `quiet_hours` | 静默时段（22:00–08:00） |
| `human_present` | 你刚发了消息，不插话 |
| `run_in_progress` | 会话里有 run 在跑 |
| `deferred` | 会话里有 run 在跑，等它结束再送 |
| `deferred_timeout` | 等排位超过 10 分钟，放弃 |
| `active_run_in_cwd` | 同一目录有 run 在跑 |
| `cancelled_by_user` | 你取消了值守 |

⚠ `human_present` **写中性事实，不归责用户**（不写「因为你在说话」）。

└────────────────────────────────────────────────────────────────────┘

### 4.1 筛选器五个，全部落在索引列上

| 筛选 | 取值 | 为什么必须有 |
|---|---|---|
| 模板 | `全部` + 每个模板 | 定位是哪个模板的问题 |
| **状态** | `done` / `failed` / `skipped` / `running` | **必须分开** —— 「跳过」和「失败」是两回事 |
| **判决** | `通过` / `整改` / `未证实有改动` / `需人工` / `未判` | 质量一眼看 |
| 时间 | 近 24h / 7 天 / 30 天 / 自定义 | 默认 7 天（表无限增长） |
| 用户 | 全部 + 用户名列表 | 定位到人（**不到会话**） |

⚠ **筛选后的汇总要跟着变** —— 否则「通过 320 (88.6%)」和筛出来的 3 行对不上，
用户会以为坏了。

⚠ **没有 session 列、没有「点进会话」的链接**（决策者 2026-11-15：不允许管理后台跟踪特定会话，
那是 FDE 用户自己的事）。点行展开的是**事实**，不是会话。

### 4.2 详情：事实 + 时间线

```
┌ run 4b02 · 完成审查 · 默认 ────────────────────────────┐
│ 状态    failed                                        │
│ 原因    审查 run 超时（8 轮 / 240s 到点）              │
│ 判决    未判（unclassified）                           │
│ 快照    snapshot 3f9a… · 变更 12 文件 · 未跟踪 3        │
│ 动作    未回灌 · 已通知用户                            │
│ 成本    ↑82k ↓3.1k · 4m12s                             │
│                                                       │
│ 时间线                                                 │
│  14:03:12  触发（run 9f3a 终态 judge_done）            │
│  14:03:14  快照就绪（12 文件）                          │
│  14:03:15  审查 run 启动                               │
│  14:07:15  超时 → 未判                                  │
│  14:07:16  worktree 已清理 · 用户已通知                 │
└───────────────────────────────────────────────────────┘
```

**「时间线」是诊断的关键** —— 光有最终状态无法判断卡在哪一步。

### 4.3 为什么管理员需要这个页

| 场景 | 没有它会怎样 |
|---|---|
| 模板建完没人用 | 不知道是没触发、还是触发了全被跳过 |
| 某模板一直 `unclassified` | 用户抱怨「审查没用」，管理员查不到根因 |
| 成本突然涨了 | 只能看总账，不知道是哪个模板 |
| 要停用一个模板 | 不知道影响面（多少次、多少人） |
| **`audience=admin` 的模板自己跑的结果** | 号池审计跑完了，管理员没地方看结论 |

最后一行是「管理员也要运行模板」的直接后果：**admin-scope 模板不回灌到任何用户会话，
只有管理台能看它的结果**。

## 6. 数据来源（不新建表）

```
macro_runs  已有：assignment_id · anchor · state · verdict · skipped_reason
                  · started_at · finished_at · child_run_id · depth
                  · verdict_raw · reason · worktree_path · snapshot_id
  JOIN macro_assignments  → user_id
  JOIN macro_templates    → name / kind
  LEFT JOIN runs (child_run_id) → usage（token / 轮数）
```

**一个查询、三表 JOIN**（不是「一个 JOIN」），不需要事件总线、不需要物化视图。
⚠ 模板用 `LEFT JOIN`：软删的模板也要能显示出名字（[07](07-surfaces-and-panel.md) §2.3 末）。

⚠ **新增一列**：`macro_assignments.last_evaluated_at`（§1 的水位线）。
这是本文唯一需要加到数据形状里的字段 —— 没有它，问题 ① 无法回答。

## 7. 分页与保留

⚠ 执行历史**会无限增长**，不能只画「最近若干条」。

| 项 | 第一版做法 |
|---|---|
| 分页 | keyset（`WHERE (started_at, id) < (?, ?)`），照 `listSessions` 的现成形状 |
| 筛选索引 | `(template_id, started_at)` / `(state, started_at)` / `(user_id, started_at)` |
| 导出 | ❌ 不做（会绕开权限面） |
| 保留 | 同 `audit_log` 不删，但默认只查近 7 天 |

## 8. 汇总口径

```
近 7 天：触发 412 · 完成 361 · 跳过 42 · 失败 9
         通过 320 (88.6%) · 整改 33 · 未判 8 · ↑48.2M
```

⚠ **「跳过 42」必须单列**，不能并进「完成」。
跳过率高说明参数配错了（比如静默时段设太宽），而它看起来像「一切正常」。

⚠ **百分比的分母是「完成」不是「触发」** —— 被跳过的没有判决，不该进分母。
