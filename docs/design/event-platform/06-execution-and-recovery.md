# 06 · 执行与回灌：打卡、审查、失败恢复

> 状态：可研（2026-11-07）。来源：一个具体问题——**「每天打卡自动跑 subagent 可以吗？自动开新 session 呢？」**
> 答案分三段：`subagent` 不需要；新会话可以但要一起做三件事；**而「打卡」本身暴露了一个硬阻塞**。

---

## 1. 「跑 subagent」：不需要，而且现在也做不到

### 1.1 现在做不到（是决定，不是缺陷）

station **故意没接** delegation 面：`createDelegateTool` / `config.run.parentRunId` / 五个端口
（`runChild` / `notifyParent` / `transcriptPathFor` / `cwdFor` / `isProcessAlive`）一律不接。理由三条：

1. runner 没有「启动子 run」的原语——**一个 run = 一个 worker 子进程，由 agentd fork**。
2. 名册目录 `~/.erix/delegation/` 是**共享**的；不接 `isProcessAlive` 就没有陈旧记录清理，别的进程能改写你那条。
3. `capacity=1` 让并行没有意义。

### 1.2 但「打卡派活」不需要它

**一个 run 内部就能串行干多件事**（工具循环）。subagent 的真实价值只有两个：

| subagent 的价值 | 在 station 里成立吗 |
|---|---|
| **并行**（同时查三个仓库） | ❌ `capacity=1`，并行只是换个地方排队 |
| **上下文隔离**（子任务不污染主上下文） | ⚠ 有价值，但折叠（`fold-llm`）已经承担了大半 |

⇒ **要「每天干三件事」，有两条路，选第二条：**

| 路 | 形态 | 成败可见性 | 计费 |
|---|---|---|---|
| 一条宏起一个 run 干三件事 | 模型自己拆 | 三件事一起成/一起败 | 一个 run 的账 |
| **三条宏各起一个 run** | 三个独立 run | **各自独立** | **各自独立** |

打卡场景必须选后者：**独立失败可见性比省一个 run 的钱重要得多。**

---

## 2. 「自动开新 session」：可以，但要一起做三件事

`POST /api/sessions` 是普通 API，**没有「只能人建」的闸**。所以技术上成立。
但只做这一半，一个月后这个功能会被关掉——三件事必须同时做：

### 2.1 来源标记（`chat_sessions` 现在**没有**这一列）

**实测**：`chat_sessions` 的列是 `id / user_id / project_id / title / model / status / last_seq / created_at / updated_at`
——**没有任何 origin/source 标记**。⇒ 机器人建的会话和人的会话在侧栏里**长得一模一样**。

每天 1 个 = 一个月 30 个「AI 的日记本」混在你的项目会话里。这不是审美问题：
用户会找不到自己的会话，然后关掉这个功能。

⇒ 必须加 `origin`（`human` / `macro:<name>`），侧栏**默认折叠**自动会话。

### 2.2 确定性标题（不能靠 AI 起名）

AI 自动改名**默认是关的**（#114 的代码默认 + compose 默认 0）。新建会话的标题因此走降级链：
**首条用户消息截断**。而宏投的首条消息是**模板文本** ⇒ **所有日报会话标题一模一样**，翻历史时无法区分。

⇒ 宏生成的会话，标题由**平台写死**：`<宏名> · <日期>`（如 `每日日报 · 2026-11-08`），不参与自动改名。

### 2.3 错峰（`capacity=1` 是硬的）

agentd 每个 FDE 串行。五条宏都在 09:00:00 触发 ⇒ 第 5 条可能 10:30 才跑，而「9 点的日报 10:30 到」已经失去意义。

⇒ clock 源必须带 **jitter**（`09:00 ± N 分钟`），且**同一锚的多条宏之间要错开**。

---

## 3. 硬阻塞：「打卡」需要跨会话记忆，而 notes 作用域是 sessionId

### 3.1 事实

**实测**（`runner/worker.js:537-557`）：notes 目录 = `<home>/sessions/<sessionId>/notes`，
`scopeRef = sessionId`。⇒ **同一会话跨 run 可见，跨会话一行也看不到。**

### 3.2 于是两难

| 选 | 后果 |
|---|---|
| **每天新建会话** | 昨天的 notes 看不见 ⇒ **员工每天失忆**（它不记得昨天做了什么、试过什么、踩了什么坑） |
| **每天复用同一会话** | notes 可见 ⇒ 但长会话**砖化**风险（站内为账本形状修过六轮：分页切轮 / 链式 `partOf` / 未结清 `tool_use` / `:resume` 裸重放 / 归档膨胀 / 取错折叠行） |

### 3.3 结论：这是 [05](01-decision-and-feasibility.md) §18.2 那条缺口的**具体化**，不是细节

> **「跨会话的机器档案放哪」是打卡模式的地基。**

方向很明确：**档案的锚要从 `sessionId` 抬到「目录」或「用户」**——
因为打卡员工盯的是**目录**（这个项目的状态），不是**某次对话**。
notes 的 key 已经是可排序的形态（`fold-20261026T021530Z-r57-s1`），把它从会话目录搬到
`<home>/projects/<dir>/.erix-notes/` 或一个 DB 表，是**作用域参数**的改动，不是重写。

⚠ **但不能简单搬**：notes 目前有「写者=读者」的假设（同一个 run 写的注，下一个 run 读）。
跨会话后会出现**多个 run 同时写同一份档案** ⇒ 需要并发/覆盖语义（谁赢？追加还是替换？）。
这条没想清楚之前，别动。

---

## 4. 「打卡」这个隐喻要小心

station **没有常驻 agent**。每天打卡 = **每天一个新实例**。它的「记忆」只有三个来源：

| 来源 | 跨天可见吗 |
|---|---|
| 会话账本（transcript） | 复用会话则可见，新建会话则不可见 |
| 注入的 `AGENTS.md`（平台约定 + 项目约定） | ✅ 每次 run 都注入 |
| **跨会话档案** | ❌ **今天不存在**（§3） |

⇒ 它不是「员工每天醒来」，是「**员工每天重新入职，靠档案恢复上下文**」。
这个隐喻的差别决定了：**档案是地基，不是可选项**。没有档案的打卡员工，每天都会重做昨天做过的事、
重踩昨天踩过的坑——而这恰好是站内最贵的一类浪费（重复读 150 次、78.5% 重复率那次 §8.84 有实测）。

## 5. 新增的三格（补进 [06](03-macro-model-and-catalog.md) §3 的五格）

| 格 | 值 | 为什么 |
|---|---|---|
| `session_origin` | `human` / `macro:<name>` | 侧栏默认折叠自动会话，否则一个月后功能被关掉 |
| `session_title` | 平台写死 `<宏名> · <日期>` | AI 改名默认关，模板首条消息会导致标题全同 |
| `notify_on_failure` | `true` / `false` | **任务型宏的失败必须自己会说话**，见 §6 |

## 6. 任务型宏的失败必须自己会说话

任务型宏的产物是**一个 run**，而 run 失败只在**那个会话里**显示。
⇒ **没人打开那个会话，就永远不知道日报从周二起就没发过。** 这是 [02](02-event-model-and-verdict.md) §8 那三种静默死法的第四种。

**两条口径**：

1. **`notify_on_failure: true`** 是任务型宏的默认值。失败 ⇒ 走通知通道（邮件/站内）说清「哪个宏、哪个锚、什么 reason」。
2. **失败不补跑**。第二天该跑还是跑当天的，**不是把昨天的补上**——否则一次故障会让成本在第二天翻倍，
   而且「补跑的日报」本身没有价值（它描述的是过去）。正确动作是 **跳过 + 记一笔「因上次失败跳过」+ 通知**。

⚠ 这与站内 `queued_inputs` 的既有口径**相反**，而那个相反是对的：排队的话是**人的意图**（不能丢），
宏的触发是**时间的意图**（过期就废）。**别把两者混成一个机制。**

---

## 7. 所以打卡型宏的最小形状

```
anchor_type      用户（或目录）
on_state         clock: <date> tick（状态型：今天还没 tick 且已过点，不是「刚好到点」）
action           任务型：新建会话（origin=macro:xxx，标题=平台写死）+ 起 run
criteria         <该宏自己的判据>
budget           每锚每日 1 次 + jitter ±N 分钟
notify_on_failure  true（默认）
```

**已定（2026-11-08，与 [05](05-first-macros.md) §4.2 的 M7 一致）**：第一版用**宏会话复用**，
即每个 `(用户, 宏)` 一条长期会话（`origin=macro:<name>`，标题平台写死），
产物**由平台落盘** + 发一条通知。

⚠ **初稿在这里写的是「第一版先做产出文件 + 通知，会话留到第二步」，与 05 的 M7 冲突。**
现在统一到 05：**会话是要的（run 必须挂在 session 上），但它是「宏会话」，不是给用户对话的会话**。
「文件 + 通知」仍然是**交付形态**（用户看的是文件与通知，不是那条会话），两者不矛盾。

**宏会话复用还顺手解掉了一个硬阻塞**：notes 是 `sessionId` 作用域 ⇒ 同一会话 ⇒ 昨天的注今天还在，
「跨会话记忆不存在」这条（§3）对宏会话不成立。代价是会变长，靠 #351/#352 的读侧折叠兜。

## 9. 先接受一条简化：参数进模板，不进订阅

上一轮我把 `threshold` / `phases` 放进订阅参数。**产品上第一版不该这么做**，理由：

- 参数进订阅 ⇒ 同一个宏在不同人手里有 N 种行为，**运维无法审计「这个宏到底在干什么」**
- 宏的全部价值是「范围缩减」：管理员定义一次，所有人行为一致，最坏成本可算
- 现在也没有第二个用户提出过参数需求

⇒ **模型上**参数仍然分两类（源的 `state` 枚举 vs 规则参数，[09](03-macro-model-and-catalog.md) §14.8），
但**第一版所有参数写在宏模板里**，订阅只有「开 / 关 + 作用域」。等真有人需要再开。

## 10. 两条流程其实是同一条

```
E1 run 终态
   → 分诊（按 reason/errorCode 决定走哪条判据）
   → 判据求值（机械的，或起一个审查 run）
   → 判决：pass / red / no-op-claim / needs-human   ← [03](02-event-model-and-verdict.md) 的封闭枚举
   → 动作：回灌（新 run） / 通知（站内、邮件） / 什么都不做
```

审查与恢复的差别**只在判据从哪来**：

| | 完成 → 审查 | 失败 → 恢复 |
|---|---|---|
| 判据是什么 | 「成果对不对」（需要语义判断） | 「还能不能救」（先机械分诊） |
| 谁判 | 一个**新会话**里的审查 agent | 机械表（§12.1），只有救不了才起 agent |
| 回灌到哪 | **原会话**（执行者接着改） | **原会话**（要上下文） |
| 出口 | 通过 ⇒ 结束；不过 ⇒ 回灌一次；再不过 ⇒ 人 | 救回来 ⇒ 结束；救不了 ⇒ 邮件 |

## 11. 流程 A：完成 → 审查 → 回灌

> 决策者原话：「针对已经完成的 agent，调用一个 agent 去做 check 和 review，就结果，
> 如果发现未竟事宜，或者 bug，漏洞啥的，怎么把消息灌回去。」

### 11.1 审查者必须是**另一个会话**（这条不能省）

[03](02-event-model-and-verdict.md) §14 的硬口径：判据必须**独立于执行者**。同会话 = 同一份上下文 =
继承执行者已经建立的假设（“我已经改好了”），那不叫审查，叫自审。

⇒ 新会话，`trigger_kind='synthetic'`，`runs.actor='macro:review'`，cwd 与原会话相同。

⚠ 代价如实记：新会话看不到原 transcript ⇒ 必须由**平台拼装证据**（§11.2）。这是可接受的成本，
因为「看得见原 transcript」正是独立性被破坏的原因。

### 11.2 审查者看什么：平台拼装，不让它自己去翻

| 证据 | 从哪来 | 不给会怎样 |
|---|---|---|
| 原任务 | `messages` 首条 user | 它不知道要审什么，只能泛泛点评 |
| 最终答复 | 最后一条 assistant | 只审代码、不审「声称」⇒ 漏掉 no-op-claim |
| `git status --porcelain -uall` | shell | 漏掉「说成了但没提交」 |
| `git log --oneline -5` | shell | 不知道 agent 自己提交过没有 |
| `git diff --stat` 或 `git show --stat HEAD` | shell | 不知道改了哪些文件 |
| 验证命令与退出码 | 从 transcript 的 `tool_result` 里抠 | 不知道它到底跑没跑测试 |

⚠ **不给 diff 全文**（可能几 MB）。给 `--stat` + 路径清单，让它自己按路径 `git diff <path>` 挑着看。
这是「平台拼装证据」的边界：**给坐标，不给全文**。

### 11.3 审查的判据（三条机械可查，不是「你觉得对吗」）

1. **声称做的事有没有对应改动/证据** —— 防 `no-op-claim`（[03](02-event-model-and-verdict.md) §13）
2. **改动有没有被 git 兜住** —— 防「说成了没提交」（D9 的真实事故形状）
3. **有没有跑过验证，退出码是什么** —— 防「我改了但没测」

⇒ 判决只能落在 `{pass, red, no-op-claim, needs-human}` 里，**不许输出自由文本结论**。
`needs-human` 的典型：改动涉及密钥/权限/删除，审查者不该自己判。

### 11.4 怎么把消息灌回去（用户问的核心）

站内有**三条**投递通道，终态之后只有一条是对的：

| 通道 | 语义 | 终态后用它对吗 |
|---|---|---|
| `postMessage` | 新建一个 run | ✅ **对** |
| `queued_inputs`（`follow_up`） | 排给「当前 run 之后」 | ⚠️ 终态时队列刚被 drain，时序靠不住 |
| `steer` | 打断**正在跑**的 run | ❌ 没有活跃 run |

⇒ `postMessage(pool, { userId, sessionId: 原会话, content, triggerKind: 'synthetic' })`
（`portal/src/sessions.js:532`；`trigger_kind` 的 CHECK 里已经有 `synthetic`，
至今零写入者 —— 它就是为这件事留的，**零迁移**）

**灌回去的不是审查报告全文，是一条带判据的指令：**

```
上一轮你声称完成了，但审查发现 3 条未竟事宜：
1. <finding>   证据：<file:line / 命令与输出>
2. ...
请逐条处理；不要重做已完成的部分；处理完请说明每条怎么核实的。
```

为什么不是全文：审查者的推理灌进执行者上下文 ⇒ 执行者会替审查者辩护（"它可能没理解"），
而且上下文暴涨（一次审查报告可能几万 token）。

⚠ **`postMessage` 会 409 `run_in_progress`**（用户刚好发了新消息）。处理 = 记一笔 `deferred`，**不重试**。
理由：人已经在场，机器人插话只会更乱；重试还会和人的消息抢 `capacity=1`。

### 11.5 回灌几次：**一次**

```
depth 0：执行 → 审查 → 通过            ⇒ 结束
depth 1：执行 → 审查 → 不通过 ⇒ 回灌
         → 执行 → 审查 → 不通过        ⇒ 停，转人工（邮件）
```

三条理由：

1. **两轮「AI 说成了 / AI 说没成」说明判据本身不清楚**，第三轮不会更清楚
2. **成本**：每次审查 = 一次 run（实测单 run 输入 148k–390k token，
   见 [08](06-execution-and-recovery.md) §4）⇒ 一次回灌 ≈ 2 次额外 run
3. **[03](02-event-model-and-verdict.md) 的「验收带宽」**：AI 自循环把审查量放大，人反而更看不清

## 12. 流程 B：失败 → 分诊 → 恢复

> 决策者原话：「针对出错的 agent，触发一个 agent 去做分析，并尝试使其恢复工作，
> 失败了调用邮箱通知用户。」

### 12.1 ⚠ 「出错」不是一个事件，是七种 —— 只有两格半该起 agent

| `termination.reason` / `errorCode` | 平台能自己修吗 | 该谁处理 | 起 agent？ |
|---|---|---|---|
| `failed` + `retryable`（timeout / rate_limited / server / disconnect） | ✅ 重发 | **平台** | ❌ **白烧钱** |
| `failed` + `invalid_messages` | ✅ 读侧折叠已修（#351/#352） | **平台** | ❌ |
| `failed` + 其他（工具/代码错误） | ❌ | **agent 分析** | ✅ |
| `max_rounds_cap` | 半（要判断还剩什么） | **agent 继续** | ✅ |
| `guard_unverified` | 半 | **agent 复核** | ✅ |
| `aborted` | —（用户主动） | 不问 | ❌ |
| `persistence_failed` | ✅ 平台落盘 | **内置告警** | ❌ |

⇒ 给一个 `timeout` 起 agent 去「分析」，它花 30 万 token 得出的结论是「建议重试」。
**这一格必须留在平台侧。**

### 12.2 平台能修的就别起 agent（同 [09](03-macro-model-and-catalog.md) §14.6 的原则）

`retryable` 的重发**甚至不该是宏**，它是 `runs` 状态机的一部分。
⚠ 但现在**没有**这个自动重发 —— 这是**平台的欠账**，不是宏的用例。
把它做成宏会犯「把平台责任转嫁给用户」的同一个错。

### 12.3 起分析 agent 时给它什么

| 证据 | 为什么 |
|---|---|
| `termination.reason` + `errorCode` + 最后一条错误文本 | 不知道死因就只能瞎猜 |
| 最后一次 `tool_use` 与它的 `tool_result` | 崩在哪一步 |
| 原任务 | 要恢复得知道目标 |
| `git status --porcelain` | 有没有半成品，别覆盖掉 |

### 12.4 恢复动作只有两种，都回灌到**原会话**

- **继续**（`max_rounds_cap` / `guard_unverified`）：回灌「你还有预算，继续完成剩下的」
- **修**（工具/代码错误）：回灌「上次失败在 X，先修 X 再继续」

⚠ **这里与流程 A 相反**：审查要**新会话**（独立性），恢复要**原会话**（上下文）。
判据：**要独立性就换会话，要上下文就留会话。**

⚠ `max_rounds_cap` 的「继续」必然是**新 run**（旧 run 的轮数预算已耗尽），
不能在同 run 上加预算 —— 那会破坏「`max_rounds_cap` 是一个确定的终态」这条契约。

### 12.5 恢复失败的出口：邮件（A4）

判决 `needs-human` ⇒ 邮件。正文必须有四件：

```
1. 会话链接（点进去就是现场）
2. 失败原因（reason + errorCode + 一句话人话）
3. agent 尝试过什么（它改了什么 / 诊断结论）
4. 还剩什么没做
```

⚠ **不给「再试一次」按钮**：见 [08](06-execution-and-recovery.md) §6 ——
循环型失败不重放，因为时间/意图已经过期，重放只会重复烧钱。

## 13. 回灌是**唯一**能让系统成环的边

前面所有宏都是「事件 → 动作」的一次性边。**回灌把动作的结果重新变成事件的输入** ——
这是整个设计里唯一能成环的地方，也是唯一必须上血统的地方（[02](02-event-model-and-verdict.md) §7）。

### 13.1 血统三件套（零迁移）

| 字段 | 取值 | 现状 |
|---|---|---|
| `runs.trigger_kind` | `synthetic` | CHECK 里已有，**至今零写入者** |
| `runs.actor`（新增） | `macro:review` / `macro:recover` | 需新增列（或先塞进 `termination`/事件 payload） |
| `depth`（可从 actor 链推） | 0 / 1 | 第一版可用「会话内已有几条 synthetic run」代替 |

⚠ `trigger_kind` 的语义是**发起方式**，`actor` 是**谁干的** —— 两者不能合并
（[02](02-event-model-and-verdict.md) 已有这条口径）。

### 13.2 幂等：同一 `(session, run, finding_key)` 只回灌一次

`finding_key` = 审查判决里那条 finding 的稳定标识（例如 `file:line:rule` 的哈希）。
没有它，审查者换个措辞就会触发第二次回灌 —— 那就是成本螺旋的入口。

### 13.3 上限：`depth ≤ 1`（即最多回灌一次）

### 13.4 三种死法

| 死法 | 症状 | 防线 |
|---|---|---|
| **成本螺旋** | 每轮审查都发现新问题，永远不收敛 | `depth ≤ 1` + 每会话每日审查次数上限 |
| **抖动** | 审查者说 A 有问题 → 执行者改 A → 审查者说 A 改坏了 | 只回灌一次；第二次直接转人 |
| **判决漂移** | 同一份产出，两次审查结论不同 | 判据快照（[03](02-event-model-and-verdict.md) §17）；两次差异超阈值 ⇒ 转人 |

## 14. 接线点（不造新东西）

| 需要什么 | 已有 | 缺 |
|---|---|---|
| 终态事件 | `runs.status` + `termination` | 一个谓词（[10](05-first-macros.md) §4.1） |
| 起审查 run | `postMessage(triggerKind='synthetic')` | `actor` 标记 |
| 证据拼装 | `messages` 表 + shell（git） | 一个小函数 |
| 判决 | [03](02-event-model-and-verdict.md) 的枚举 | 判决落库（一张小表） |
| 邮件 | `mailer.send({to,subject,text})` | 「通知用」模板路径 |
| 可见面 | 会话内分隔条 | 一行「宏：审查未通过，已回灌」 |

⚠ **可见面不是可选项**：没有它，「审查跑了但没回灌」和「审查根本没跑」在界面上长得一样
（站内 #331 死光纤的同型失败）。

## 15. 待定（要决策者拍）

1. **审查者的工具面**：只读（`readFile` / `searchText` / `tree` + 只读 shell）还是全量？
   只读更安全，但它就没法跑测试来验证「测试真的过了」。
2. **审查者能不能顺手改代码**：能 ⇒ 就没有「回灌」这一步（但独立性也没了）；不能 ⇒ 现在的设计。
3. **审查 run 在侧栏怎么显示**：出现一个叫「审查」的会话会不会让用户困惑？
   还是挂在原会话下面（像 delegate 抽屉那样）？
4. **邮件正文给不给 diff 摘要**：给 ⇒ 人不用点开就知道；不给 ⇒ 正文短、必须点进去。
5. **`actor` 放哪**：`runs` 新列（要迁移），还是先塞进 `run_events` 的 payload（零迁移但不可索引）。
