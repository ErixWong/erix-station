# 06 · 宏：管理员定义，用户直接用

> 状态：可研（2026-11-07）。本文记录一个**改变简化版 scope 的决定性收敛**：
> 把「用户可写的规则」换成「**管理员定义的宏目录 + 用户订阅**」。
> 前提仍未变：只做设计，不做开发。

---

## 1. 结论

> **宏不是「省掉用户配置」的便利功能，它是一次范围缩减：把「需要一门规则语言」降级成「需要一张目录表」。**
>
> ⚠ **但它不是「复杂度消除」，是「复杂度集中」**：场景五的「这周没提交」、场景四的「这次升级会红几格」——
> 宏表达不了，必须由**源**算完以 `state` 枚举交出来。⇒ 复杂度从「N 个用户写的规则」搬到「M 个源」
> （`M << N`、可测、可审查、可版本化）。这才是宏模型的真正论证，不是「用户省事」。
> 代价：**源会成为平台里最重的代码**，每个源都必须有「state 枚举是什么意思」的文档与判据，否则它就是黑箱。

三件事同时消失：

| 原本要写的 | 宏之后 |
|---|---|
| 规则表达式语言（谓词、条件、组合） | **不存在**——宏内部零分支（§4.1） |
| 规则的权限模型（谁能写、谁能改、谁能看） | **不存在**——用户不能写规则，只能订阅（§6） |
| 成本不可预估（用户自建规则 × 模型调用） | **可预估**——预算随宏一起定义，管理员能算总账（§6） |

而它换来的东西不是「用户省事」，是 [03](03-verdict.md) 那篇的核心命题落地：
**把一个已经被验证过的验收流程变成可复用的。**
（不是复用「流程」——见 §3，那是 n8n template 的做法，也是我们不该学的。）

---

## 2. 三面分离：定义 / 执行 / 呈现

「在管理台实现简版」这个提法里有三件不同的事，它们落点不同：

| 面 | 是什么 | 落点 | 为什么 |
|---|---|---|---|
| **定义面** | 宏目录、参数、预算、全局开关 | **管理台**（`admin.<域>:9443`） | 这是运维决策，不是用户决策 |
| **执行面** | 事件求值、边沿判定、投递、血统 | **portal 后端**（不属于任何 UI） | 它是后端循环，不该依赖有人打开页面 |
| **呈现面** | 用户看到「这个目录被哪些宏盯着」「这个会话被唤醒过几次」「证据」 | **工作台**（session 相关） | 证据落在会话账本里，用户在那儿看 |

### 2.1 一条硬边界（#450 之后就是物理的）

管理台入口的边缘白名单**只放** `①SPA ②/api/admin ③/api/auth + /api/me`，其余 `/api/*` 一律 deny。
⇒ **任何「用户侧」的动作（订阅、查看自己的宏、看证据）都不能做成 `/api/admin/*`**，
否则用户为了开关一个宏得开两个 host —— 这是可用性灾难，不是洁癖。

⇒ 正确的切法：**宏的定义与预算是 admin API；宏的订阅与证据是用户面 API。**
同一个宏在两个 UI 里各出现一半，**这是设计要接受的分裂，不是 bug**。

## 3. 宏是什么（五格）

```
macro:
  anchor_type   目录 | 仓库 | 端口 | 服务 | 会话 | 用户   ← 它盯着什么（见 §4.2 三层）
  on_state      (source, object_key, state) 的枚举值  ← 什么时候动（封闭，允许派生）
  action        投一句话 / 起一个 run / 只记一笔 / 发通知  ← 做什么
  criteria      判据清单（声明式，随宏版本快照）    ← 怎么算数
  budget        每锚每日 N 次 + 免打扰时段 + 单 run maxRounds  ← 花多少钱
```

**没有第六格。没有表达式、没有条件分支、没有子宏调用、没有编排。**

### 3.1 与 n8n template 的根本区别

| | n8n template | 本平台的宏 |
|---|---|---|
| 复用什么 | **流程**（节点连线） | **判据**（什么算干完了） |
| 用了之后 | 流程跑完了 | 你接受了一套验收标准 |
| 失败了谁告诉你 | 节点报错 | 判决是 `red` / `no-op-claim` |
| 有没有「看起来成功」 | 有（返回 200 就算成功） | **没有**（`no-op-claim` 单独一档） |

> **n8n 有几千个模板，全是流程。流程模板不告诉你它到底有没有用。
> 我们的宏把判据一起打包 —— 所以「用这个宏」= 「接受这套验收标准」。**

这是唯一一处我们比 n8n 强、而且它结构上学不来的地方（它没有可执行判据的土壤）。

## 4. 三个必须接受的代价

### 4.1 分支判断必须前移到源的 `state` 枚举

宏内部零分支，所以「如果 A 就 X，否则 Y」必须变成 **两个宏 + 一个更细的 `state` 枚举**：

```
源产出 state: trivial | breaking | blocked-by-upstream
宏① on_state=trivial   → 起一个升 pin 的 run
宏② on_state=breaking  → 通知人并附证据
宏③ on_state=blocked   → 静默退避（不通知）
```

**这不是妥协，这是收益**：它强迫「这个判断到底是什么」变成**有名字、可测试、可计数**的东西。
反例就是站内 §8.87 那次事故——「TTL 层有没有工作」这个判断没有枚举，我就读错了观测面。

⚠ **对源的硬要求**：源的 `state` 必须足够细，细到「一个 state 对应一个动作」。
如果做不到，说明**这个判断还没想清楚**，不是「宏不够灵活」。

### 4.2 锚 ≠ 投递目标（这条解决了「事件和 session 相关」的直觉）

用户的直觉对一半：**证据、通知、用户看的地方都在会话里**——这是对的。
但**订阅不能绑会话**，三条理由：

1. **会话有生命周期**。用户今天开新会话，昨天订阅的宏就失效了。
2. **同一目录会有 N 个会话**。绑会话就要重复订阅 N 次。
3. **事件是目录/仓库的属性**（git 灯、端口、证书），不是会话的属性。

⇒ **订阅锚 = 作用域；事实对象 = 那个具体的东西；投递目标 = 某个会话。三层分开。**

| 层 | 是什么 | 例 |
|---|---|---|
| **订阅作用域** | 我允许这个宏盯我哪些东西 | 我的所有目录 / 某个目录 / 我的所有会话 / 我的账号 |
| **事实对象** | 具体那个东西 | `dir:~/projects/x` / `session:<uuid>` / `run:<uuid>` / `port:22000` |
| **投递目标** | 通知落在哪个会话 | 该作用域下最近活跃的会话 / 新建 |

⚠ **「订阅绑会话」仍然不对**（会话有生命周期、同目录多会话），但**「会话」必须是合法的事实对象类型**：
⚠ **「会话」不是事实对象**：没有任何事件的 object 是会话（砖化是平台缺陷，不是事件，见 [09](09-catalog.md) §1.1）。
会话只是**作用域**与**投递目标**。「事件和 session 相关」在投递层成立，在事实层不成立。

### 4.3 宏不组合

一旦允许「A 完再 B」，就回到 DAG，然后回到可视化编排器（[01](01-positioning.md) §5）。

**替代品是黑板**：宏之间不互相调用，只通过**锚的状态**互相看见。
`A 干完 → 锚的 state 变了 → B 的 on_state 命中`。这不需要任何组合语法。

## 5. 关键一刀：宏的「是什么」在代码里，「开不开 / 参数多少」在 DB

这是让整个模型落地的最小形状：

| | 存哪 | 谁能改 | 为什么 |
|---|---|---|---|
| **宏的内容**（锚类型 / on_state / action / criteria / 默认预算） | **代码**（一份常量表） | 只有发版 | 判据要能被**变异测试**、被审查、被 diff。放进 DB 编辑就等于把判据变成数据，而数据不能被测试 |
| **启用状态 / 参数 / 预算覆盖** | **DB** | 管理员（管理台） | 调参不该发版 |

⇒ 管理台 UI 因此极小：**一个列表 + 每行几个参数框 + 一个开关**。**没有编辑器。**

⚠ 这条同时解决了「宏会腐烂」的一半：宏改版 = 发版，所以它跟着代码一起过 CI、过变异测试、过 review。
DB 里的宏定义会静默腐烂（站内 #331「配了没人读」正是这一族）。

## 6. 三方分离：定义权 / 订阅权 / 预算权

| 权力 | 谁 | 后果 |
|---|---|---|
| **定义** | 管理员（改代码 + 发版） | 用户不能写规则 ⇒ 没有规则语言 ⇒ 没有权限模型 |
| **订阅** | 用户（在自己的目录上开/关） | 用户自己决定「这个目录要不要被盯着」 |
| **预算** | 管理员（宏自带日限额，可覆盖） | **全公司开满的最坏成本可算** |

**超额行为必须是确定的**：超过日限额 ⇒ **静默退避 + 记一笔「因预算跳过」**，不排队、不补发。
理由：补发会让成本在第二天翻倍，而「因为没钱所以没提醒你」这件事**必须可见**（否则就是 [02](02-model.md) §8 的静默死法）。

⚠ **`budget` 不只管次数，还管时段**：通知型宏必须有 `quiet_hours`（默认 22:00–08:00，UTC+8），
否则凌晨三点一封「session 完成」的邮件会让人关掉整个功能。窗口内**积压到窗口外合并发一封**
（不是丢弃，也不是逐条补发）——「因为你睡觉所以没告诉你」同样必须可见。

⚠ **一个真实的错配**：用户开满 10 个宏，管理员预算只够 2 个。⇒ 宏列表上必须**同时显示**「这个宏一天最多花多少」
和「你已经开了几个」，否则用户以为自己在用，实际全被预算挡掉。

## 7. 投递目标：通知型 vs 任务型

宏声明自己是哪一种，决定通知落在哪：

| 类型 | 动作 | 投递目标 | 成本 |
|---|---|---|---|
| **通知型** | 往会话投一句话（不起 run） | **该锚下最近活跃的会话** | 0 |
| **任务型** | 起一个 run | **新建会话**（除非宏显式指定） | 一个 run |

**为什么任务型默认新建会话**：长会话反复被机器人插话会让账本形状变复杂（站内为账本形状修过六轮），
而且「这是宏起的活」和「这是我刚才在聊的活」混在一个会话里，用户分不清。

**为什么通知型投最近活跃会话**：用户正在那儿工作，弹在眼前才有用。新建会话会让「提醒」变成「又开一个窗口」。

## 8. 宏的版本与判据快照

宏的身份是 `macro:<name>@<version>`。改判据 = 升版本，不原地改。

理由（[03](03-verdict.md) §6）：**判据必须随 run 存快照**，否则改完判据之后，历史 run 会变成
「按今天的标准看它失败了」——你在**重写历史**。

⇒ 订阅存的是 `macro:<name>`（跟随最新版），但**已跑的 run 记的是当时那个 `@<version>` 的判据全文**。

## 9. 简化版因此缩到多小

对照 [04](04-scope.md) §4 那四小格：

| 原四小格 | 宏模型之后 |
|---|---|
| ① 规则表（四格 + 作用域 + 预算） | **拆成两件更小的**：宏目录（代码常量）+ 订阅表（`(user, anchor, macro, params, enabled)`） |
| ② 谓词求值 + 边沿/状态区分 | **只剩**「`state` 枚举比对 + 边沿/状态区分」，**没有表达式求值** |
| ③ 血统 | **不变**（`trigger_kind` 进谓词 + 深度上限） |
| ④ 可见性面 | **不变**（且多一格：`因预算跳过`） |

⚠ **诚实的一句**：宏砍掉的是「**用户可写的规则语言**」和「**权限模型**」，**不是执行机制**。
求值、边沿、血统、可见性一样都不能少（[04](04-scope.md) §6 同一条纪律）。
把「宏」理解成「所以实现变简单了」是错的；它变简单的是**要设计的东西**，不是**要跑的东西**。

## 10. 宏目录的初稿已经写好了

**`AGENTS.md` 的每一节都是一条宏的草稿。** 那不是文档，那是需求。

而且它自动分两类，锚不同：

| 类 | 例 | 锚 | 执行者 |
|---|---|---|---|
| **用户宏** | 收工检查（git 灯红/黄）、依赖更新、日报 | 目录 / 用户 | 该 FDE 自己的容器 |
| **运维宏** | 部署后 digest 核对、证书到期、号池占用、版本漂移 | 仓库 / 服务 / 端口 | 一个指定的 FDE（或运维自己的） |

⚠ **没有「无锚宏」**。运维宏看起来最像「平台自己干的事」，但它仍然锚在某个具体对象上，
执行仍然落在某个具体 FDE 里 —— 否则没人跑它、没人付 token（[02](02-model.md) §6.2 的同一条）。

## 11. 三条风险（宏模型特有的）

| 风险 | 形态 | 防线 |
|---|---|---|
| **宏会腐烂** | 写了一次、判据过时、没人再验 | 宏在代码里 ⇒ 跟着 CI 跑；判据必须钉在具名用例上（[03](03-verdict.md) §5）；宏的命中率上可见性面 |
| **宏目录会变成「功能列表」** | 20 个宏之后要求组合、要求条件、要求编辑器 | §4.3 不组合 + §4.1 分支前移到枚举。**这两条一破就回到 n8n** |
| **用户开满但预算不够** | 界面显示「已启用」而实际全被挡 | §6 的错配提醒 + `因预算跳过` 必须可见 |

## 12. 第一个该设计的宏：收工提醒（git 灯）

选它而不是「上游发版」，因为它验的是**链路**而不是**钱**：

| 格 | 值 |
|---|---|
| `anchor_type` | 目录 |
| `on_state` | `gitlight: uncommitted`（🔴）或 `unpushed`（🟡） |
| `action` | 通知型：往该目录最近活跃会话投一句话（附仓库名 + 灯色 + 「让 AI 收尾」的提示） |
| `criteria` | `git status --porcelain -uall` 为空 ∧ 有远端时 `HEAD == refs/remotes/<r>/<br>`（**就是 `gitlight.js` 现有判据，零新增**） |
| `budget` | 每目录每日 1 次 |

四条理由：

1. **判据现成**（`gitlight.js` 已实现红/黄/绿/⚪ 三态判定与全部坑：`-uall` 不能退化成 `-uno`、`--no-optional-locks` 必须在子命令之前、worktree 的 refs 在 `commondir`）。
2. **成本几乎零**：通知型，不起 run；大部分时候不触发。
3. **它补的是一个已经被决策者认下的洞**：D9 明确写了「告知面先行，灯后上」，灯已经上了（#359 P0a/P0b），
   而**「收工即提交」至今只有告知面，没有任何执行者**。
4. **它验全链**：源（gitlight）→ 影子表（目录状态）→ 谓词（红/黄）→ 边沿/状态 → 动作（投递）→ 血统（`trigger_kind`）→ 可见性（命中了几次、为什么没触发）。

第二个再上「上游发版」（任务型 + 语义源 + 真花钱），验的是 run 侧与预算侧。
