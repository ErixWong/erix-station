# 08 · 打卡型宏：每天自动跑、自动开会话

> 状态：可研（2026-11-07）。来源：一个具体问题——**「每天打卡自动跑 subagent 可以吗？自动开新 session 呢？」**
> 答案分三段：`subagent` 不需要；新会话可以但要一起做三件事；**而「打卡」本身暴露了一个硬阻塞**。

---

## 1. 「跑 subagent」：不需要，而且现在也做不到

### 1.1 现在做不到（是决定，不是缺陷）

station **故意没接** delegation 面：`createDelegateTool` / `config.run.parentRunId` / 五个端口
（`runChild` / `notifyParent` / `transcriptPathFor` / `cwdFor` / `isProcessAlive`）一律不接。理由三条：

1. runner 没有「启动子 run」的原语——**一个 run = 一个 worker 子进程，由 agentd fork**。
2. 名册目录 `~/.erix/delegation/` 是**共享**的；不接 `isProcessAlive` 就没有陈旧记录清理，别的进程能改写你那条。
3. `capacity=1` 让并行没有意义。

### 1.2 但「打卡派活」不需要它

**一个 run 内部就能串行干多件事**（工具循环）。subagent 的真实价值只有两个：

| subagent 的价值 | 在 station 里成立吗 |
|---|---|
| **并行**（同时查三个仓库） | ❌ `capacity=1`，并行只是换个地方排队 |
| **上下文隔离**（子任务不污染主上下文） | ⚠ 有价值，但折叠（`fold-llm`）已经承担了大半 |

⇒ **要「每天干三件事」，有两条路，选第二条：**

| 路 | 形态 | 成败可见性 | 计费 |
|---|---|---|---|
| 一条宏起一个 run 干三件事 | 模型自己拆 | 三件事一起成/一起败 | 一个 run 的账 |
| **三条宏各起一个 run** | 三个独立 run | **各自独立** | **各自独立** |

打卡场景必须选后者：**独立失败可见性比省一个 run 的钱重要得多。**

---

## 2. 「自动开新 session」：可以，但要一起做三件事

`POST /api/sessions` 是普通 API，**没有「只能人建」的闸**。所以技术上成立。
但只做这一半，一个月后这个功能会被关掉——三件事必须同时做：

### 2.1 来源标记（`chat_sessions` 现在**没有**这一列）

**实测**：`chat_sessions` 的列是 `id / user_id / project_id / title / model / status / last_seq / created_at / updated_at`
——**没有任何 origin/source 标记**。⇒ 机器人建的会话和人的会话在侧栏里**长得一模一样**。

每天 1 个 = 一个月 30 个「AI 的日记本」混在你的项目会话里。这不是审美问题：
用户会找不到自己的会话，然后关掉这个功能。

⇒ 必须加 `origin`（`human` / `macro:<name>`），侧栏**默认折叠**自动会话。

### 2.2 确定性标题（不能靠 AI 起名）

AI 自动改名**默认是关的**（#114 的代码默认 + compose 默认 0）。新建会话的标题因此走降级链：
**首条用户消息截断**。而宏投的首条消息是**模板文本** ⇒ **所有日报会话标题一模一样**，翻历史时无法区分。

⇒ 宏生成的会话，标题由**平台写死**：`<宏名> · <日期>`（如 `每日日报 · 2026-11-08`），不参与自动改名。

### 2.3 错峰（`capacity=1` 是硬的）

agentd 每个 FDE 串行。五条宏都在 09:00:00 触发 ⇒ 第 5 条可能 10:30 才跑，而「9 点的日报 10:30 到」已经失去意义。

⇒ clock 源必须带 **jitter**（`09:00 ± N 分钟`），且**同一锚的多条宏之间要错开**。

---

## 3. 硬阻塞：「打卡」需要跨会话记忆，而 notes 作用域是 sessionId

### 3.1 事实

**实测**（`runner/worker.js:537-557`）：notes 目录 = `<home>/sessions/<sessionId>/notes`，
`scopeRef = sessionId`。⇒ **同一会话跨 run 可见，跨会话一行也看不到。**

### 3.2 于是两难

| 选 | 后果 |
|---|---|
| **每天新建会话** | 昨天的 notes 看不见 ⇒ **员工每天失忆**（它不记得昨天做了什么、试过什么、踩了什么坑） |
| **每天复用同一会话** | notes 可见 ⇒ 但长会话**砖化**风险（站内为账本形状修过六轮：分页切轮 / 链式 `partOf` / 未结清 `tool_use` / `:resume` 裸重放 / 归档膨胀 / 取错折叠行） |

### 3.3 结论：这是 [05](05-feasibility.md) §4.2 那条缺口的**具体化**，不是细节

> **「跨会话的机器档案放哪」是打卡模式的地基。**

方向很明确：**档案的锚要从 `sessionId` 抬到「目录」或「用户」**——
因为打卡员工盯的是**目录**（这个项目的状态），不是**某次对话**。
notes 的 key 已经是可排序的形态（`fold-20261026T021530Z-r57-s1`），把它从会话目录搬到
`<home>/projects/<dir>/.erix-notes/` 或一个 DB 表，是**作用域参数**的改动，不是重写。

⚠ **但不能简单搬**：notes 目前有「写者=读者」的假设（同一个 run 写的注，下一个 run 读）。
跨会话后会出现**多个 run 同时写同一份档案** ⇒ 需要并发/覆盖语义（谁赢？追加还是替换？）。
这条没想清楚之前，别动。

---

## 4. 「打卡」这个隐喻要小心

station **没有常驻 agent**。每天打卡 = **每天一个新实例**。它的「记忆」只有三个来源：

| 来源 | 跨天可见吗 |
|---|---|
| 会话账本（transcript） | 复用会话则可见，新建会话则不可见 |
| 注入的 `AGENTS.md`（平台约定 + 项目约定） | ✅ 每次 run 都注入 |
| **跨会话档案** | ❌ **今天不存在**（§3） |

⇒ 它不是「员工每天醒来」，是「**员工每天重新入职，靠档案恢复上下文**」。
这个隐喻的差别决定了：**档案是地基，不是可选项**。没有档案的打卡员工，每天都会重做昨天做过的事、
重踩昨天踩过的坑——而这恰好是站内最贵的一类浪费（重复读 150 次、78.5% 重复率那次 §8.84 有实测）。

## 5. 新增的三格（补进 [06](06-macros.md) §3 的五格）

| 格 | 值 | 为什么 |
|---|---|---|
| `session_origin` | `human` / `macro:<name>` | 侧栏默认折叠自动会话，否则一个月后功能被关掉 |
| `session_title` | 平台写死 `<宏名> · <日期>` | AI 改名默认关，模板首条消息会导致标题全同 |
| `notify_on_failure` | `true` / `false` | **任务型宏的失败必须自己会说话**，见 §6 |

---

## 6. 任务型宏的失败必须自己会说话

任务型宏的产物是**一个 run**，而 run 失败只在**那个会话里**显示。
⇒ **没人打开那个会话，就永远不知道日报从周二起就没发过。** 这是 [02](02-model.md) §8 那三种静默死法的第四种。

**两条口径**：

1. **`notify_on_failure: true`** 是任务型宏的默认值。失败 ⇒ 走通知通道（邮件/站内）说清「哪个宏、哪个锚、什么 reason」。
2. **失败不补跑**。第二天该跑还是跑当天的，**不是把昨天的补上**——否则一次故障会让成本在第二天翻倍，
   而且「补跑的日报」本身没有价值（它描述的是过去）。正确动作是 **跳过 + 记一笔「因上次失败跳过」+ 通知**。

⚠ 这与站内 `queued_inputs` 的既有口径**相反**，而那个相反是对的：排队的话是**人的意图**（不能丢），
宏的触发是**时间的意图**（过期就废）。**别把两者混成一个机制。**

---

## 7. 所以打卡型宏的最小形状

```
anchor_type      用户（或目录）
on_state         clock: <date> tick（状态型：今天还没 tick 且已过点，不是「刚好到点」）
action           任务型：新建会话（origin=macro:xxx，标题=平台写死）+ 起 run
criteria         <该宏自己的判据>
budget           每锚每日 1 次 + jitter ±N 分钟
notify_on_failure  true（默认）
```

**第一版建议先做「产出文件 + 通知」，会话留到需要追问时再开**：
打卡要验的是「到点它来找我，并附上证据」，不是「能对话」。
会话一旦开了，就要同时承担 §2.1–2.3 三件事 + §3 的记忆问题——**那是第二步，不是第一步**。
