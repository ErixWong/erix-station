## 0. 一句话

> **会话停下 → 平台把事实摆到审查 agent 眼前（不下判决）→ agent 判 → 不过就一句话要求整改 →
> 灌回原会话 → 再判一次 → 再不过转人工。**

只有一个判决者。没有机械判据层 —— 平台只**采集事实**，不**下结论**。

## 1. 为什么 M9 不设「机械判据层」（范围：只限 M9）

> ⚠ **范围限定（2026-11-15 审计后修正）**：本节撤掉的是「**M9 旁边再放一个机械判决者**」，
> **不是**「整个平台不要机械检查」。`02`/`05`/`06` 里的机械判据（M7 的产出非空、失败分诊表、
> 变异测试）**保留**。机械检查在本框架里的角色是**可引用事实与硬前置**，不是最终判决。

曾经设计过「判据层 ①：机械（`gitlight` reason 直接出整改话，零 token），M9 语义层只在它全绿时才跑」。
**撤掉了**，三条理由：

1. **Goodhart**：`git commit` 一下灯就绿，哪怕内容是垃圾（「一个空 commit 也能让灯绿」是站内既有结论）。
2. **两个判决者，用户永远信便宜的那个**：机械层零 token 秒级、语义层一个 run 分钟级 ⇒
   机械层会**替代**语义层，不是漏斗。
3. **它给的是确定性的假象**：**灯只有 4 种颜色**（`portal/src/gitlight.js:41`
   `LIGHT_ORDER = ['red','yellow','grey','green']`），而工作树的状态空间远大于四种。
   `reason` 更不是封闭枚举 —— 它是「这次采样为什么是这个色」，多仓库/部分扫描会不断产生新值
   （`unreadable` / `busy` / `unchecked_partial` / `no_repo` / `covered_by_outer_repo` / …）
   **【实测】**。
   **藏起来的不确定性比显式的不确定性更危险** —— 看到"灯绿了"就不再追问，而问题还在。

⇒ **机械证据 ≠ 机械判据**。平台必须把事实采集得**完整且不可回避**（agent 只读，看不到就是不知道），
但**不许替 agent 下结论**。

⚠ **反例要认**：有些机械检查确实比模型可靠（「某条测试退出码必须为 0」「某文件必须存在」）。
它们的正确位置是**硬前置**：不过就直接判 `red`，不进模型。所以不是「不要机械检查」，
是「**机械检查不许和模型并列发布同一个最终判决**」。

## 2. 概念图（五个东西的关系）

## 4. 事实采集（平台的责任，不下判决）

审查启动前，平台把下面这些**摆进工作包**。缺任何一项，agent 就是"不知道"：

| 事实 | 来源 |
|---|---|
| 原任务 | `messages` 首条 user |
| 执行者最后的说法 | 最后一条 assistant |
| `git status --porcelain -uall` | shell（平台侧） |
| `git log --oneline -5` | 同上 |
| HEAD / 是否 detached / 是否有远端 | 同上 |
| `git diff --stat` | 同上 |
| **原 run 跑过的验证命令与退出码** | 从 transcript 的 `tool_result` 提取 |
| `termination.reason` / `error_code` / 轮数 / 用量 | `runs` |

⚠ **第 7 行是硬要求**：审查者只读 ⇒ 它跑不了测试 ⇒ 「验证过没有」只能引用原 run 的记录。
没有这一项，它只能猜。

### 4.1 还要补三组事实（2026-11-15 审计后补）

**① 快照身份**（回答「审的是哪一份成果」）：

| 事实 | 为什么 |
|---|---|
| 原目录的 `HEAD` sha + 冻结 worktree 的 `HEAD` sha | 两者必须相同，不同就说明基线错了 |
| 已跟踪/未跟踪变更清单 + 工作树内容摘要 hash | `git diff --stat` 只是统计，**不是可复核的变更清单** |
| 冻结时刻 | 判断"这次审查对应哪一刻" |

**② 验证与快照的绑定**（回答「那些测试结果还算不算数」）：

| 事实 | 为什么 |
|---|---|
| 命令原文 + cwd + 退出码 + 结束时间 | 只有退出码不知道跑的是什么 |
| 具名失败用例（若有） | 「失败 3 个」不如「`not ok 7 - 空态四种`」 |
| **验证时**的文件树/HEAD 指纹 | 否则旧测试可能发生在最后一次编辑**之前**，不能证明当前 worktree |

⇒ **只读审查不许声称「测试通过」**。它能说的是：「原 run 在指纹 X 上跑过这些命令，退出码 Y；
本次审查未独立复验。」这是两件事，文档必须分开写。

**③ 过滤边界**（回答「这份快照是不是完整的」）：

| 事实 | 为什么 |
|---|---|
| 排除了哪些 ignored 文件（清单） | 排除掉构建配置会让 agent 把不完整快照当完整 |
| 密钥/环境文件如何脱敏 | `.env` 之类既不能给也不能静默丢弃，要记「已脱敏」 |

⚠ 审计原话：「只读审查无需声称测试通过」—— 这一条比原来那句「验证过没有」准确，已采纳。

## 5. 审查（唯一的判决者）

| 项 | 做法 |
|---|---|
| 会话 | **新会话**（`trigger_kind='synthetic'`），同容器、同 cwd |
| 审查对象 | **worktree**：`git worktree add --detach <path> HEAD` + 把脏文件带进去 |
| 只读 | jail root = worktree、`writable: []`、**不给 `shell`**、**不给 note** |
| 工具面 | 只有 `readFile` / `searchText` / `tree` |
| 输出 | 见 §6 |
| 清理 | `git worktree remove --force` |

### 5.1 为什么必须 worktree

`capacity` 实际是 **2**（`runner/agentd.js:56` `ERIX_AGENTD_CAPACITY || 2`，`:418` 显式发送；
`:15-17` 注释写明「同项目并行放行…同 cwd 两个 run 各自隔离…工作文件碰撞由用户 git 自治」）**【实测】**。

⇒ 同一 cwd 可能有两个 run 在写。**不冻结，「通过」指哪一刻的工作树就说不清。**

`git worktree add` 共享 object database ⇒ **省掉的是 `.git` 历史的复制**。
⚠ 但**仍要 checkout 整棵 tracked 工作树**（成本 ∝ checkout 的文件数/字节数），
再加上补丁与未跟踪文件的搬运 —— 所以「成本 ∝ 脏文件数」这个说法**过强**，已改。

**它只 checkout 已提交内容，看不到未提交改动** —— 而那正是最常见的审查对象，所以必须补：

```bash
git -C <原目录> worktree add --detach <wt> HEAD
git -C <原目录> diff HEAD --binary > /tmp/<id>.patch
git -C <wt> apply /tmp/<id>.patch
git -C <原目录> ls-files --others --exclude-standard -z \
  | rsync -a --from0 --files-from=- <原目录>/ <wt>/
```

### 5.2 为什么只读必须「不给 shell」

`shell` 是 `bash -c <command>`，无命令白名单（`runner/lib/shell-tools.js:84-98,192`）**【实测】**。
`cwd` 只是起点，`cd ~/projects/foo` 就逃出 worktree ⇒ jail 管不到它。

⚠ 两道门都要关，且**装配点有两处**：`runner/worker.js:613-615`（registry）与 `:643`（`baseToolSchemas`）
**【实测】**。只改一处等于没改。

### 5.3 worktree 的建/清生命周期（任何一步失败都不许开始审查）

```
建：worktree add → diff HEAD --binary → apply → rsync 未跟踪 → 【一致性校验】→ 启动审查
清：审查结束 → worktree remove --force → 删 patch → 记账
```

| 环节 | 失败时 |
|---|---|
| `worktree add` 失败 | 记 `state=failed` + `reason=worktree_add_failed`，**不启动审查**，通知用户 |
| `git apply` 非零退出 | 丢弃半成品、`remove --force`、记 `patch_apply_failed`、不启动审查 |
| `rsync` 失败 | 同上，记 `untracked_copy_failed` |
| **一致性校验不过** | 见下 |

**一致性校验**（补上 copilot 指出的原子性缺口）：搬运前后各取一次
`HEAD` + `git status --porcelain -uall | sha256`，不一致 ⇒ 说明搬运期间原目录被改，
**重试一次；仍不一致 ⇒ 记 `snapshot_unstable` 并放弃本次审查**（不许拿拼凑树去审）。

**孤儿清理**：worktree 的路径登记进 `macro_runs.worktree_path`。portal 启动时扫一遍：
`git worktree list` 里有、但对应 `macro_runs` 已终态超过 1 小时的 ⇒ `git worktree remove --force`。
清理本身失败 ⇒ 记 warn + 留到下次启动（**不阻塞**，但必须可见）。

**预算**：仓库大小 / `worktree add` 耗时 / 磁盘占用各设上限，超限 ⇒ 记 `snapshot_too_large`，
不启动审查，通知用户（而不是默默跑半小时）。

### 5.4 五种失败出口（每种都要有持久状态）

| 情况 | `state` | `verdict` | 谁被通知 | 回灌吗 |
|---|---|---|---|---|
| 审查 run 超时（8 轮 / 240s 到点） | `failed` | `unclassified`（未判） | 用户 | ❌ |
| LLM / API 失败 | `failed` | `unclassified` | 用户 | ❌ |
| 工作包构建失败（§5.3 任一环） | `failed` | `unclassified` | 用户 | ❌ |
| 首行格式非法 | `done` | `unclassified` | 用户 + 管理员 | ❌（存原文供人看） |
| 回灌 409 `run_in_progress` | `skipped` | 保留原判决 | **不通知**（人在场） | ❌，记 `deferred` |

⚠ **共同底线**：这五种都**不许伪装成 `red` 或 `needs-human`** —— 它们是"没判成"，不是"判成没过"。
所以统一落 `unclassified`，界面显示「未判」。

### 5.5 `until` 到期时的在途审查

`until` 到期 ⇒ `enabled=false`，但**不强杀已经启动的审查**：

| 时刻 | 行为 |
|---|---|
| 到期前已启动的审查 | 允许在 8 轮 / 240s 预算内收尾，结果正常入流水 |
| 到期后 | **禁止**由它再触发整改 run 或下一轮审查 |
| 到期通知 | 与"最后一轮结果"分两条，文案要说清"这轮结果之后不会再审" |
| 用户主动取消值守 | 与自然到期**分开处理**：可中止在途审查，并记 `cancelled_by_user` |

⚠ 没有这一格会出现：到期那一刻在跑的审查回来触发了一次整改，用户以为已经关了。

⚠ **同 UID 不等于"文件系统给不了只读"**（我曾这么写，是错的）。准确说法：
同 UID ⇒ **不能靠属主/传统权限做每会话区分**；只读靠「换根 + 空 writable + 无 shell」。

## 6. 判决的落库：第一行固定格式

回灌要一句话（自由文本），面板要能显示判决（四档）—— 两者用一个最小约定解决。

### 6.1 唯一映射表（全文以此为准）

| 存储枚举（`macro_runs.verdict`） | 模型首行 | 界面词 | 谁产生 |
|---|---|---|---|
| `pass` | `结论：通过` | 通过 | 模型 |
| `red` | `结论：整改` | 整改 | 模型 |
| `no-op-claim` | `结论：未证实有改动` | 未证实有改动 | 模型 |
| `needs-human` | `结论：需人工` | 需人工 | 模型 |
| `unclassified` | —— | 未判 | **平台**（未完成 / 超时 / 首行非法） |

⚠ **`未判` 是平台状态，不是第五种模型判决**，模型不许输出它。
`07` 里的「未通过 / 未达成」只作正文用语，**不再作为独立存储或解析枚举**。

### 6.2 首行契约与 fail closed

```
结论：整改
有 3 个未跟踪文件没纳入版本管理：a.js, b.ts, c.md
```

- 平台只接受**首行完整匹配** `^结论：(通过|整改|未证实有改动|需人工)$`
- **正文原样回灌**（前面加 `[系统]`），不引入 JSON、不要求 findings 数组
- **非法输出一律 fail closed**：缺行 / 前置 BOM 或 Markdown / 大小写或空格变化 / 未知值 / 首行被截断
  ⇒ 存原文、`verdict=unclassified`、界面显示「未判」、**不自动回灌**、转人工并发通知
- 不许把正文里偶然出现的「结论：通过」当首行

⚠ **`needs-human` 走人工出口**（通知人），不套用「整改回灌」这个动作 —— 它要求的是人看，不是 AI 再改。

⚠ 这是**有意的取舍**：代价是「整改到第几条了」机器不知道，进度只能靠人看。

## 7. 回灌（唯一的环）

```js
postMessage({
  sessionId: 原会话,
  content: "[系统] <结论之后的正文>",
  triggerKind: 'synthetic',   // CHECK 里已有，零迁移
})
```

| 约束 | 为什么 |
|---|---|
| 幂等 `(assignment, anchor, 判据)` | 否则换个措辞就再灌一次，无限循环 |
| `depth ≤ 1` | 两轮「AI 说成了 / AI 说没成」说明判据不清楚 |
| `409 run_in_progress` ⇒ 记 `deferred`，**不重试** | 人已在场，机器人插话只会更乱 |
| 正文必须以 `[系统]` 开头 | 模型读到的是一段 `role=user` 文本，它不知道这是系统说的 |

## 9. 分期：审查进第一版（M9）

**这是本轮的决策**：审查不再是「后续候选」，进第一版，编号 **M9**。
连带改动：`05-first-macros.md` 的目录从 3 条变 4 条；`07-surfaces-and-panel.md` 撤掉

## 10. 数据形状（只写形状，不写 DDL）

⚠ **本节是 [07](07-surfaces-and-panel.md) §6 形状的增量**，不是另一份定义。
两边合起来才是完整形状；`07` 已有的字段这里不重复列。

```
macro_templates      同 07
macro_assignments    07 的字段 + until(timestamptz, UTC 存储)
macro_runs           07 的字段（state / skipped_reason / started_at / finished_at）
                       + verdict(enum, 见 §6.1) · remediation_text
                       + child_session_id · depth · parent_macro_run_id
                       UNIQUE (assignment_id, anchor, 判据)   ← 幂等的唯一执行点
```

- `until` 到期 ⇒ `enabled=false` + 一条通知。默认**次日 09:00**（存 UTC，显示本地）。
- `state` 取值（与 `07` 对齐）：`pending` / `running` / `done` / `skipped` / `failed`。
- `skipped_reason` 取值：`budget_exhausted` / `quiet_hours` / `human_present` /
  `run_in_progress` / `deferred_timeout` / `active_run_in_cwd`。

## 11. 风险与防线

| 风险 | 防线 |
|---|---|
| 回灌成环 | `depth ≤ 1` + 幂等键 |
| 审查对象在变 | worktree 冻结（含脏文件） |
| 用户以为在守、其实没守 | 到期通知 + 面板「上次评估时刻」+ 管理台 `skipped_reason` |
| 审查者改了用户代码 | worktree + `writable: []` + 无 shell |
| 成本失控 | 值守有 `until`；单次预算 8 轮 / 240s；同 cwd 有活跃 run 不启动 |

### 11.1 「同 cwd 无活跃 run」必须是原子的

⚠ **`capacity=2` 本身不是锁。** 先查"没有活跃 run"、再启动审查，两步之间另一个 run 可以起来。

⇒ 判据落在**同一条 SQL 的条件插入/条件更新**里（或 `SELECT … FOR UPDATE` 锁住该 cwd 的登记行），
不能写成"查一次、然后启动"。查失败/有活跃 run ⇒ 记 `skipped_reason=active_run_in_cwd` 并等下一个事件。

**人优先**（`08` §11 那条）同理：用户发消息时若审查在排队 ⇒ 审查标 `superseded`，
**不得回灌过期结论**，重新开始时针对新快照重审。
