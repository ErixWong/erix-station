# 08 · 值守与审查（框架定稿草稿）

> 状态：**草稿，2026-11-15，待评审**。上游 [05](05-first-macros.md)（第一版宏）、
> [06](06-execution-and-recovery.md)（回灌）、[07](07-surfaces-and-panel.md)（界面）。
> 本文是这几轮讨论的收口：**一条链、一个判决者、一次回灌**。
> 结论标注沿用【实测】/【推断】/【未验】。

---

## 0. 一句话

> **会话停下 → 平台把事实摆到审查 agent 眼前（不下判决）→ agent 判 → 不过就一句话要求整改 →
> 灌回原会话 → 再判一次 → 再不过转人工。**

只有一个判决者。没有机械判据层 —— 平台只**采集事实**，不**下结论**。

## 1. 为什么没有机械判据层（这条是设计决定，不是省略）

曾经设计过「判据层 ①：机械（`gitlight` reason 直接出整改话，零 token）」。**撤掉了**，三条理由：

1. **Goodhart**：`git commit` 一下灯就绿，哪怕内容是垃圾（「一个空 commit 也能让灯绿」是站内既有结论）。
2. **两个判决者，用户永远信便宜的那个**：机械层零 token 秒级、语义层一个 run 分钟级 ⇒
   机械层会**替代**语义层，不是漏斗。
3. **它给的是确定性的假象**：`reason` 只有 8 个离散值，而真实完成度是连续的。
   **藏起来的不确定性比显式的不确定性更危险** —— 看到"灯绿了"就不再追问，而问题还在。

⇒ **机械证据 ≠ 机械判据**。平台必须把事实采集得**完整且不可回避**（agent 只读，看不到就是不知道），
但**不许替 agent 下结论**。

## 2. 概念图（五个东西的关系）

```
值守（= 一组 session-scope 订阅 + 一个 until）        ← 不是新概念，是一个组合
  ├─ 完成审查    run-review   有判决、有回灌          ← 第一版第 4 条（M9）
  ├─ 静默告警    run-silence  纯通知（M8）
  └─ 终态通知    run-notify   纯通知（M1）

界面右上角（user scope，管理员代配）
  └─ 定时任务    scheduled-task  任务型（M7）
```

**「值守」不是新实体**：它就是「用户在会话右上角勾的那几个 + 一个到期时间」。
勾了「完成审查」= 开了值守。

## 4. 事实采集（平台的责任，不下判决）

审查启动前，平台把下面这些**摆进工作包**。缺任何一项，agent 就是"不知道"：

| 事实 | 来源 |
|---|---|
| 原任务 | `messages` 首条 user |
| 执行者最后的说法 | 最后一条 assistant |
| `git status --porcelain -uall` | shell（平台侧） |
| `git log --oneline -5` | 同上 |
| HEAD / 是否 detached / 是否有远端 | 同上 |
| `git diff --stat` | 同上 |
| **原 run 跑过的验证命令与退出码** | 从 transcript 的 `tool_result` 提取 |
| `termination.reason` / `error_code` / 轮数 / 用量 | `runs` |

⚠ **第 7 行是硬要求**：审查者只读 ⇒ 它跑不了测试 ⇒ 「验证过没有」只能引用原 run 的记录。
没有这一项，它只能猜。

## 5. 审查（唯一的判决者）

| 项 | 做法 |
|---|---|
| 会话 | **新会话**（`trigger_kind='synthetic'`），同容器、同 cwd |
| 审查对象 | **worktree**：`git worktree add --detach <path> HEAD` + 把脏文件带进去 |
| 只读 | jail root = worktree、`writable: []`、**不给 `shell`**、**不给 note** |
| 工具面 | 只有 `readFile` / `searchText` / `tree` |
| 输出 | 见 §6 |
| 清理 | `git worktree remove --force` |

### 5.1 为什么必须 worktree

`capacity` 实际是 **2**（`runner/agentd.js:56` `ERIX_AGENTD_CAPACITY || 2`，`:418` 显式发送；
`:15-17` 注释写明「同项目并行放行…同 cwd 两个 run 各自隔离…工作文件碰撞由用户 git 自治」）**【实测】**。

⇒ 同一 cwd 可能有两个 run 在写。**不冻结，「通过」指哪一刻的工作树就说不清。**

`git worktree add` 共享 object database ⇒ 成本 ∝ 工作文件数，不是仓库大小。
**但它只 checkout 已提交内容，看不到未提交改动** —— 而那正是最常见的审查对象，所以必须补：

```bash
git -C <原目录> worktree add --detach <wt> HEAD
git -C <原目录> diff HEAD --binary > /tmp/<id>.patch
git -C <wt> apply /tmp/<id>.patch
git -C <原目录> ls-files --others --exclude-standard -z \
  | rsync -a --from0 --files-from=- <原目录>/ <wt>/
```

### 5.2 为什么只读必须「不给 shell」

`shell` 是 `bash -c <command>`，无命令白名单（`runner/lib/shell-tools.js:84-98,192`）**【实测】**。
`cwd` 只是起点，`cd ~/projects/foo` 就逃出 worktree ⇒ jail 管不到它。

⚠ 两道门都要关，且**装配点有两处**：`runner/worker.js:613-615`（registry）与 `:643`（`baseToolSchemas`）
**【实测】**。只改一处等于没改。

⚠ **同 UID 不等于"文件系统给不了只读"**（我曾这么写，是错的）。准确说法：
同 UID ⇒ **不能靠属主/传统权限做每会话区分**；只读靠「换根 + 空 writable + 无 shell」。

## 6. 判决的落库：第一行固定格式

回灌要一句话（自由文本），面板要能显示判决（`通过/整改/需人工`）—— 两者用一个最小约定解决：

```
结论：通过
```
或
```
结论：整改
有 3 个未跟踪文件没纳入版本管理：a.js, b.ts, c.md
```
或
```
结论：需人工
detached HEAD 上改了 6 个文件，看不出是有意还是失误
```

**平台只读第一行的 `结论：` 后面那三个字**，填 `macro_runs.verdict`；**正文原样回灌**。
不引入 JSON、不引入字段校验、不要求 findings 数组。

⚠ 这是**有意的取舍**：代价是「整改到第几条了」机器不知道，进度只能靠人看。

## 7. 回灌（唯一的环）

```js
postMessage({
  sessionId: 原会话,
  content: "[系统] <结论之后的正文>",
  triggerKind: 'synthetic',   // CHECK 里已有，零迁移
})
```

| 约束 | 为什么 |
|---|---|
| 幂等 `(assignment, anchor, 判据)` | 否则换个措辞就再灌一次，无限循环 |
| `depth ≤ 1` | 两轮「AI 说成了 / AI 说没成」说明判据不清楚 |
| `409 run_in_progress` ⇒ 记 `deferred`，**不重试** | 人已在场，机器人插话只会更乱 |
| 正文必须以 `[系统]` 开头 | 模型读到的是一段 `role=user` 文本，它不知道这是系统说的 |

```
│ ☐ 静默告警                                    │

```

### 8.2 界面右上角：我的模板（`user` scope，管理员代配）

```
┌                                        [🔔] [模板 ▾] [头像] ┐
└─────────────────────────────────────────────────────────────┘

┌ 模板 ▾ ─────────────────────────────┐
│ ☑ 定时任务 · 每日 9 点    到 11-16  │
│ ──────────────────────────────────  │
│ 本会话：☑ 完成审查                  │
└─────────────────────────────────────┘
```

### 8.3 流水面板（点值守 → 覆盖式右抽屉 480–520px）

```
┌ 消息流 ────────────────┬ 值守 ───────────────────────┐
│                        │ 12:03 · run 9f3a · judge_done│
│ ── 宏：审查 · 整改 ─────│   结论：整改                 │
│                        │   3 个未跟踪文件 → 已回灌    │
│                        │ 11:40 · run 7c21 · judge_done│
│                        │   结论：通过                 │
└────────────────────────┴─────────────────────────────┘
```

判决四档显示词：`通过` / `整改` / `需人工` / `未判`（审查没跑完或超时）。
上游四档 `pass/red/no-op-claim/needs-human` 到界面的映射见 [02](02-event-model-and-verdict.md) §13，
`no-op-claim`（未证实有改动）在界面单独显示成「未证实有改动」，**不并入「整改」**。

### 8.4 用户回来看到什么

```
值守已结束（11-16 09:00 到期）

审查 3 次：
  · 9f3a  整改 → 已回灌（未跟踪文件）
  · 7c21  通过
  · 4b02  需人工（detached HEAD，回灌 1 次后仍未建分支）

[看流水]  [再守一天]
```

**到期必须通知**，否则用户以为还在守。

## 9. 分期：审查进第一版（M9）

**这是本轮的决策**：审查不再是「后续候选」，进第一版，编号 **M9**。
连带改动：`05-first-macros.md` 的目录从 3 条变 4 条；`07-surfaces-and-panel.md` 撤掉
「`run-review` 是后续候选」的标注。

理由：整个框架的重心在审查上；「自动值守」这个产品价值离开审查就不成立。

## 10. 数据形状（只写形状，不写 DDL）

```
macro_templates      id · kind · name · params · audience · scope · enabled
macro_assignments    id · template_id · user_id · session_id · until · enabled
macro_runs           id · assignment_id · anchor · verdict · remediation_text
                        · child_session_id · depth
                        UNIQUE (assignment_id, anchor, 判据)   ← 幂等的唯一执行点
```

`until` 到期 ⇒ 自动 `enabled=false` + 一条通知。默认**次日 09:00**。

## 11. 风险与防线

| 风险 | 防线 |
|---|---|
| 回灌成环 | `depth ≤ 1` + 幂等键 |
| 审查对象在变 | worktree 冻结（含脏文件） |
| 用户以为在守、其实没守 | 到期通知 + 面板「上次评估时刻」+ 管理台 `skipped_reason` |
| 审查者改了用户代码 | worktree + `writable: []` + 无 shell |
| 成本失控 | 值守有 `until`；单次预算 8 轮 / 240s；同 cwd 有活跃 run 不启动 |

## 12. 待定

1. 判据清单要不要写成声明式快照（现在靠 §4 的事实 + 原任务，没写成固定清单）。
2. 同 cwd 多个会话是否共享一次审查（允许各挂各的 ⇒ 3 倍钱；共享 ⇒ 幂等键要含 cwd）。
3. 审查期间用户发消息 ⇒ 人优先，审查让位（`capacity=2`，不是靠串行）。
4. `until` 默认值是否允许「长期」。
5. UI 细节：i18n 键、窄屏规则、通知落点、面板分页筛选、宏会话在侧栏怎么显示、前端测试判据。
