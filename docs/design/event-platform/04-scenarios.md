# 04 · 场景压测：六个典型宏，逐个搭

> 状态：可研（2026-11-07）。做法：拿真实场景去**压**宏的五格（[06](03-macro-model-and-catalog.md) §3），
> 压出裂的地方比压不裂的地方值钱——§8 汇总了六处，其中三处是 [06](03-macro-model-and-catalog.md) 写窄了。

---

## 1. 读法

每个场景填同一张表：`anchor_type` / `on_state` / `action` / `criteria` / `budget`。
填不满的那一格，就是设计缺口。**不要为了让表好看去编一个值。**

---

## 2. 场景一：session 完成 → 自动发邮件给用户（用户提的例子）

| 格 | 值 |
|---|---|
| `anchor_type` | **会话**（不是目录——见 §8.C） |
| `on_state` | `session.completed`（**派生值**，见下） |
| `action` | **通知型**：走 mail channel 发一封信（不起 run） |
| `criteria` | **零**（不需要验收——它只是通知，不是干活） |
| `budget` | 每会话每日 N 封 + **免打扰时段**（见 §8.D） |

**「完成」不是一个 state，是一个判断。** DB 里没有「完成」这一列，只有
`runs.status='finished'` + `termination.reason` 十个值。所以源必须**派生**：

```
session.completed  :=  status='finished'  AND  reason IN ('judge_done','end_turn')
session.failed     :=  status='failed'    （含 persistence_failed / final_guard_unverified）
session.capped     :=  reason='max_rounds_cap'
session.aborted    :=  reason='aborted'     ← 用户自己按的停止，不是失败
```

⚠ **派生规则必须写进源的定义并版本化，不能藏在宏里。** 否则「完成」会有两个定义：
邮件宏认为 `end_turn` 算完成，日报宏认为只有 `judge_done` 算——**同一个词两套语义**，
而这正是站内反复踩的那类坑（同一件事两种可见性 / 两个观测面）。

**为什么它是很好的第二个宏**：

- 判据零、成本零（不起 run、不烧 token）；
- 价值直接（人不在电脑前）；
- 但它**同时暴露了三处设计缺口**（§8.A / C / D）。

**一个必须先答的问题**：`object_key` 是会话还是 run？
- 若是**会话**：同一个会话里第二次 run 完成 ⇒ 幂等键 `(session, completed)` 与第一次相同 ⇒ **第二封信被吞掉**。
- 所以 `object_key` 必须是 **`run:<id>`**，`state=completed`。⇒ **每封信 = 每个 run 一封**。

这就是 §8.B：**`object_key` 的粒度决定幂等语义，选错就漏发或重发。**

## 3. 场景二（**反例**）：session 砖了 → 巡检 / 提醒 —— 这个**不是宏**

| 格 | 值 |
|---|---|
| `anchor_type` | ~~会话~~ |
| `on_state` | ~~`session.bricked`~~ |
| `action` | ~~起一个 run 跑巡检 SQL 修数据~~ |
| `criteria` | ① 下一次发消息不再报 `invalid_messages`；② 修数据的 `UPDATE` 行数 = 1（不是 0——站内踩过「`UPDATE 0` 看起来像幂等其实啥也没写」）；③ 备份表 `jsonb_array_length` 前后对得上 |
| `budget` | ~~每会话每日 1 次~~ |

**这一格我最初写成了宏，是错的。** 判据只有一句：**这件事平台能不能自己修好？**

- **能。** 会话砖化是**平台自己的缺陷**（账本形状那一族，站内修过六轮），不是世界的事实。
- 把它做成宏 = 让用户配一个规则去盯平台的 bug ⇒ **把平台的责任转嫁给用户**。

**第二条独立判据指向同一结论**：修账本是**破坏性**动作（`UPDATE` 历史行），而宏模型刻意不给这种能力
（[06](03-macro-model-and-catalog.md) §4）。**需要「破坏性 + 人工确认」才能做的事，不是宏，是工单。**

⇒ 它的正确形态是 **平台内置告警 + 运维手册**（`docs/ops/transcript-ledger-inspection.md`）：
不可配置、不可关闭、不需要用户配判据、不走宏引擎。详见 [09](03-macro-model-and-catalog.md) §14.2。

⚠ **这个反例的价值比它作为正例大得多**：它给出了一条能反复用的判据，
而「事件表」如果收进平台故障，**它就会变成 bug 列表**——而 bug 列表是无限的。

## 4. 场景三：收工提醒（git 灯红/黄）

已设计，见 [06](03-macro-model-and-catalog.md) §12。摘要：

| 格 | 值 |
|---|---|
| `anchor_type` | 目录 |
| `on_state` | `gitlight: uncommitted`（🔴）或 `unpushed`（🟡） |
| `action` | 通知型：投一句话到该目录最近活跃会话 |
| `criteria` | `git status --porcelain -uall` 为空 ∧（有远端时）`HEAD == refs/remotes/<r>/<br>` |
| `budget` | 每目录每日 1 次 |

**它的独特价值：验全链而不烧钱。** 源 → 影子表 → 谓词 → 边沿/状态 → 动作 → 血统 → 可见性，
七段全走一遍，成本 ≈ 0。

## 5. 场景四：上游发版 → 考据 → 派活

| 格 | 值 |
|---|---|
| `anchor_type` | **仓库**（`erixwong/erix-agent`，以及本站 pin） |
| `on_state` | `npm: new-version` → 再经语义源细分成 `trivial` / `breaking` / `blocked-by-upstream` |
| `action` | `trivial` → 任务型起升 pin 的 run；`breaking` → 通知人并附证据；`blocked` → 静默退避 |
| `criteria` | ① 引擎版本线闸 3 处同步；② 随包契约套件零放宽（红了要么改代码要么记理由）；③ `termination.reason` 全集逐项在册；④ 根/runner/前端三套基线给出数字且**判绿看退出码** |
| `budget` | 每仓库每日 1 次（真发版不会一天三次） |

**它是唯一需要两个源串联的场景**：机械源（`dist-tags.latest`）产事件，
语义源（一个 run）产**带证据的判断**（读了哪两个包目录的 diff、哪几条判据翻红、`npm pack` 的 `shasum`）。

**⚠ 一条真实教训要写进判据**：上游文档说删了 16 个导出，而 npm 上实际一个没删（§8.86）。
⇒ **判据不许读 CHANGELOG，只许读包真件**（`npm pack` + `dist.shasum` 对账 + 解包 `grep` 导出面）。
这就是「证据必须可复核」在宏里的具体形态。

## 6. 场景五：每天 9 点 → 昨天的日报

| 格 | 值 |
|---|---|
| `anchor_type` | **用户**（覆盖其所有目录）——第五种锚类型，见 §8.C |
| `on_state` | `clock: 09:00`（时钟源，**边沿**触发：一天一次） |
| `action` | 任务型：起一个 run 汇总昨天（哪些 run、哪些提交、哪些红过又变绿） |
| `criteria` | ① 每条结论带坐标（run id / sha / 文件名）；② **不许出现「应该」「可能」**；③ 报告落文件（不许只在对话里活着） |
| `budget` | 每用户每日 1 次 |

**时钟源是特殊的**：它不是「某对象处于某状态」，是「到点了」。所以它的 `object_key` 是日期
（`clock:2026-11-08`），`state='tick'`——**幂等键因此天然是「一天一次」**，不需要额外去重。
这是时钟源唯一比别的源简单的地方。

⚠ **但它是「状态型」伪装成「边沿型」的陷阱**：如果 tick 因为容量满被跳过，`clock:2026-11-08`
这一天就永远不会有 `tick` 了 ⇒ 日报**静默缺失**。⇒ 时钟源的谓词必须能补：
「今天还没有 `tick` 且已过 09:00」才是触发条件，而不是「刚好 09:00」。

**这条与站内 §8.87 同源**：判据落在「刚好那一刻」上，错过就没了；落在「状态」上才能补。

## 7. 场景六：预览端口起了但应用回 502

| 格 | 值 |
|---|---|
| `anchor_type` | **端口**（或目录） |
| `on_state` | `preview: listening-but-unhealthy` |
| `action` | 通知型：投一句话到该目录会话（附「403/502 分别是什么意思」） |
| `criteria` | 容器内 `curl -sS -o /dev/null -w '%{http_code}' 127.0.0.1:<port>/` 拿到 2xx/3xx（**零凭据**，见下） |
| `budget` | 每端口每日 2 次 |

**这个场景的价值：它说明某些源天然长在容器里。**

- 平台侧要知道「应用回什么」需要**一张预览票**（无票是 403，票要人点）——那是能力注入问题。
- 容器内 `curl 127.0.0.1:<port>` **零凭据、零出网**，而且正好是「应用自己看到的世界」。

⇒ 照抄 `collectListeners` 的形态：**探测在容器、结果捐在心跳载荷里、写失败只 warn、新鲜度在读侧过滤**
（[02](02-event-model-and-verdict.md) §4）。**不要为了这个去给平台发探针票。**

## 8. 六个场景（含一个反例）压出七处

### 8.A 「完成 / 失败」不是 state，是**派生值**

DB 里只有 `status` + `termination.reason`（10 个值）+ `errorCode`。语义层（「这算完成吗」）
必须由**源**显式派生并版本化。

⇒ 补进 [02](02-event-model-and-verdict.md) §2：**`state` 允许是派生值，但派生规则属于源的定义，不属于宏。**

### 8.B `object_key` 的粒度决定幂等语义

| 选错 | 后果 |
|---|---|
| `object_key = session`（「会话完成」） | 同会话第二次 run 完成时幂等键相同 ⇒ **第二封信被吞** |
| `object_key = run:<id>` | 每个 run 一封 ✅ |

⇒ 补进 [02](02-event-model-and-verdict.md) §9：**幂等键的 `object_key` 必须取「一次性的那个对象」，不是「持久的那个容器」。**

### 8.C 「会话」不是事实对象，是**作用域**与**投递目标**

我原先写「锚类型要加**会话**」（理由是砖化是会话的属性）。**那个理由随着 §3 的反例一起没了**——
砖化不是事件，所以**没有任何事件的事实对象是会话**。

正确的三层：

| 层 | 是什么 | 例 |
|---|---|---|
| **作用域**（订阅） | 我允许这个宏盯我哪些东西 | 我的所有目录 / 某个目录 / **我的所有会话** / 我的账号 |
| **事实对象** | 具体那个东西 | `run:<id>` / `dir:…` / `repo:…` / `port:<n>` / `service:tls` / `clock:<date>` |
| **投递目标** | 通知落在哪 | 该作用域下最近活跃的会话 / 新建会话 / 邮件 |

⇒ 用户那句「事件和 session 相关」在**投递**这一层成立，在**事实**这一层不成立。
`run` 终态的投递目标通常是「发起它的那个会话」——**投递相关，不等于事实相关。**

### 8.C ′. 新增一条判据：**平台能不能自己修好**（这是本文最值钱的一条）

| 能自己修 | ⇒ | **不是事件**，是平台健康面（[09](03-macro-model-and-catalog.md) §14.2） |
|---|---|---|
| 不能（要人决定 / 外部事实 / 用户的工作状态） | ⇒ | **是事件** |

它一刀切掉了四项：会话砖化、队列卡 `delivering`、租约耗尽、镜像漂移。
**没有这条判据，事件表会变成 bug 列表**——每发现一个 bug 就多一个「事件源」。

### 8.D 通知型宏必须有时段，不只是次数

`budget` 只有「每日 N 次」不够：凌晨 3 点给你发一封「session 完成」的邮件，你会关掉整个功能。
⇒ `budget` 拆成 **`max_per_day` + `quiet_hours`（默认 22:00–08:00，UTC+8）**。

而 `quiet_hours` 内的行为必须确定：**积压到窗口外合并发一封**（不是丢弃，不是逐条补发）。
「因为你睡觉所以没告诉你」和「因为没钱所以没告诉你」一样，**必须可见**。

### 8.E 发邮件不算「写外部系统」，写 GitHub 评论才算

[05](01-decision-and-feasibility.md) §18.1 把「平台写外部系统」整块延后了。这个场景把它切清楚了：

| 动作 | 性质 | 结论 |
|---|---|---|
| 发邮件 / 站内通知 | **平台自己的渠道**（`mail_settings` 已有、`users.email` 已有） | **不算外部写，可以做** |
| 在 GitHub/Gitea 上评论留痕 | 写**别人的**系统，且会暴露平台身份 | 仍延后，要单独裁决 |

⇒ 补进 [05](01-decision-and-feasibility.md) §18.1：**边界是「谁的渠道」，不是「出了容器没有」。**

### 8.F 宏没有消灭复杂度，它把复杂度**搬进了源**

场景五的「这周没有提交」、场景四的「这次升级会不会红几格」——这些判断**宏表达不了**，
必须由源算完，以 `state` 枚举的形式交出来。

```
用户自建规则：复杂度分散在 N 个用户写的规则里（N 大、不可测、不可审查）
宏模型：      复杂度集中在 M 个源里（M << N、可测、可审查、可版本化）
```

**这才是宏模型的真正论证**，不是「用户省事」。⇒ 补进 [06](03-macro-model-and-catalog.md) §1：
**宏是一次复杂度的集中，不是一次复杂度的消除。**

⚠ **代价要一起认**：源会变成平台里最重的代码。**每个源都必须有「它的 state 枚举是什么意思」的文档与判据**，
否则它就是一个黑箱，而黑箱里的判断没人能验——那就回到了「模型说了算」。

## 9. 六个场景 → 复杂度落在哪

| 场景 | 新增源 | 新增动作 | 新增判据 | 需要新能力吗 |
|---|---|---|---|---|
| ① 完成 → 邮件 | 派生 `run.completed` | **mail 通知**（已有 channel，缺「通知用」路径） | 零 | **需要**：通知模板 + 免打扰 |
| ~~② 砖了 → 巡检~~ | ~~派生 `session.bricked`~~ | — | — | **不是宏**（§3 反例）：平台自己修 + 内置告警 |
| ③ 收工提醒 | `gitlight`（已有） | 投递（已有） | 现成（`gitlight.js`） | 无 |
| ④ 上游发版 | npm `dist-tags`（新） | 起 run + 通知 | 现成（三套基线 + 版本线闸） | 无 |
| ⑤ 每天日报 | `clock`（新，很小） | 起 run | 新写（但有现成纪律可抄） | 无 |
| ⑥ 端口不健康 | **容器内探针**（照 `collectListeners`） | 通知 | 一条 `curl` | 无 |

**结论：六个场景里只有 ① 和 ② 需要真正的新能力，其余全是「已有零件的接线」。**

## 10. 建议的落地顺序

| 序 | 宏 | 验什么 | 成本 |
|---|---|---|---|
| 1 | **收工提醒** | 全链路（源→影子表→谓词→投递→血统→可见性），不烧钱 | ≈0 |
| 2 | **完成 → 邮件** | 通知通道 + 免打扰 + 派生 state 的版本化 | ≈0 |
| 3 | **每天日报** | 时钟源 + 补触发（状态型而非边沿型） | 1 run/天/人 |
| 4 | **上游发版** | 语义源 + 预算 + 证据纪律 | 1 run/次发版 |
| 5 | **端口不健康** | 容器内探针（为将来的 L0 探针负载打样） | ≈0 |
| ~~6~~ | ~~砖了 → 巡检~~ | — | **已移出宏范围**（§3）：它是平台缺陷，走内置告警 + 运维手册 |

⚠ 原第 6 个「砖了 → 巡检」**已移出宏范围**（§3）：修账本是破坏性动作，宏模型刻意不给这个能力。
