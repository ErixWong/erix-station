## 1. 先拆一个词：「模板」其实是三层

不拆开，管理台和用户面会各说各话。

| 层 | 是什么 | 谁定 | 能不能写逻辑 |
|---|---|---|---|
| **模板类型**（kind） | 代码里注册的几种行为骨架：`run-notify` / `run-silence-alert` / `scheduled-task`（第一版）· `run-review` / `run-recover`（**后续候选**） | **开发者** | 是（但只有开发者） |
| **模板实例**（template） | 管理台建的一条：`kind` + 参数 + 名字 + 可见范围 | **管理员** | ❌ 只填参数 |
| **订阅**（assignment） | 用户把某个模板实例挂到某个会话 | **用户** | ❌ 只有开/关 |

用户说的「管理台里的模板定义」= **第二层**；「下拉菜单 assign 到当前会话」= **第三层**。

⚠ **第一层不能开放给管理员**。理由不是保守，是 [06](03-macro-model-and-catalog.md) §5 那条：
判据要能被**变异测试**、被 review、被 diff。放进 DB 编辑就等于把判据变成数据，而数据不能被测试
—— 站内 #331「配了没人读」正是这一族的尸体。

## 2. 管理台：模板**实例化**，不是编辑器

### 2.1 界面长什么样

```
┌ 模板 ─────────────────────────────────────────────────────────┐
│ [+ 新建模板]                                                   │
│                                                                │
│  终态通知 · 默认            run-notify    all     [已启用]  ⋯  │
│  静默告警 · 15m             run-silence   all     [已启用]  ⋯  │
│  每日 9 点 · eric 的项目    scheduled     admin   [停用]    ⋯  │
│  ── 以下为后续候选 ───────────────────────────────────────────  │
│  完成审查 · 默认            run-review    all     [未实现]  ⋯  │
└────────────────────────────────────────────────────────────────┘
```

**没有连线画布、没有条件分支、没有表达式输入框。** 点「新建模板」是选一个 kind，
然后按那个 kind 的 schema 出 3–5 个字段。

### 2.2 每个 kind 的字段（= [10](05-first-macros.md) 的宏五格，只暴露该暴露的）

| kind | 管理员要填的 | 写死在代码里（不可改） |
|---|---|---|
| `run-notify` | 名字 · `states` 多选 · `channel` | `anchor_type=用户`、动作 = 站内通知 |
| `run-review` | 名字 · `review_depth`(0/1) · `on_fail`(回灌/仅通知) · `max_rounds` | 审查者工具面、判据三条、证据包 |
| `run-recover` | 名字 · `max_attempts` · `notify_channel` | 分诊表（[11](06-execution-and-recovery.md) §12.1）、哪些 reason 才起 agent |
| `scheduled-task` | 名字 · `at` · `cwd` · `task` · `maxRounds` | 状态型 tick 语义、jitter、失败必通知 |

⚠ **`run-review` / `run-recover` 的分诊表不可配置**：它决定「哪些失败该起 agent」。
让管理员改它 = 允许把 timeout 配成「起 agent 分析」，那是 [11](06-execution-and-recovery.md) §12.1 明令禁止的白烧钱。

### 2.3 模板实例的字段

| 字段 | 说明 |
|---|---|
| `id` | 平台生成 |
| `kind` | 四选一，**建完不可改** |
| `name` | 用户下拉里看到的字（≤ 40） |
| `params` | 该 kind 的参数字典（§2.2） |
| `audience` | `all` / `admin` |
| `enabled` | 全局开关（关掉 ⇒ 所有订阅一起失效） |
| `scope` | `session` / `user`（见 §3.2） |
| `created_by` / `created_at` | 审计 |

⚠ **`scope` 在建的时候就定死**：`scheduled-task` 只能是 `user`，其余只能是 `session`。
不允许「一个模板既能挂会话又能挂用户」—— 那会让「它到底在盯什么」变成运行时才知道的事。

### 2.4 `audience` 只有两档，理由同 [10](05-first-macros.md) §4.3 的枚举纪律

- `all`：所有用户都能在自己的会话里看到并 assign
- `admin`：只有管理员能 assign（运维型，如「号池审计」）

⚠ 不做「指定某几个用户」—— 那是权限系统，第一版不该长出来。

## 3. 用户面：会话头部一个下拉

### 3.1 位置：chip 与下拉**职责分开**

**会话头部**（标题右边），不是输入框旁边。理由：

- 输入框旁边是「发消息」的语义区，模板是「这个会话的长期设置」，放一起会让人以为发一次就生效一次
- 会话头部已经有标题、模型、git 灯这些「会话级设置」，同族

⚠ **一次点击只能做一件事**（初稿没写清，会把两个功能叠在同一个 chip 上）：

| 元素 | 点击后 |
|---|---|
| `自动化 · 2 启用` chip | 打开**流水抽屉**（[13](07-surfaces-and-panel.md)） |
| 抽屉内的 `[配置 ▾]` | 打开**模板下拉**（assign / 取消） |
| 抽屉内每条的 `[›]` | 展开该条详情 |

**为什么 chip 不直接开下拉**：流水才是用户想验证的东西（“它到底跑了没有”）；
配置是低频动作，放进抽屉里作为二级入口就够。

⚠ **入口不放左栏底部**：`SidebarPanel.vue:401` 的底部栈只有 `max-h-[50vh]` 一个滚动区，
且已被「监听段 + 目录树」占满，再塞一个入口会挤掉工作区导航。

### 3.2 ⚠ 只列**会话级**模板

| scope | 例子 | 在哪 assign |
|---|---|---|
| `session` | 终态通知、静默告警（**第一版**）；完成审查、失败恢复（**后续候选**） | **会话头下拉** |
| `user` | 每日 9 点定时任务（**第一版**，管理员代配） | **不在会话里** —— 它是用户级设置 |

⚠ **分期必须显式写出来**（评审 blocker）：[05](05-first-macros.md) 定了第一版只有
M1 / M8 / M7 三条，**不含审查与恢复**。本节前面的模板类型与下拉示例把它们列在一起，
容易被读成「第一版就有」——现按上表标为**后续候选**。

「assign 到当前会话」这句话天然只对 `session` scope 成立。定时任务不属于任何会话
（[08](06-execution-and-recovery.md)：它起自己的宏会话）。

⇒ **已定（2026-11-08，经独立评审后从“建议”升级为结论）**：
**用户面只做 `session` scope 的下拉；`user` scope 的由管理员在管理台直接指定给某个用户。**
这样用户面就真的是「一个下拉」，不需要第二个设置页。

⚠ **`user` scope 的流水不在用户面显示**（[13](07-surfaces-and-panel.md) §19.1）。
它自己起宏会话，结果在侧栏会话列表里可见 —— 不需要第二个流水面板。
初稿在 [13](07-surfaces-and-panel.md) §19 把这条列为“待定”，与本节的“已定”冲突，已统一。

### 3.3 交互：选中即生效，不插消息流

```
┌ 完成审查 ▾ ┐
│ ☑ 完成审查 · 默认     未通过时回灌一次，再不过邮件通知 │
│ ☐ 完成审查 · 严格     未通过时只通知，不回灌          │
│ ☐ 失败恢复            只在代码/工具类失败时启动        │
└──────────────────────────────────────────────────────┘
```

- 打勾即写库、即生效，**没有「保存」按钮**
- **不往消息流里插任何东西** —— 消息流是「发生过什么」，配置变更不是
- 已启用的模板在会话头部显示成一个 chip，点开可以取消

⚠ **为什么不做成「发一条消息就触发一次」**：那会把宏降级成 prompt 模板，
而它真正要的是「这个会话之后每次 run 结束都跑一遍」。两者的生命周期差一个数量级。

### 3.4 取消

点 chip 上的 ×，或在下拉里取消勾选。已触发的历史**不回滚**（它们已经发生了）。

## 4. 后台：执行器在 portal 进程里，与浏览器无关

### 4.1 为什么必须与浏览器无关

站内已有先例：[08](06-execution-and-recovery.md) 的队列**落在 DB**（`queued_inputs`），
因为 pi 那种「内存队列 + 浏览器回调」的形态，关页面就等于队列蒸发。

⇒ 模板订阅落 DB，执行器在 portal 进程内：

| 事件 | 浏览器 | 后台 |
|---|---|---|
| 用户 assign | 发一次 `PUT` | 写 DB |
| 用户关页面 | —— | **继续跑** |
| 用户换设备 | —— | 继续跑 |
| portal 重启 | —— | 从 DB 恢复（订阅是状态，不是内存） |
| 触发条件命中 | 不需要在线 | 执行动作 |

### 4.2 触发链

```
① 边沿（E1）：run 终态写入 → 同一事务/紧随其后 → 查该会话启用的 session 模板
                                            → 谓词求值 → 动作
② 状态（评估循环）：每 N 秒 → 静默告警、定时任务
```

⚠ **① 必须挂在「终态已 COMMIT」之后**：终态事务里做外部动作会把事务拉长，
且失败会连带回滚终态（站内 `drainQueueAfterRun` 就是这个形状，照抄）。

### 4.3 与 `capacity=1` 的关系

回灌会起新 run，而 `capacity=1` ⇒ 它排在人后面。这是**对的**：人优先于机器人。
但如果用户连续发消息，回灌会一直被挤 ⇒ 需要有「最多等多久就放弃并通知」的上限
（否则就是 [11](06-execution-and-recovery.md) §11.4 那个 `deferred` 的无限变体）。

## 5. 可见面（不能省）

「后台跑」的反面是「用户看不见它在跑」。没有可见面，「跑了但没触发」和「根本没跑」长得一模一样
—— 站内 #331 死光纤、#371 事件承接面都是这个死法。

### 5.1 会话头部：已启用 N 个

一行 chip：`⚙ 2 个模板`。点开是列表 + 每个的「上次触发时间 / 上次判决 / 下次预计」。

### 5.2 每次触发：消息流里一条分隔条

```
──────── 宏：完成审查 · 未通过（3 条未竟事宜）→ 已回灌 ────────
```

- 复用现有 `.roundsep` 分隔条（[#236]），不新增 UI 结构
- 判决用词与 [03](02-event-model-and-verdict.md) 的枚举一致：`通过` / `未通过` / `未达成` / `需人工`
- 点开能看到证据（审查报告、finding 列表）

### 5.3 「为什么没触发」

模板卡片上必须能回答这四问：

| 问题 | 数据 |
|---|---|
| 它看过吗 | `last_evaluated_at` |
| 谓词命中了吗 | `last_state` |
| 命中了为什么没动 | `skipped_reason`（预算 / 静默时段 / 人在场 / `deferred` 超时） |
| 动了结果如何 | `last_verdict` + 链接 |

⚠ **`skipped_reason` 是这一格的全部价值**。站内反复出现的「配置了但没有消费者」
在界面上表现为「开关是开的、什么都没发生」—— 只有 `skipped_reason` 能把它们分开。

## 6. 权限与 API 落点

### 6.1 端点（受 #450 边缘白名单约束）

| 端点 | 谁 | 落在哪个 host |
|---|---|---|
| `GET/POST/PATCH /api/admin/macro-templates` | 管理员 | `admin.<域>:9443` |
| `GET /api/macro-templates` | 用户（按 `audience` 过滤） | 用户面 |
| `GET/PUT /api/sessions/:id/macro-assignments` | 会话属主 | 用户面 |

⚠ **用户面的端点不能放 `/api/admin/*`**：管理台入口只白名单 `①SPA ②/api/admin ③/api/auth + /api/me`，
而用户入口**deny** `/api/admin/*`。把用户操作塞进 admin 路径 = 让用户去第二个 host 点开关。

### 6.2 属主校验

`macro-assignments` 的读写必须走 `fetchSession(client, sessionId, userId)`
—— 站内既有口径：不存在与不属于你**返回同一个 404**（不泄露存在性）。

### 6.3 第一版不做破坏性模板

模板动作只允许「通知 / 起 run / 回灌」三类。**没有**「自动提交」「重建容器」「改证书」。
理由：那些要么是 [10](05-first-macros.md) §5 的破坏性组合，要么是平台自愈。

## 7. 数据形状（只写形状，不写 DDL）

```
macro_templates
  id · kind · name · params(jsonb) · audience · scope · enabled
  created_by · created_at · updated_at

macro_assignments
  id · template_id · user_id · session_id(nullable，user scope 时为 null)
  enabled · created_at
  UNIQUE (template_id, user_id, session_id)

macro_runs          ← 每次触发的账（可见面靠它）
  id · assignment_id · anchor(object_key) · state · bucket
  verdict · skipped_reason · started_at · finished_at
  child_session_id(nullable) · child_run_id(nullable)
  UNIQUE (assignment_id, anchor, state, bucket)     ← 幂等
```

⚠ `macro_runs` 的 `UNIQUE` 是**幂等的唯一执行点**。没有它，
状态型模板会每分钟发一次，回灌型模板会无限循环。

## 8. 一个必须先定的分叉：模板是代码还是数据

这是本节唯一需要决策者拍的东西，两种都自洽，但代价完全不同。

| | **A. 模板类型 = 代码常量**（本文默认） | **B. 模板 = 管理台可编辑数据** |
|---|---|---|
| 管理员能做 | 选 kind + 填参数 + 起名 | 从零定义锚/状态/动作/判据 |
| 判据能不能被测试 | ✅ 变异测试、review、diff | ❌ 数据不能被测试 |
| 会不会腐烂 | 不会（跟着代码过 CI） | 会（#331 那一族） |
| 灵活性 | 四种骨架 × 参数 | 无限 |
| 风险 | 想做的事骨架里没有 ⇒ 要发版 | 管理员造出一个没人能审计的东西 |

**我的建议是 A**，理由不是保守：`run-review` 的判据（三条机械可查）和 `run-recover` 的分诊表
都是**已经踩过坑的结论**（[11](06-execution-and-recovery.md)），把它们变成可编辑数据
等于把踩坑记录变成可覆盖的配置。

⚠ 但 A 有一个真实代价：**管理员想要的骨架如果不存在，只能等发版**。
缓解办法：kind 的注册表写成一个数组，加一种 kind 是加一个文件 + 一条用例，
发版成本是「一个 PR」，不是「一次架构变更」。

## 10. 单位必须是「一次触发」，不是「一条配置」

| 视角 | 一行是什么 | 能回答 | 不能回答 |
|---|---|---|---|
| **配置列表** | 一条已启用的模板 | 开了没有、参数是什么 | 它到底跑过没有 |
| **触发流水** | 一次 trigger → action → result | 什么时候为什么动了、动了什么、结果如何 | 现在开了哪些 |

用户要的是**第二种**。第一种只能证明"我点了开关"，第二种才能证明"系统真的在替我干活"
—— 而后者才是这个平台的全部价值（[README](README.md) §14 第 8 条：「把我自己从八千行仪式里赎出多少小时」）。

⚠ **配置入口仍然要有**（[12](07-surfaces-and-panel.md) §3 的下拉），但它只是入口，不是证据。
两个东西分开：**下拉改配置，面板看流水。**

## 11. 位置与形态：**覆盖式**抽屉，不是并排

从会话头部的「自动化」chip 打开，形态**照抄** `DelegateChildDrawer.vue` 的现有实现：

```
DelegateChildDrawer.vue:217   <div class="fixed inset-0 z-50">
DelegateChildDrawer.vue:218     <div class="absolute inset-0 bg-black/40" @click="close">
DelegateChildDrawer.vue:225     class="absolute inset-y-0 right-0 w-full max-w-xl"
```

⇒ 它是**全屏遮罩 + 右侧覆盖面板**（`max-w-xl` = 576px），**不是**「消息流变窄 + 右栏并排」。

**本面板取 480–520px**（比 delegate 窄一档：宏流水没有子 run 的完整对话那么宽的需求）。

⚠ **这一条是本文初稿的 blocker（已改）**：初稿写「形状照 delegate 抽屉」，却画了一个
「左消息流 + 右面板」并排的线框 —— 两者布局后果完全不同（并排 ⇒ 消息流变窄；覆盖 ⇒ 消息流不变但被遮住）。
**承诺必须只有一个。**

为什么用覆盖而不是并排：

- **已有先例**：delegate 抽屉、`ModalShell` 都是遮罩层，站内没有「并排常驻面板」的范式
- **没有证据证明「消息流与流水需同时可读」**：用户 90% 的时间在消息流里，
  看流水时是「暂停读消息去查一件事」，不是「一边读一边查」
- 并排会再拆一次已有工作区（`WorkbenchView.vue:324-336` 已经是「流 → 状态条 → 队列条 → 输入框」四段）
- 侧栏底部堆叠区（`SidebarPanel.vue:401`）只有 `max-h-[50vh]` 一个滚动区，
  且已被「监听段 + 目录树」占满 ⇒ **主入口不能放那里**

```
┌─ 消息流（被遮罩，关闭后位置不变）───────────────┐
│  ……                                            │
│                            自动化 · 2 启用  [×] │
│                            [配置 ▾]            │
│ ───────────────────────────────────────────── │
│ 12:03 · run 9f3a · judge_done          已完成  │
│ 审查 run → 3 条未通过 → 已回灌                  │
│ ↑82k ↓3.1k · 4m12s                     [展开]  │
│ ───────────────────────────────────────────── │
│ 11:40 · run 7c21 · judge_done          已跳过  │
│ 静默时段 · 最近 5 次同原因              [›]    │
│ ───────────────────────────────────────────── │
│ 本会话用量 ↑124k ↓9.2k · 估算详情      [⌄]    │
└────────────────────────────────────────────────┘
```

## 12. 一条记录是什么

**默认两行**（时间/锚/状态 + 动作与结果），附注**只在有值时出现**：

```
12:03 · run 9f3a · judge_done              已完成
审查 run → 3 条未通过 → 已回灌
↑82k ↓3.1k · 4m12s · 深度 0
```

| 行 | 内容 | 从哪来 | 无值时 |
|---|---|---|---|
| trigger | 时间 + 锚 + state | `macro_runs.anchor` / `state` / `started_at` | 必填 |
| action | 做了什么（通知 / 起 run / 回灌 / 跳过） | 动作类型 + `skipped_reason` | 必填 |
| result | 判决（`pass` / `red` / `no-op-claim` / `needs-human`） | `macro_runs.verdict` | 必填 |
| 附注 | 成本 + 耗时 + 深度 | `child_run` 的 usage / `depth` | **整行隐藏，不填 0** |

⚠ **附注行按数据有无显示**（初稿写成「固定三行 + 附注」，那是空占位）。
没成本就不显示 `↑0 ↓0`，没链就不显示 `深度 0` —— 站内既有口径：
**「不知道」不渲染成 0**（`RunStatusBar.vue:155-186` 就是按数据可用性逐段显示的）。

⚠ **`depth` 只在链存在时显示**。审查回灌是唯一能成环的边（[11](06-execution-and-recovery.md) §13），
用户看到 `深度 1` 就知道「这已经是最后一轮了，再不过就要转人工」；
单条无链的记录写 `深度 0` 只是噪音。

## 13. 什么该显示，什么不该（这一节决定面板是工具还是噪音）

| 情况 | 显示吗 | 为什么 |
|---|---|---|
| 谓词**没命中**（run 是 `judge_done` 但模板只盯 `failed`） | ❌ **不显示** | 每个 run 每条模板都有一条，纯噪音 |
| 谓词命中 + 动作执行成功 | ✅ | 主体 |
| 谓词命中 + **被跳过**（预算 / 静默时段 / 人在场 / `409`） | ✅ **必须** | 否则「开关是开的但没反应」 |
| 动作执行**失败** | ✅ 红色 | |
| 评估本身出错（读不到数据） | ✅ | 否则就是静默失败 |

**「被跳过」是这一格的核心价值。** 站内反复出现的「配置了但没有消费者」
在界面上表现为「开关是开的、什么都没发生」—— 只有 `skipped_reason` 能把它们分开。

### 13.1 呈现分级：颜色不承重，文字才是判据

| 状态 | 颜色 | 文字 | 参考 |
|---|---|---|---|
| 成功 | **中性** | `已完成` | `.roundsep`（`style.css:17`） |
| 跳过 | **灰色** | `已跳过 · 静默时段` | 同上，更淡 |
| 失败 | **红** | `失败 · <原因>` | `.syserr`（`style.css:16`） |
| 额度风险 | **琥珀** | `额度用完 · 查看额度` | 借 `judge-panel` 的琥珀色（`style.css:19`）**但不借它的面板形态** |

⚠ **颜色必须伴随文字标签**，且完整口径同时进 `title` 与 `aria-label` ——
照 `GitLightBadge.vue:134-145` 的现成做法（那行注释写着「颜色不承重：点只是复述，语义在文字里」）。

⚠ **不要把所有宏状态涂成告警色**：`StreamPanel.vue:593` 把普通 `.roundsep`、
黄色 `judge-panel`、红色 `.syserr` 分开渲染，宏记录沿用这套语义区分，不要新造第四种告警色。

### 13.2 跳过要**聚合**，不要逐条占位

连续同因跳过不能一条一行（静默时段一晚上能攒十几条）：

```
11:40 · run 7c21 · judge_done              已跳过
静默时段 · 最近 5 次同原因                    [›]
```

- 主列表只留**一条**汇总行，展开才看每次的时刻
- **不同原因不合并**（`静默时段 ×3` 与 `额度用完 ×2` 是两件事）
- **`human_present` 写中性事实**（`你刚发了消息，不插话`），**不归责用户**

### 13.3 `skipped_reason` 的人话对照（不在 UI 暴露原始枚举）

| `skipped_reason` | 人话 | 呈现 |
|---|---|---|
| `budget_exhausted` | 今日额度用完（20/20） | 琥珀 + 「查看额度」 |
| `quiet_hours` | 静默时段（22:00–08:00） | 灰 |
| `human_present` | 你刚发了消息，不插话 | 灰 |
| `run_in_progress` | 会话里有 run 在跑 | 灰 |
| `deferred_timeout` | 等排位超过 10 分钟，放弃 | 灰 |

### 13.4 「它看过吗」单独一格

谓词没命中的评估**不进流水**，但用户仍然需要知道「这个模板是活的」。所以抽屉顶部
（配置区）每条模板后面跟一行：

```
完成审查 · 默认   已启用   上次评估 12:03:11   命中 3 次 / 跳过 1 次
```

**「上次评估」是活的证据**。没有它，一个坏掉的评估循环和一个「从来没命中过」的模板长得一样。

## 14. 审查链怎么显示

一次审查触发会生出 2–3 条记录，它们**不是并列的**，是一条链：

```
run 9f3a 结束（judge_done）
  └─ 审查 run 4b02 → 未通过 3 条
       └─ 回灌 → run c711 结束（judge_done）
            └─ 审查 run e35d → 未通过 1 条
                 └─ 转人工 → 邮件已发
```

显示形态：**默认折叠，首屏只给摘要 + 当前终态**。

初稿写「不做折叠 —— 四级折起来反而看不见」，**那条是错的**：
在 480–520px 的覆盖抽屉里，四级链的 run id、报告、动作文字会把主信息挤到看不见
（`DelegateChildDrawer.vue:322-330` 的工具行已经靠截断才放得下）。

```
run 9f3a 结束
  └─ 审查 run 4b02 → 未通过 3 条
       └─ 回灌 → run c711 …              另有 2 步  [⌄]
             └─ 转人工 · 已发邮件给 eric
```

四条口径：

1. **默认最多两层**，更深的收成「另有 N 步」
2. **链的末端必须常显**（`转人工 · 已发邮件给 eric` / `发送失败`），
   即使它在第三层 —— 否则用户看到「未通过」不知道接下来会发生什么
3. **竖线只在有子步骤时画**，单条记录不画连接线
4. **run id 与报告全文进详情**，不复制进流水行

不做图形化树、不做时间线视图 —— 第一版深度 ≤ 1（[11](06-execution-and-recovery.md) §13.3），
缩进 + 竖线够用。

⚠ 链的**末端必须明确**：`转人工` 那一行要写清「已发邮件给 eric」。
否则用户看到「未通过」却不知道接下来会发生什么。

## 15. 成本：逐条真实，汇总只给估算

「后台跑」的反面是「账单在你不知道的时候涨」。但**逐条与汇总是两种精度**，不能混：

| 层 | 显示什么 | 精度 |
|---|---|---|
| 每条记录 | `↑82k ↓3.1k · 4m12s` | **实测**（`runs.usage`） |
| 抽屉底部 | `本会话 12 次触发 · ↑1.2M ↓38k` | **实测** |
| 抽屉底部（折叠） | `≈ ¥x.xx（估算）` | **估算**，默认收起 |

⚠ **三条不能越过的线**（初稿写了「≈ ¥x.xx」常驻，是过度设计）：

1. **没有确认的单价就不显示金额** —— 单价来自 LiteLLM 的定价配置，可能没填（[#164] 那类「未设定价」）。
   没填就只给 token，不给钱。
2. **汇总范围必须先声明**（按会话 / 按模板 / 按人），否则同一个数字有两种读法。
   范围未定 ⇒ 只显示「本会话」。
3. **估算必须带「≈」和「估算」两个字**，且**默认折叠** —— 常驻金额会变成账单警报，
   而它本身并不精确。

⚠ 用量缺失写「未知」，**不补 0**（同 §12 附注行口径）。

这条是 [10](05-first-macros.md) §7「月成本必须可见」的落地形态：
**可见 ≠ 精确**。先保证能看到量级，再谈钱。

## 16. 刷新策略

| 时机 | 动作 |
|---|---|
| 打开抽屉 | 拉一次 |
| 有**未完成**的记录（`finished_at IS NULL`） | 每 2s 轮询 |
| 全部完成 | **停轮询** |
| 消息流收到 `run_end` | 拉一次（新记录可能刚生成） |
| 手动 ↻ | 拉一次 |

同 `#8.103` 的 delegate 抽屉形状：单飞、可见性门控、终态即停。
**不做常驻轮询** —— 面板关着的时候一个请求都不该发。

## 17. 空态：**四种业务态 + 三种技术态**

「什么都没发生」是这个面板最常见的状态，所以空态不能是一句"暂无数据"。
而且**加载失败不能伪装成空** —— 这是站内既有口径（`DelegateChildDrawer.vue:265-305`、
`PreviewPortsPanel.vue:266-280` 都把首次加载 / 错误 / 空列表分开渲染）。

### 17.1 技术态（与业务态分开，不可合并）

| 情形 | 该说什么 |
|---|---|
| 首次加载中 | skeleton / 「加载中」，**不显示空文案** |
| 加载失败 | 「加载失败」+ 重试按钮 + 错误原文（过 `toDisplayText`） |
| 无权限（会话不属于你） | 「无权查看」，**不伪装成「没有记录」** |

### 17.2 业务空态（四种）

| 情形 | 该说什么 |
|---|---|
| 没启用任何模板 | 「这个会话没挂模板」+ 一个「选择模板」按钮（直达下拉） |
| 启用了但从没触发 | 「已启用 2 个，还没触发过。上次评估 12:03:11」 |
| 启用了但一直被跳过 | 「最近 5 次都被跳过：额度用完 ×3、静默时段 ×2」+ 一句「要调额度吗」 |
| 筛选后为空（如只看失败） | 「没有匹配的记录」+ 清除筛选 |

### 17.3 ⚠ 健康告警**不放在流水的空白区**

初稿把「评估循环没跑」列在空态里，**位置错了**：它是平台健康，不是业务空态。
应放在抽屉**顶部状态条**（与流水列表分离）：

```
⚠ 上次评估在 47 分钟前，预期每 60 秒一次 · 宏可能不生效
```

理由：

- 空态区的文案会被当成「我这边没配置好」，而这是**平台的问题**
- 它可能在**有记录**时也存在（循环卡住但历史还在）⇒ 放空态里就永远看不见
- 必须给**最后成功时刻 + 预期频率 + 下一步**三个信息，否则用户不知道要不要管

## 18. 数据：复用 `macro_runs`

[12](07-surfaces-and-panel.md) §7 那张表就是面板的数据源，不需要新表：

|---|---|

| action | 动作类型 + `skipped_reason` |
| result | `verdict` |
| 链 | `parent_macro_run_id`（新增，指回上一条） |

## 19. 已定与待定

### 19.1 已定（不再开放）

| 事项 | 结论 | 依据 |
|---|---|---|
| 面板作用域 | **只做会话级** | [12](07-surfaces-and-panel.md) §3.2：第一版用户面只做 `session` scope |
| `user` scope 流水 | **不在用户面显示** —— 它由管理员代配，结果落在它自己的宏会话里（侧栏可见） | 同上 |
| 布局形态 | **覆盖式右抽屉 480–520px** | §11（`DelegateChildDrawer.vue:217-225`） |
| 深层链 | **默认折叠** | §14 |
| 月度金额 | **默认折叠 + 标估算 + 单价未定则不显示** | §15 |

⚠ **初稿把「user scope 流水放哪」列为待定，与 [12](07-surfaces-and-panel.md) §3.2 的「只做 session scope」冲突。**
一个文档说已定、一个说还开着 —— 这种「两头说法」是站内反复出现的事故形状（部署面说关、代码说开）。
现在统一到「已定」：**第一版用户面不显示 `user` scope 的流水**。

### 19.2 待定

1. **要不要给一个「显示未命中的评估」的调试开关**：默认关，排查时才开。
2. 面板里的「判决」要不要可点开看证据（审查报告全文）：点开 = 新页面 vs 展开区。
3. 月汇总的**单价来源**：从 LiteLLM 定价读，还是平台自己配一张价目表。
4. 抽屉宽度 480 还是 520 —— 需要真机量一次消息流剩余宽度。
